# 使用工作树运行并行会话

> 在单独的 git 工作树中隔离并行 Claude Code 会话，以便更改不会发生冲突。涵盖 `--worktree` 标志、子代理隔离、`.worktreeinclude`、清理和非 git VCS 挂钩。

[git worktree](<https://git-scm.com/docs/git-worktree>) 是一个单独的工作目录，拥有自己的文件和分支，与您的主要结帐共享相同的存储库历史记录和远程。在其自己的工作树中运行每个 Claude Code 会话都会为其提供要编辑的文件的单独副本，因此一个会话可以构建功能，而第二个会话可以修复错误。



**注释：**

工作树需要 git 存储库；对于其他版本控制系统，[配置钩子来替换git逻辑](<#非-git-版本控制>)。在 [ 桌面应用程序 ](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>) 中，启动会话时选择 ** 工作树 ** 选项，为其提供自己的工作树。


工作树是并行运行 Claude 的几种方法之一。他们隔离文件编辑。 [子代理](<https://code.claude.com/docs/en/sub-agents>)在一个会话中拆分工作，[跨会话消息传递](<https://code.claude.com/docs/en/cross-session-messaging>)允许Claude在工作树中的会话之间传递结果。请参阅 [并行运行 agents](<https://code.claude.com/docs/en/agents>) 来比较这些方法，或跳到 [使用工作树隔离子代理](<#使用工作树隔离子代理>)以一起使用工作树和子代理。

大多数会话只需要前两个部分：[在工作树](<#在工作树中启动-claude>)中启动Claude，然后[退出时清理](<#清理工作树>)。当您需要[恢复会话](<#恢复工作树会话>)、[更改工作树的创建方式](<#自定义工作树创建>)或[调试故障](<#故障排除>)时，请返回页面的其余部分。

## 在工作树中启动 Claude

传递 `--worktree` 或 `-w` 及其名称，以创建一个独立的工作树并在其中启动 Claude。默认情况下，工作树是在存储库根目录的 `.claude/worktrees/<name>/` 下创建的，位于名为 `worktree-<name>` 的新分支上：

```bash theme={null}
claude --worktree feature-auth
```

在另一个终端中使用不同的名称再次运行该命令以启动第二个隔离会话。如果省略名称，Claude 会生成一个名称，例如 `bright-running-fox`。

交互式运行需要 [ 工作空间信任 ](<https://code.claude.com/docs/en/security>)：如果您之前没有在目录中运行过 Claude，请运行 `claude` 接受信任对话框，否则 `--worktree` 将退出并显示错误提示。使用 `-p` 的非交互式运行会跳过信任检查，因此 `claude -p --worktree` 无需信任检查即可继续。



**提示：**

将 `.claude/worktrees/` 添加到您的 `.gitignore`，以便工作树内容不会在您的主结账中显示为未跟踪的文件。


### 设置工作树环境

工作树是一个新的签出，因此在那里初始化您的开发环境：要求Claude安装依赖项，或者在`.claude/worktrees/`下的工作树目录中自行运行项目的设置。要将 gitignored 文件（例如 `.env`）自动携带到每个新工作树中，请添加一个 [`.worktreeinclude` 文件 ](<#将-gitignored-文件复制到工作树中>)。

### 要求 Claude 创建工作树

您还可以要求 Claude 在会话期间“在工作树中工作”，它会使用 [`EnterWorktree`](<https://code.claude.com/docs/en/tools-reference>) 工具创建一个工作树。一旦进入一个工作树，Claude可以通过使用目标路径调用`EnterWorktree`直接切换到`.claude/worktrees/`下的另一个工作树；以前的工作树保持在磁盘上不变。

当 Claude 输入存储库的 `.claude/worktrees/` 目录之外的路径时，Claude Code 首先会请求您的批准，因为该移动会占用会话的工作目录、写入权限和项目配置（例如 `CLAUDE.md`）以及该位置的设置。 `EnterWorktree` [权限规则](<https://code.claude.com/docs/en/permissions>)或选择“不再询问”不会抑制此提示；只有`bypassPermissions`模式会跳过它。在v2.1.206之前，Claude无需询问即可进入任何现有的工作树路径。



**注释：**

**挂钩路径不遵循工作树。** Claude 进入工作树后，Claude Code 将 `${CLAUDE_PROJECT_DIR}` 保留在 [ 挂钩 ](<https://code.claude.com/docs/en/hooks#reference-scripts-by-path>) 中，并将工作树路径传递给它们另一种方式：

  * **`${CLAUDE_PROJECT_DIR}` 保持不变**：它仍然指向会话启动的项目根目录，因此诸如 `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` 之类的挂钩命令仍然在主结账中运行脚本。
  * **`cwd` 位于 Claude** 之后：钩子的 [ 输入 JSON](<https://code.claude.com/docs/en/hooks#common-input-fields>) 中的 `cwd` 字段是工作树根，当 Claude 运行 `cd` 时，它会再次移动。当钩子需要工作树路径时阅读它。



## 清理工作树

当您退出交互式工作树会话时，Claude 检查工作树中是否有删除会删除的工作：已更改或未跟踪的文件、已签出子模块内未提交的工作以及新提交。这些规则适用于使用 git 创建的工作树 Claude。对于您的 [WorktreeCreate 挂钩 ](<https://code.claude.com/docs/en/hooks#worktreecreate>) 创建的工作树，请参阅 [WorktreeRemove](<https://code.claude.com/docs/en/hooks#worktreeremove>)。

* **工作树很干净**：对于未命名的会话， Claude 自动删除工作树及其分支。一个 [命名的](<https://code.claude.com/docs/en/sessions#name-your-sessions>) 会话首先提示您，以便您可以保留工作树供以后使用
* **工作树中有工作**：Claude提示您保留或删除工作树。保留会保留目录和分支。要稍后返回，请运行 Claude Code 在退出时打印的 `claude --worktree <name> --resume` 命令。删除会删除工作树目录及其分支，以及其中的所有工作
* **无法验证工作树的状态**：当Claude Code无法计算工作树的更改或无法检查其子模块签出时，它会提示您而不是自动删除工作树。提示列出了它无法检查的内容

使用 `-p` 的非交互式运行没有退出提示，因此 Claude 不会清理其工作树，并且 Claude Code 会将其在创建时对每个工作树施加的锁定保留在适当的位置，直到稍后会话的 [ 陈旧锁扫描 ](<#清理子代理和后台会话工作树>) 释放它。要删除一个，请运行 `git worktree remove`；如果 git 因为工作树被锁定而拒绝，请先在其上运行 `git worktree unlock`。

在 Windows 上，删除工作树不会删除其外部的文件。如果工作树内的文件夹是到其他位置的链接，例如 NTFS 连接或目录符号链接，则 Claude Code 仅删除该链接并保留它指向的文件夹。在 v2.1.205 之前，删除带有嵌套在子目录中的链接的工作树可能会删除它指向的文件夹。

## 恢复工作树会话

当您恢复在工作树内结束的会话而不 [ 退出它 ](<#清理工作树>) 时，Claude Code 将会话返回到该工作树。这适用于交互式简历、[非交互模式](<https://code.claude.com/docs/en/headless>)和`-p`中的`--continue`和`--resume`，以及AgentSDK。 `--continue` 选择您启动目录下记录的最新会话。回到工作树内部，Claude仍然可以使用[`ExitWorktree`](<https://code.claude.com/docs/en/tools-reference>)工具退出它。

在将会话返回到其工作树之前，Claude Code 验证该工作树仍然是与主工作树分开的签出，并拒绝重新进入未通过检查的工作树。对于 git 工作树，检查会读取其 git 元数据。没有 git 元数据的工作树，例如创建的 [`WorktreeCreate` 钩子 ](<#非-git-版本控制>)，可以通过检查；案例 Claude Code 仍然拒绝，其恢复结果列在 [Claude Code 拒绝使用工作树 ](<#claude-code-拒绝使用工作树>) 下。有关消息以及如何从每个消息中恢复，请参阅 [会话在其工作树外部恢复 ](<#会话在其工作树之外恢复>)。

从哪里启动以及如何恢复，更改 Claude Code 重新输入的内容：

* **启动目录**：从主签出或存储库的其他目录中使用`--resume`恢复。 Claude Code 会重新进入它在 `.claude/worktrees/` 下使用 git 创建的工作树，即使您从其中启动也是如此。当您从任何其他工作树内部启动时，Claude Code 仅当它可以从那里保证它时才重新输入：一个工作树是它自己的存储库，一个没有 git 元数据的工作树，或者从您使用 `git worktree add` 创建的工作树的子目录启动会拒绝，因此从主结帐启动这些工作树。
* **`--fork-session`**：分叉会话在您启动 Claude 的目录中启动，并且 Claude Code 保持原始会话的工作树不变。
* **已删除工作树**：如果工作树目录不再存在，Claude Code将在您启动Claude的目录中恢复会话。它告诉您工作树已消失并清除会话的工作树绑定。



**注释：**

在 v2.1.212 之前，非交互式简历保留在起始目录中，并且 `ExitWorktree` 报告没有要退出的活动工作树会话。


当Claude进入或退出Claude Code用git创建的工作树时，记录如下：Claude Code将会话记录在会话的新工作目录下，与[`/cd`](<https://code.claude.com/docs/en/commands>)的方式相同，因此`/desktop`和`--resume`在那里找到它。退出以同样的方式将其移回。由 [`WorktreeCreate` 挂钩 ](<#非-git-版本控制>) 创建的工作树将其副本保存在启动目录中。需要 Claude Code v2.1.198 或更高版本。

## Claude Code 如何强制隔离

当会话在工作树中隔离时，Claude Code 会阻止该工具调用下面定义的检查。无论您使用 `--worktree` 启动会话、Claude 使用 `EnterWorktree` 输入工作树，还是恢复工作树会话，都适用相同的规则。

相同的强制执行涵盖了从隔离会话中生成的每个子代理 Claude。无论会话是交互式的还是在 [ 后台 ](<https://code.claude.com/docs/en/agent-view#how-file-edits-are-isolated>) 中运行，它都适用。 [在自己的工作树](<#使用工作树隔离子代理>)中运行的子代理进行相同的检查。它们的版本历史记录位于[写入子代理文件](<https://code.claude.com/docs/en/sub-agents#write-subagent-files>)下。

Claude Code 应用四项检查：

* **文件编辑**：Claude Code阻止以主结账中的路径为目标的`Edit`、`Write`或`NotebookEdit`。
* **命令工作目录**：Claude Code阻止Bash、PowerShell或Monitor命令，其工作目录解析为主签出，或其无法验证的工作目录位于其外部。
* **Git 重定向 **：Claude Code 阻止将 git 重定向到主结账的 Bash 或 Monitor 命令。在运行 git 之前，重定向可以通过 `git -C`、`--git-dir`、`GIT_DIR` 或 `GIT_WORK_TREE` 变量或 `cd` 进入主结账。
* **命令形状**：当无法从命令文本验证命令运行的任何 git 是否保留在工作树内时，Claude Code 会阻止 Bash 或 Monitor 命令。例如，当在运行时计算命令名称时，当无法解析语法时，或者当诸如 `${!name}` 或 `${ command; }` 之类的扩展可以运行文本未拼写的命令时，就会发生这种情况。 Claude Code告诉Claude如何重写被拒绝的命令，例如将其拆分为简单的、单独的命令。您无法关闭此检查。

这些检查读取编辑目标的路径、命令运行的目录以及命令的文本。它们都不会跟踪 shell 命令写入的文件，因此它们不会拒绝在不运行 git 的情况下写入主结帐的命令，例如 `cp` 或 shell 重定向。 Claude Code 将该命令视为与 [ 权限 ](<https://code.claude.com/docs/en/permissions>) 和 [ 沙箱 ](<https://code.claude.com/docs/en/sandboxing>) 设置下的任何其他 shell 命令一样。

这些检查适用于您从中启动 Claude Code 的存储库。它们还涵盖了链接工作树所链接的主结帐。对于 PowerShell 命令，Claude Code 仅应用工作目录检查。

Claude 将每次拒绝视为工具错误，该错误命名工作树并说明如何继续。对于被拒绝的命令，请参见[拒绝消息的含义以及如何清除它](<https://code.claude.com/docs/en/errors#command-blocked-by-the-worktree-isolation-checks>)。

## 使用工作树隔离子代理

子代理可以在自己的工作树中运行，因此并行编辑不会发生冲突。要求 Claude“为您的 agents 使用工作树”，或者通过将 `isolation: worktree` 添加到其 frontmatter 来使 [ 自定义子代理 ](<https://code.claude.com/docs/en/sub-agents#supported-frontmatter-fields>) 永久隔离。

`.claude/agents/` 中的这个子代理始终在其自己的工作树中运行：

```markdown theme={null}
---
name: refactorer
description: Applies mechanical refactors across many files
isolation: worktree
---

Apply the requested refactor across every affected file, then run the tests
and report the results.
```

每个子代理都会获得一个临时工作树，当子代理完成且没有任何更改时，Claude Code会自动删除该工作树；发生更改的工作树保留在磁盘上，直到下面的 [ 定期扫描 ](<#清理子代理和后台会话工作树>) 可以将其删除而不丢失工作。

子代理工作树使用与 `--worktree` 相同的 [ 基本分支 ](<#选择基础分支>)，因此它们从存储库的默认分支分支，除非 `worktree.baseRef` 设置为 `"head"`。

其自己的工作树中的子代理获取指令文件 [开始于](<https://code.claude.com/docs/en/sub-agents#what-loads-at-startup>) 来自您的主要对话，而不是来自其工作树。当该工作树位于默认位置时 `.claude/worktrees/`，子代理也不加载 `CLAUDE.md` 文件或 `.claude/rules/` 工作树的根目录，因为它读取那里的文件，即使这些文件在工作树的分支上不同。

### 清理子代理和后台会话工作树

Claude Code 运行定期扫描，一旦 Claude 为子代理和 [ 后台会话 ](<https://code.claude.com/docs/en/agent-view#how-file-edits-are-isolated>) 创建的工作树早于您的 [`cleanupPeriodDays`](<https://code.claude.com/docs/en/settings-reference#cleanupperioddays>) 设置，就会删除这些工作树，然后执行 [ 保留扫描规则](<https://code.claude.com/docs/en/claude-directory#cleaned-up-automatically>)。

当您将 [ 后台 ](<https://code.claude.com/docs/en/agent-view#send-the-session-to-the-background>) 会话设置为 `--worktree` 时，其工作树将成为扫描可以删除的后台会话工作树。在这些情况下，扫描会保留工作树：

* 工作树仍然保留工作：已更改或未跟踪的文件，或未推送的提交。
* 工作树中签出的子模块保存已更改或未跟踪的文件，或者 Claude Code 无法检查工作树的子模块。此检查需要 Claude Code v2.1.274 或更高版本。
* [也会阻止工作树创建的四种情况之一](<#git-lfs-content-is-missing-from-a-worktree-claude-code-created>)适用：Claude Code无法确定存储库配置定义了哪些过滤器驱动程序，或者找到了无法关闭的设置。
* 该工作树属于您尚未后台处理的 `--worktree` 会话，无论其年龄如何。
* 您自己使用 `git worktree add` 创建了工作树，即使您随后在其中运行了 `--worktree <name>` 会话并将该会话置于后台。

Claude Code 将标记写入它使用 git 创建的每个工作树的 git 元数据中，并且扫描会保留任何没有标记的工作树，包括创建的 [`WorktreeCreate` 钩子 ](<#非-git-版本控制>) 的工作树。

当 agent 运行时，Claude Code 在其工作树上保留 `git worktree lock`，以便并发清理无法删除它，并在 agent 完成时释放锁定。当会话运行时，Claude Code 在为后台会话创建的工作树上持有相同的锁，因此扫描将工作树保留在原位，并且 `git worktree remove` 拒绝删除它。

扫描还会释放为进程已退出的会话设置的锁 Claude Code，因此终止的后台会话不会使其工作树永久锁定。扫描永远不会释放您自己设置的锁定 `git worktree lock`。在 v2.1.210 之前，被终止的会话留下的锁会保留在原处，直到您运行 `git worktree unlock`。

要清理扫描保留的工作树，请运行 `git worktree remove`，如果工作树有未提交的更改或未跟踪的文件，请添加 `--force`。如果 git 由于工作树被锁定而拒绝，请先在其上运行 `git worktree unlock`。

## 自定义工作树创建

Claude Code 创建工作树的默认设置涵盖了大多数会话：它在 `.claude/worktrees/` 下创建它们，从存储库的默认分支中分支它们，并仅签出跟踪的文件。本节中的选项会更改这些默认值。

### 选择基础分支

新的工作树分支来自存储库的默认分支，因此大多数会话不需要此设置。在 [ 设置 ](<https://code.claude.com/docs/en/settings-reference#worktree>) 中设置 `worktree.baseRef` 以从当前工作分支。该设置接受两个值：

* `"fresh"`（默认）：来自远程存储库默认分支的分支，通常为 `main`，因此工作树从与远程匹配的干净树开始。
* `"head"`：来自当前本地 `HEAD` 的分支，因此工作树携带您未推送的提交和功能分支状态。在隔离需要对正在进行的工作进行操作的子代理时使用此选项。在工作树内部，`"head"` 解析为该工作树的 `HEAD`，而不是主结帐的。

您不能将 `worktree.baseRef` 设置为分支名称。要从特定的现有分支启动工作树，[直接使用 git 创建它](<#手动管理工作树>)。

对于 `"fresh"` 基础，Claude Code 使 `origin/HEAD` 保持最新：当在过去 24 小时内未获取存储库时，它会获取默认分支（上限为五秒），并在获取失败时使用本地缓存的引用。 fetch 永远不会等待终端中的输入，因此当 git 或 ssh 要求输入密码、密钥密码或确认新的 SSH 主机时，它也会被视为失败。如果未配置远程，或者 `origin/HEAD` 未在本地缓存且无法获取，则工作树将回退到当前本地 `HEAD`。在 v2.1.208 之前，新的工作树使用已在本地缓存的任何 `origin/HEAD`。

此示例从您当前的工作中创建每个新的工作树分支：

```json theme={null}
{
  "worktree": {
    "baseRef": "head"
  }
}
```

### 从拉取请求分支

要从特定拉取请求或合并请求分支，请传递以 `#` 为前缀的数字 `--worktree`、GitHub 拉取请求 URL 或 GitLab 合并请求 URL，例如 `https://gitlab.com/group/repo/-/merge_requests/123`。 Claude Code 从 `origin` 获取更改的头提交，并在 `.claude/worktrees/pr-<number>` 创建工作树。引用该参数，以便您的 shell 不会将 `#` 视为注释的开头：

```bash theme={null}
claude --worktree "#1234"
```

Claude Code仅读取URL中的编号。它始终从存储库的 `origin` 远程获取，并通过 `origin` 的主机选择获取路径：

* **github.com**：获取`pull/<number>/head`
* **gitlab.com**：获取`merge-requests/<number>/head`
* **GitHub 企业、自我管理 GitLab 或任何其他主机 **：首先尝试 `pull/<number>/head`，然后尝试 `merge-requests/<number>/head`

此提取从不等待终端中的输入。如果 git 或 ssh 要求输入密码、密钥密码或确认新的 SSH 主机，则提取会失败，并且 Claude Code 退出并显示 `Error creating worktree: Failed to fetch PR/MR #<number>` 消息。 `ssh-agent` 持有的密钥仍然有效，因此在开始之前将密钥加载到此处并手动运行 `git fetch` 一次以记录新主机。

在 v2.1.233 之前，Claude Code 只接受 `#<number>` 和 GitHub 样式的 `--worktree` 拉取请求 URL，并且始终获取 `pull/<number>/head`。

### 将 gitignored 文件复制到工作树中

工作树是全新签出的，因此主存储库中的未跟踪文件（例如 `.env` 或 `.env.local`）不存在。要在 Claude 创建工作树时自动复制它们，请将 `.worktreeinclude` 文件添加到项目根目录。

该文件使用 `.gitignore` 语法。仅复制与模式匹配且 gitignored 的文件，因此跟踪的文件永远不会重复。

如果您编写以 `**/` 开头的模式，并且您想要的文件位于整个 gitignored 的目录中，则仅当该目录本身与该模式匹配时，或者当 `**/` 后面的第一个名称是目录路径中的名称之一时，Claude Code 才会复制它们。例如，如果您编写 `**/.claude/skills/*.md`，则该名字为 `.claude`，因此 Claude Code 将匹配的文件从被忽略的 `.claude/` 目录中复制出来。要将文件从 `**/` 模式无法到达的忽略目录中复制出来，请在模式中命名该目录：写入 `vendor/**/config.json` 而不是 `**/config.json`。在 v2.1.239 之前，仅当目录本身与模式匹配时，Claude Code 才从完全忽略的目录中复制文件 `**/` 模式。

此 `.worktreeinclude` 将两个 env 文件和一个机密配置复制到每个新工作树中：

```text .worktreeinclude theme={null}
.env
.env.local
config/secrets.json
```

这适用于使用 git 创建的每个工作树 Claude Code：`--worktree` 工作树、[ 子代理工作树 ](<#使用工作树隔离子代理>) 以及 [ 桌面应用程序 ](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>) 中的并行会话。使用 [`WorktreeCreate` 挂钩 ](<#非-git-版本控制>)，复制挂钩脚本内的文件。

### 重用工作树名称

传递 `--worktree` 目录已存在的名称将打开现有工作树，而不是创建新工作树。

使用默认的 `"fresh"` [base](<#选择基础分支>)，当满足以下所有条件时，重新打开的工作树将重置为存储库的默认分支，而不是在其旧提示处继续：

* 它没有未提交的更改或未跟踪的文件。
* 它仍然位于为其创建的分支 Claude Code 上。
* 它没有自己的提交，或者它的拉取请求或合并请求被合并并且它的远程分支被删除。

Claude Code 仅从 git 状态检测合并情况：工作树推送到的远程分支不再存在，并且工作树中的每个提交都已经在默认分支上。

在所有其他情况下，Claude Code 在其旧尖端重新打开工作树：

* 工作树不满足任何条件。
* Claude Code 无法验证工作树的状态。
* `worktree.baseRef` 是 `"head"`。
* 该名称是拉取请求或合并请求引用。

在 v2.1.208 之前，当您重复使用名称时，Claude Code 总是在其旧尖端重新打开旧工作树。

### 用钩子替换工作树创建

配置 [`WorktreeCreate` 挂钩 ](<https://code.claude.com/docs/en/hooks#worktreecreate>) 以完全替换默认的 `git worktree` 逻辑，包括将工作树放置在 `.claude/worktrees/` 之外的位置。有关完整示例，请参阅[非 git 版本控制](<#非-git-版本控制>)。

## 工作树与主结帐共享哪些内容

工作树有自己的文件和分支，但它与主检出共享以下内容：

* **存储库的`.git`目录**：工作树中的git命令写入主存储库的共享`.git`目录，并且[沙箱](<https://code.claude.com/docs/en/sandboxing#filesystem-isolation>)允许这些写入，因此命令如`git commit` 在启用沙箱的情况下在工作树内部工作。
* **插件**：从主签出安装在[项目范围](<https://code.claude.com/docs/en/plugins/loading#find-where-a-plugin-is-enabled>)的插件也会加载到同一存储库的工作树中，因此您不需要为每个工作树重新安装它们。需要 Claude Code v2.1.200 或更高版本。
* **权限批准**：在工作树会话中为 Bash 命令选择“是，不再询问”会将规则保存到主签出的 `.claude/settings.local.json`，因此它适用于主签出和存储库的每个其他工作树，并且在工作树删除后仍然存在。在 Windows 上以及 Claude Code [ 不使用存储库根 ](<https://code.claude.com/docs/en/settings#where-claude-code-looks-for-each-file>) 的其他情况下，规则保留在该工作树中。在 v2.1.211 之前，工作树中授予的批准会保存在该工作树内，不会在其他地方应用，并且在删除工作树时会丢失。请参阅[保存批准的位置](<https://code.claude.com/docs/en/permissions#permission-system>)。
* **未跟踪的技能、agents 和命令**：当工作树签出的根目录没有 `.claude/skills` 目录时，例如因为您的 `.claude/skills` 被 gitignored，Claude Code 加载主签出的[工作树会话中的项目技能](<https://code.claude.com/docs/en/skills#where-skills-live>)。在具有自己的 `.claude/skills` 目录的工作树中，仅加载该副本。

相同的通读涵盖了`.claude/agents`和`.claude/commands`。对于技能，通读需要 Claude Code v2.1.277 或更高版本。

无论您使用 `--worktree` 还是使用 `git worktree add` 创建工作树，所有这些都适用。

在从 [ 桌面应用程序 ](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>) 启动的工作树会话中，Claude Code 从主签出的根而不是从工作树读取项目配置，例如设置、挂钩、技能、agents、命令和 [`.mcp.json`](<https://code.claude.com/docs/en/mcp#project-scope>) 服务器。挂钩命令在该根目录中运行，并且 `${CLAUDE_PROJECT_DIR}` 指向它。要访问 Claude 正在处理的文件，请从挂钩的 [`cwd` 输入字段 ](<https://code.claude.com/docs/en/hooks#common-input-fields>) 读取工作树的路径。 `CLAUDE.md` 文件和 `.claude/rules/` 仍从工作树加载。

## 手动管理工作树

当您需要签出特定的现有分支或将工作树放置在存储库之外时，可以直接使用 Git 创建工作树。

在新分支上创建工作树：

```bash theme={null}
git worktree add ../project-feature-a -b feature-a
```

从现有分支创建工作树，将 `fix-issue-456` 替换为存储库中已存在的分支：

```bash theme={null}
git worktree add ../project-bugfix fix-issue-456
```

在工作树中启动Claude：

```bash theme={null}
cd ../project-feature-a
claude
```

列出您的工作树：

```bash theme={null}
git worktree list
```

用完后将其删除：

```bash theme={null}
git worktree remove ../project-feature-a
```

有关完整命令参考，请参阅 [Git 工作树文档 ](<https://git-scm.com/docs/git-worktree>)。

## 非 git 版本控制

工作树隔离默认使用git。对于 SVN、Perforce、Mercurial 或其他系统，配置 [`WorktreeCreate` 和 `WorktreeRemove` 挂钩 ](<https://code.claude.com/docs/en/hooks#worktreecreate>) 以提供自定义创建和清理逻辑。由于该钩子替换了默认的 git 行为，因此当您使用 `--worktree` 时，不会处理 [`.worktreeinclude`](<#将-gitignored-文件复制到工作树中>)。而是将所有本地配置文件复制到挂钩脚本中。

此 `WorktreeCreate` 挂钩使用 `jq` 从标准输入上的 JSON 读取工作树名称，检出新的 SVN 工作副本，并打印目录路径，以便 Claude Code 可以将其用作会话的工作目录。将配置添加到您的[`settings.json`](<https://code.claude.com/docs/en/settings#where-settings-live>)：

```json theme={null}
{
  "hooks": {
    "WorktreeCreate": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash -c 'NAME=$(jq -r .name); DIR=\"$HOME/.claude/worktrees/$NAME\"; svn checkout https://svn.example.com/repo/trunk \"$DIR\" >&2 && echo \"$DIR\"'"
          }
        ]
      }
    ]
  }
}
```

将其与 `WorktreeRemove` 挂钩配对，以便在会话结束时进行清理。有关输入模式和删除示例，请参阅 [ 挂钩参考 ](<https://code.claude.com/docs/en/hooks#worktreecreate>)。

`WorktreeCreate` 挂钩还允许您在 git 存储库之外运行 [`/batch`](<https://code.claude.com/docs/en/commands#all-commands>)。然后，每个 `/batch` 子代理都会使用项目的版本控制命令发布其更改，并且当它无法打开拉取请求时，会报告其发布的内容。在 git 存储库外部运行 `/batch` 需要 Claude Code v2.1.281 或更高版本。

## 故障排除

Claude Code 在创建工作树、启动时输入工作树或将恢复的会话返回到工作树时报告以下错误。

### Claude Code启动时无法进入工作树

当Claude Code在启动时无法进入工作树目录时，它会打印一条命名路径的错误并以代码1退出。当 [`WorktreeCreate` 挂钩 ](<https://code.claude.com/docs/en/hooks#worktreecreate>) 打印其创建的目录以外的内容时，或者目录在设置后被删除时，可能会发生这种情况。

### 在符号链接路径上创建工作树失败

当 `.claude`、`.claude/worktrees` 或工作树目录本身是符号链接时，Claude Code 拒绝创建工作树，并且错误命名了符号链接路径。删除符号链接并重试。在 v2.1.212 之前，如果存储库已在这些路径之一包含已提交的符号链接，则工作树创建将遵循它，并且可以在存储库外部创建文件。

<h3 id="git-lfs-content-is-missing-from-a-worktree-claude-code-created">
 Git LFS 文件是创建的工作树 Claude Code 中的指针文件
</h3>

如果您使用 `git lfs install --local` 设置 [Git LFS](<https://git-lfs.com>)，则 Claude Code 创建的工作树包含 LFS 指针文件而不是真实文件。 `--local` 标志将 LFS 过滤器写入存储库自己的 `.git/config` 而不是全局 git 配置。普通的 `git lfs install` 写入您的全局配置并且不受影响。这同样适用于存储库自己的配置中定义的任何其他[过滤器驱动程序](<https://git-scm.com/docs/gitattributes>)。

Claude Code 在创建工作树时会跳过存储库自己的过滤器驱动程序，因为过滤器驱动程序是一个 shell 命令，任何可以写入存储库的内容（包括 Claude）都可以在那里放置一个。在 v2.1.247 之前，Claude Code 在工作树创建期间运行这些驱动程序。

要获取真实文件，请在工作树内运行 `git lfs pull`。

在四种罕见的情况下，Claude Code 根本不创建工作树：它无法分辨存储库的配置定义了哪些过滤器驱动程序，或者它发现了一个无法关闭的设置。将错误与其修复相匹配：

* **`Could not read the repository git config to neutralize filter drivers`**：Claude Code 无法读取存储库的 `.git/config`，例如由于其权限问题。修复该问题并重试。
* **`The repository git config defines a filter driver whose name cannot be neutralized (contains "=" or a newline)`**：重命名或删除`.git/config`中的筛选器驱动程序，然后重试。
* **`The repository git config has a conditional include (includeIf)`**：将`.git/config`中的`includeIf`直接拉入该文件中的设置，删除`includeIf`，然后重试。全局 git 配置中的 `includeIf` 不会触发此操作。
* **`Git was not run: the repository's own git config sets <key>`**：消息命名一个键，将 Git LFS 指向要运行的程序，例如 `lfs.customtransfer.<name>.path` 或 `lfs.standalonetransferagent`。如果该设置是您的，请将其移至您的全局 git 配置。如果您不认识它，请将其从存储库的 git 配置中删除，因为您不信任的工具或签出可能已经写入了它。一旦密钥从存储库的配置中消失，请重试。

### Claude Code 拒绝使用工作树

启动 `Refusing to use <path> as an isolation worktree` 的错误意味着 Claude Code 在采用目录的 git 身份作为会话或子代理的隔离签出之前检查了该目录，并拒绝了它。该检查运行 Claude Code 是否正在创建工作树、输入现有工作树或重用先前运行中的工作树。

在大多数情况下，消息的其余部分表示目录的 git 元数据解析为主要签出：例如，其 `.git` 文件指向主存储库自己的 `.git` 目录，或者 git 通过 `core.worktree` 重定向将其工作树解析为主要签出。在这样的目录中，普通的 git 命令（例如 `git reset --hard`）将作用于主结帐而不是工作树。当目录具有无法读取的 `.git` 条目时，Claude Code 也会拒绝，而不是假设工作树是安全的。

根本没有 git 元数据的目录，例如您的 [`WorktreeCreate` 挂钩 ](<#非-git-版本控制>) 创建的目录，仅当没有 git 存储库包含它时才会通过检查。如果挂钩在存储库内创建目录，git 会将其解析为该存储库的签出，并且 Claude Code 使用 `git resolves its working tree to` 消息拒绝它，因此让挂钩在任何存储库外部创建其目录。

Claude Code 将拒绝的目录保留在适当的位置，因为它可能会保留工作。将消息与其恢复相匹配，无论它是在 `Refusing to use <path>` 之后还是出现在 [ 恢复消息 ](<#会话在其工作树之外恢复>) 中；有些结尾仅出现在简历消息中：

* **说`launch from the parent checkout`或`Run the resume from the project checkout`**：您从工作树内部启动了Claude Code。而是从主结账处启动；工作树不需要娱乐。
* **说`it cannot be resumed or re-entered`**：此会话中没有任何内容可以保证您启动的工作树。重新创建它；该目录及其工作保留在磁盘上以进行手动恢复，并且当工作树具有父检出时，从那里恢复也可以。
* **说`it contains the protected checkout`**：被拒绝的目录是您的主结账的父目录，例如您的主目录。不要删除它。更改工作树路径，例如 `WorktreeCreate` 挂钩返回的路径或 `EnterWorktree` 目标，以便工作树不包含结账。
* **说`the protected checkout <path> has a .git entry that could not be examined`或`has git metadata that could not be resolved`**：问题是主要签出的git元数据，而不是工作树的。不要删除工作树，并忽略消息的尾随建议来重新创建它，这不适用于这两个结局。修复主要签出，例如权限问题或 git `dubious ownership` 拒绝其 `.git`，然后重试。
* **说`its recorded path has a network spelling`**：Claude Code永远不会恢复到网络路径上的工作树中。在本地路径重新创建工作树。
* **任何其他结尾**：消息指出问题及其修复，例如删除`core.worktree`重定向或重新创建工作树；跟随它。在删除消息表明其 git 身份无法验证的目录之前，请首先解决指定的原因，例如工作树路径中的符号链接或 git 本身无法运行，因为该目录可能是健康的。当您重新创建时，首先从旧目录中挽救您需要的任何更改；它保留在磁盘上。

### 会话在其工作树之外恢复

当您以交互方式恢复会话并且 Claude Code 无法将其返回到其工作树时，Claude Code 会通过以下消息之一进行说明。当 Claude Code 清除工作树绑定时，它会将清除记录在会话记录中。如果您[禁止转录写入](<https://code.claude.com/docs/en/sessions#where-transcripts-are-stored>)，则消息会显示绑定无法清除，并且Claude Code将在稍后的简历中重新检查工作树。

|消息开头为|发生了什么以及该怎么做|
| :- | :- |
| `Your worktree <path> no longer exists` |工作树目录已被删除。会话在当前目录中继续而不隔离，并且 Claude Code 清除工作树绑定。无需采取任何行动。|
| `Could not verify your worktree <path> this time` |Claude Code 无法验证工作树，通常是由于暂时的原因；保留绑定，并且会话在当前目录中继续而不隔离。再次恢复重试；如果这种情况持续发生，请在新会话中输入工作树，并匹配 [Claude Code 拒绝使用工作树 ](<#claude-code-拒绝使用工作树>) 下的拒绝消息，该消息可以命名主结帐的元数据而不是工作树的元数据。|
| `Did not re-enter your worktree <path>` |Claude Code 拒绝工作树绑定，因为它不安全；它清除绑定并且会话继续而不隔离。该消息包括特定的拒绝：在[Claude Code下匹配它拒绝使用工作树](<#claude-code-拒绝使用工作树>)，因为修复是对某些拒绝的重新创建和对其他拒绝的路径更改。|
| `Could not re-enter your worktree <path>` |Claude Code 无法保证您启动的工作树，最常见的是因为您是从工作树内部启动的；绑定被保留。消息的其余部分命名了修复程序；在[Claude Code下匹配它拒绝使用工作树](<#claude-code-拒绝使用工作树>)。|

在带有 `-p` 的 [ 非交互模式 ](<https://code.claude.com/docs/en/headless>) 下，并且在 [Agent SDK](<https://code.claude.com/docs/en/agent-sdk/sessions>) 运行的恢复中，Claude Code 对于除消失的工作树之外的每次拒绝都会停止恢复并显示 stderr 错误，而不是在没有隔离的情况下继续。

对于 `--output-format stream-json`，拒绝也会作为子类型为 `error_during_execution` 的 `result` 消息到达标准输出，其 `errors` 数组携带相同的文本，因此 Agent SDK 应用程序会收到原因，而不仅仅是非零退出。在 v2.1.260 之前，工作树恢复拒绝不会产生 `result` 消息。

这些消息的形状与表中的交互式消息不同：

* `Error: cannot resume into worktree <path>: ...This session was not started.` 对于拒绝，该表显示为 `Did not re-enter`。 Claude Code退出前清除工作树绑定，错误是这样说的；下次恢复对话时，会话将在当前目录中继续，而不进行工作树隔离。在v2.1.260之前，Claude Code没有写入清除的绑定，因此每次重试同一简历都会失败并出现相同的错误。

如果您[禁止转录写入](<https://code.claude.com/docs/en/sessions#where-transcripts-are-stored>)，则无法保存清除内容。然后，该错误表示相同的命令将再次被拒绝，并命名 `--fork-session` 并开始新的对话，作为在没有工作树的情况下继续的方法。
* `Error: could not verify worktree <path> for this resume, so the resume was aborted...` 为 `Could not verify`
* `Error: ...The worktree binding is kept.` 为 `Could not re-enter`
* `Notice: the worktree <path> for this session no longer exists...` 已消失的工作树； Claude Code 打印它并继续会话，就像交互式简历一样

每个错误中嵌入的拒绝结尾与交互式通知共享，因此它仍然与 [Claude Code 拒绝使用工作树 ](<#claude-code-拒绝使用工作树>) 下的条目匹配。

在stream-json结果中，[`startup_failure_reason`](<https://code.claude.com/docs/en/agent-sdk/typescript#startup_failure_reason>)对于`could not verify worktree`错误是`worktree_unverified`，对于`cannot resume into worktree`和`The worktree binding is kept`错误是`worktree_resume_refused`。应用程序可以在其上分支，而不是匹配错误文本。在v2.1.274之前，结果不携带`startup_failure_reason`字段。

# Run parallel sessions with worktrees

> Isolate parallel Claude Code sessions in separate git worktrees so changes don't collide. Covers the `--worktree` flag, subagent isolation, `.worktreeinclude`, cleanup, and non-git VCS hooks.

A [git worktree](<https://git-scm.com/docs/git-worktree>) is a separate working directory with its own files and branch, sharing the same repository history and remote as your main checkout. Running each Claude Code session in its own worktree gives it a separate copy of the files to edit, so one session can build a feature while a second fixes a bug.



**注释：**

  Worktrees require a git repository; for other version control systems, [configure hooks to replace the git logic](<#non-git-version-control>). In the [desktop app](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>), select the **worktree** option when you start a session to give it its own worktree.


Worktrees are one of several ways to run Claude in parallel. They isolate file edits. [Subagents](<https://code.claude.com/docs/en/sub-agents>) split work up inside one session, and [cross-session messaging](<https://code.claude.com/docs/en/cross-session-messaging>) lets Claude pass findings between the sessions in your worktrees. See [Run agents in parallel](<https://code.claude.com/docs/en/agents>) to compare the approaches, or skip ahead to [Isolate subagents with worktrees](<#isolate-subagents-with-worktrees>) to use worktrees and subagents together.

Most sessions need only the first two sections: [start Claude in a worktree](<#start-claude-in-a-worktree>), then [clean up when you exit](<#clean-up-worktrees>). Return to the rest of the page when you need to [resume a session](<#resume-a-worktree-session>), [change how worktrees are created](<#customize-worktree-creation>), or [debug a failure](<#troubleshooting>).

## Start Claude in a worktree

Pass `--worktree` or `-w` with a name to create an isolated worktree and start Claude in it. By default, the worktree is created under `.claude/worktrees/<name>/` at your repository root, on a new branch named `worktree-<name>`:

```bash theme={null}
claude --worktree feature-auth
```

Run the command again with a different name in another terminal to start a second isolated session. If you omit the name, Claude generates one such as `bright-running-fox`.

Interactive runs require [workspace trust](<https://code.claude.com/docs/en/security>): if you haven't run Claude in the directory before, run `claude` once there to accept the trust dialog, or `--worktree` exits with an error prompting you to. Non-interactive runs with `-p` skip the trust check, so `claude -p --worktree` proceeds without it.



**提示：**

  Add `.claude/worktrees/` to your `.gitignore` so worktree contents don't appear as untracked files in your main checkout.


### Set up the worktree environment

A worktree is a fresh checkout, so initialize your development environment there: ask Claude to install dependencies, or run your project's setup yourself in the worktree directory under `.claude/worktrees/`. To carry gitignored files such as `.env` into every new worktree automatically, add a [`.worktreeinclude` file](<#copy-gitignored-files-into-worktrees>).

### Ask Claude to create a worktree

You can also ask Claude to "work in a worktree" during a session, and it creates one with the [`EnterWorktree`](<https://code.claude.com/docs/en/tools-reference>) tool. Once in a worktree, Claude can switch directly to another one under `.claude/worktrees/` by calling `EnterWorktree` with the target path; the previous worktree stays on disk untouched.

When Claude enters a path outside the repository's `.claude/worktrees/` directory, Claude Code asks for your approval first, because the move takes the session's working directory, write access, and project configuration such as `CLAUDE.md` and settings to that location. An `EnterWorktree` [permission rule](<https://code.claude.com/docs/en/permissions>) or choosing "don't ask again" doesn't suppress this prompt; only `bypassPermissions` mode skips it. Before v2.1.206, Claude could enter any existing worktree path without asking.



**注释：**

  **Hook paths don't follow the worktree.** After Claude enters a worktree, Claude Code keeps `${CLAUDE_PROJECT_DIR}` in your [hooks](<https://code.claude.com/docs/en/hooks#reference-scripts-by-path>) where it was and passes the worktree path to them a different way:

  * **`${CLAUDE_PROJECT_DIR}` stays put**: it still points at the project root where the session started, so a hook command such as `${CLAUDE_PROJECT_DIR}/.claude/hooks/check-style.sh` still runs the script in the main checkout.
  * **`cwd` follows Claude**: the `cwd` field in the hook's [input JSON](<https://code.claude.com/docs/en/hooks#common-input-fields>) is the worktree root, and it moves again when Claude runs `cd`. Read it when a hook needs the worktree path.



## Clean up worktrees

When you exit an interactive worktree session, Claude checks the worktree for work that removal would delete: changed or untracked files, uncommitted work inside checked-out submodules, and new commits. These rules apply to worktrees Claude created with git. For a worktree your [WorktreeCreate hook](<https://code.claude.com/docs/en/hooks#worktreecreate>) created, see [WorktreeRemove](<https://code.claude.com/docs/en/hooks#worktreeremove>) instead.

* **The worktree is clean**: for an unnamed session, Claude removes the worktree and its branch automatically. A [named](<https://code.claude.com/docs/en/sessions#name-your-sessions>) session prompts you first so you can keep the worktree for later
* **The worktree has work in it**: Claude prompts you to keep or remove the worktree. Keeping preserves the directory and branch. To return later, run the `claude --worktree <name> --resume` command that Claude Code prints on exit. Removing deletes the worktree directory and its branch, along with all the work in them
* **The worktree's state can't be verified**: when Claude Code can't count the worktree's changes or can't inspect its submodule checkouts, it prompts you rather than removing the worktree automatically. The prompt names what it couldn't check

Non-interactive runs with `-p` have no exit prompt, so Claude doesn't clean up their worktrees, and Claude Code leaves the lock it took on each one at creation in place until a later session's [stale-lock sweep](<#clean-up-subagent-and-background-session-worktrees>) releases it. To remove one, run `git worktree remove`; if git refuses because the worktree is locked, run `git worktree unlock` on it first.

On Windows, removing a worktree doesn't delete files outside it. If a folder inside the worktree is a link to somewhere else, such as an NTFS junction or a directory symlink, Claude Code deletes only the link and keeps the folder it points to. Before v2.1.205, removing a worktree with a link nested in a subdirectory could delete the folder it pointed to.

## Resume a worktree session

When you resume a session that ended inside a worktree without [exiting it](<#clean-up-worktrees>), Claude Code returns the session to that worktree. This holds for interactive resumes, for `--continue` and `--resume` in [non-interactive mode](<https://code.claude.com/docs/en/headless>) with `-p`, and for the Agent SDK. `--continue` picks the most recent session recorded under the directory you launch from. Back inside the worktree, Claude can still exit it with the [`ExitWorktree`](<https://code.claude.com/docs/en/tools-reference>) tool.

Before returning the session to its worktree, Claude Code verifies that the worktree is still a checkout separate from the main one, and declines to re-enter a worktree that fails the check. For a git worktree, the check reads its git metadata. A worktree without git metadata, such as one a [`WorktreeCreate` hook](<#non-git-version-control>) created, can pass the check; the cases Claude Code still refuses are listed with their recoveries under [Claude Code refuses to use a worktree](<#claude-code-refuses-to-use-a-worktree>). For the messages and how to recover from each, see [The session resumes outside its worktree](<#the-session-resumes-outside-its-worktree>).

Where you launch from, and how you resume, change what Claude Code re-enters:

* **Launch directory**: resume with `--resume` from the main checkout or another directory of the repository. Claude Code re-enters a worktree it created with git under `.claude/worktrees/` even when you launch from inside it. When you launch from inside any other worktree, Claude Code re-enters it only if it can vouch for it from there: a worktree that is its own repository, one without git metadata, or a launch from a subdirectory of a worktree you created with `git worktree add` declines, so launch those from the main checkout.
* **`--fork-session`**: the forked session starts in the directory you launched Claude from, and Claude Code leaves the original session's worktree untouched.
* **Deleted worktree**: if the worktree directory no longer exists, Claude Code resumes the session in the directory you launched Claude from. It tells you the worktree is gone and clears the session's worktree binding.



**注释：**

  Before v2.1.212, a non-interactive resume stayed in the starting directory and `ExitWorktree` reported that there was no active worktree session to exit.


When Claude enters or exits a worktree that Claude Code created with git, the transcript follows: Claude Code records the session under the session's new working directory, the same way [`/cd`](<https://code.claude.com/docs/en/commands>) does, so `/desktop` and `--resume` find it there. Exiting moves it back the same way. A worktree created by a [`WorktreeCreate` hook](<#non-git-version-control>) keeps its transcript at the launch directory. Requires Claude Code v2.1.198 or later.

## How Claude Code enforces isolation

While a session is isolated in a worktree, Claude Code blocks the tool calls the checks below define. The same rules apply whether you started the session with `--worktree`, Claude entered a worktree with `EnterWorktree`, or you resumed a worktree session.

The same enforcement covers every subagent Claude spawns from the isolated session. It applies whether the session is interactive or runs in the [background](<https://code.claude.com/docs/en/agent-view#how-file-edits-are-isolated>). [Subagents that run in their own worktree](<#isolate-subagents-with-worktrees>) carry the same checks. Their version history is under [Write subagent files](<https://code.claude.com/docs/en/sub-agents#write-subagent-files>).

Claude Code applies four checks:

* **File edits**: Claude Code blocks an `Edit`, `Write`, or `NotebookEdit` that targets a path in the main checkout.
* **Command working directory**: Claude Code blocks a Bash, PowerShell, or Monitor command whose working directory resolves to the main checkout, or whose working directory it can't verify stays outside it.
* **Git redirects**: Claude Code blocks a Bash or Monitor command that redirects git into the main checkout. The redirect can come through `git -C`, `--git-dir`, a `GIT_DIR` or `GIT_WORK_TREE` variable, or a `cd` into the main checkout before running git.
* **Command shape**: Claude Code blocks a Bash or Monitor command when it can't verify from the command text that any git the command runs stays inside the worktree. That happens, for example, when the command name is computed at runtime, when the syntax can't be parsed, or when an expansion such as `${!name}` or `${ command; }` could run a command the text doesn't spell out. Claude Code tells Claude how to rewrite the refused command, such as splitting it into plain, separate commands. You can't turn this check off.

These checks read the path an edit targets, the directory a command runs in, and the text of the command. None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as `cp` or a shell redirect, isn't refused by them. Claude Code treats that command like any other shell command under your [permissions](<https://code.claude.com/docs/en/permissions>) and [sandboxing](<https://code.claude.com/docs/en/sandboxing>) settings.

The checks apply to the repository you launched Claude Code from. They also cover the main checkout a linked worktree is linked from. For PowerShell commands, Claude Code applies only the working-directory check.

Claude sees each refusal as a tool error that names the worktree and says how to proceed. For a refused command, see [what the refusal message means and how to clear it](<https://code.claude.com/docs/en/errors#command-blocked-by-the-worktree-isolation-checks>).

## Isolate subagents with worktrees

Subagents can run in their own worktrees so parallel edits don't conflict. Ask Claude to "use worktrees for your agents", or make the isolation permanent for a [custom subagent](<https://code.claude.com/docs/en/sub-agents#supported-frontmatter-fields>) by adding `isolation: worktree` to its frontmatter.

This subagent in `.claude/agents/` always runs in its own worktree:

```markdown theme={null}
---
name: refactorer
description: Applies mechanical refactors across many files
isolation: worktree
---

Apply the requested refactor across every affected file, then run the tests
and report the results.
```

Each subagent gets a temporary worktree that Claude Code removes automatically when the subagent finishes without changes; a worktree with changes stays on disk until the [periodic sweep below](<#clean-up-subagent-and-background-session-worktrees>) can remove it without losing work.

Subagent worktrees use the same [base branch](<#choose-the-base-branch>) as `--worktree`, so they branch from your repository's default branch unless `worktree.baseRef` is set to `"head"`.

A subagent in its own worktree takes the instruction files it [starts with](<https://code.claude.com/docs/en/sub-agents#what-loads-at-startup>) from your main conversation, not from its worktree. When that worktree is in the default location under `.claude/worktrees/`, the subagent also doesn't load the `CLAUDE.md` file or `.claude/rules/` directory at the worktree's root as it reads files there, even if those differ on the worktree's branch.

### Clean up subagent and background-session worktrees

Claude Code runs a periodic sweep that removes worktrees that Claude created for subagents and [background sessions](<https://code.claude.com/docs/en/agent-view#how-file-edits-are-isolated>) once they are older than your [`cleanupPeriodDays`](<https://code.claude.com/docs/en/settings-reference#cleanupperioddays>) setting, following the [retention sweep rules](<https://code.claude.com/docs/en/claude-directory#cleaned-up-automatically>).

When you [background](<https://code.claude.com/docs/en/agent-view#send-the-session-to-the-background>) a `--worktree` session, its worktree becomes a background-session worktree that the sweep can remove. The sweep leaves a worktree in place in these cases:

* The worktree still holds work: changed or untracked files, or unpushed commits.
* A checked-out submodule in the worktree holds changed or untracked files, or Claude Code can't inspect the worktree's submodules. This check requires Claude Code v2.1.274 or later.
* One of the [four cases that also block worktree creation](<#git-lfs-content-is-missing-from-a-worktree-claude-code-created>) applies: Claude Code can't determine which filter drivers the repository config defines, or finds a setting there it can't switch off.
* The worktree belongs to a `--worktree` session you haven't backgrounded, whatever its age.
* You created the worktree yourself with `git worktree add`, even if you then ran a `--worktree <name>` session in it and backgrounded that session.

Claude Code writes a marker into the git metadata of every worktree it creates with git, and the sweep keeps any worktree without one, including a worktree a [`WorktreeCreate` hook](<#non-git-version-control>) created.

While an agent is running, Claude Code holds a `git worktree lock` on its worktree so that concurrent cleanup can't remove it, and releases the lock when the agent finishes. Claude Code holds the same lock on the worktree it created for a backgrounded session while the session runs, so the sweep leaves the worktree in place and `git worktree remove` refuses to remove it.

The sweep also releases a lock Claude Code set for a session whose process has exited, so a killed background session doesn't leave its worktree permanently locked. The sweep never releases a lock you set yourself with `git worktree lock`. Before v2.1.210, a lock left by a killed session stayed in place until you ran `git worktree unlock`.

To clean up a worktree that the sweep keeps, run `git worktree remove`, adding `--force` if the worktree has uncommitted changes or untracked files. If git refuses because the worktree is locked, run `git worktree unlock` on it first.

## Customize worktree creation

Claude Code's defaults for creating worktrees cover most sessions: it creates them under `.claude/worktrees/`, branches them from your repository's default branch, and checks out only tracked files. The options in this section change those defaults.

### Choose the base branch

New worktrees branch from the repository's default branch, so most sessions don't need this setting. Set `worktree.baseRef` in [settings](<https://code.claude.com/docs/en/settings-reference#worktree>) to branch from your current work instead. The setting accepts two values:

* `"fresh"` (default): branch from the repository's default branch on the remote, usually `main`, so the worktree starts from a clean tree matching the remote.
* `"head"`: branch from your current local `HEAD`, so the worktree carries your unpushed commits and feature-branch state. Use this when isolating subagents that need to operate on in-progress work. Inside a worktree, `"head"` resolves to that worktree's `HEAD`, not the main checkout's.

You can't set `worktree.baseRef` to a branch name. To start a worktree from a specific existing branch, [create it with git directly](<#manage-worktrees-manually>).

For a `"fresh"` base, Claude Code keeps `origin/HEAD` current: when the repository hasn't been fetched in the last 24 hours, it fetches the default branch, capped at five seconds, and uses the locally cached ref if the fetch fails. The fetch never waits for input in your terminal, so it also counts as failed when git or ssh would ask for a password, a key passphrase, or confirmation of a new SSH host. If no remote is configured, or `origin/HEAD` isn't cached locally and can't be fetched, the worktree falls back to your current local `HEAD`. Before v2.1.208, a fresh worktree used whatever `origin/HEAD` was already cached locally.

This example makes every new worktree branch from your current work:

```json theme={null}
{
  "worktree": {
    "baseRef": "head"
  }
}
```

### Branch from a pull request

To branch from a specific pull request or merge request, pass `--worktree` the number prefixed with `#`, a GitHub pull request URL, or a GitLab merge request URL such as `https://gitlab.com/group/repo/-/merge_requests/123`. Claude Code fetches that change's head commit from `origin` and creates the worktree at `.claude/worktrees/pr-<number>`. Quote the argument so your shell doesn't treat `#` as the start of a comment:

```bash theme={null}
claude --worktree "#1234"
```

Claude Code reads only the number from the URL. It always fetches from your repository's `origin` remote, and picks the fetch path by `origin`'s host:

* **github.com**: fetches `pull/<number>/head`
* **gitlab.com**: fetches `merge-requests/<number>/head`
* **GitHub Enterprise, self-managed GitLab, or any other host**: tries `pull/<number>/head` first, then `merge-requests/<number>/head`

This fetch never waits for input in your terminal. If git or ssh would ask for a password, a key passphrase, or confirmation of a new SSH host, the fetch fails instead and Claude Code exits with an `Error creating worktree: Failed to fetch PR/MR #<number>` message. A key that `ssh-agent` holds still works, so load your key there and run `git fetch` once by hand to record a new host before you start.

Before v2.1.233, Claude Code accepted only `#<number>` and GitHub-style pull request URLs for `--worktree`, and always fetched `pull/<number>/head`.

### Copy gitignored files into worktrees

A worktree is a fresh checkout, so untracked files like `.env` or `.env.local` from your main repository are not present. To copy them automatically when Claude creates a worktree, add a `.worktreeinclude` file to your project root.

The file uses `.gitignore` syntax. Only files that match a pattern and are also gitignored are copied, so tracked files are never duplicated.

If you write a pattern that starts with `**/` and the files you want are inside a directory that is gitignored as a whole, Claude Code copies them only when that directory itself matches the pattern, or when the first name after the `**/` is one of the names in the directory's path. For example, if you write `**/.claude/skills/*.md`, that first name is `.claude`, so Claude Code copies the matching files out of an ignored `.claude/` directory. To copy files out of an ignored directory that a `**/` pattern doesn't reach, name the directory in the pattern instead: write `vendor/**/config.json` rather than `**/config.json`. Before v2.1.239, Claude Code copied files out of a wholly ignored directory for a `**/` pattern only when the directory itself matched the pattern.

This `.worktreeinclude` copies two env files and a secrets config into each new worktree:

```text .worktreeinclude theme={null}
.env
.env.local
config/secrets.json
```

This applies to every worktree Claude Code creates with git: `--worktree` worktrees, [subagent worktrees](<#isolate-subagents-with-worktrees>), and parallel sessions in the [desktop app](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>). With a [`WorktreeCreate` hook](<#non-git-version-control>), copy the files inside the hook script.

### Reuse a worktree name

Passing `--worktree` a name whose directory already exists opens that existing worktree instead of creating a new one.

With the default `"fresh"` [base](<#choose-the-base-branch>), a reopened worktree resets to the repository's default branch instead of continuing at its old tip when all of the following hold:

* It has no uncommitted changes or untracked files.
* It is still on the branch Claude Code created for it.
* It has no commits of its own, or its pull request or merge request was merged and its remote branch deleted.

Claude Code detects the merged case from git state alone: the remote branch the worktree pushed to no longer exists, and every commit in the worktree is already on the default branch.

In every other case, Claude Code reopens the worktree at its old tip:

* The worktree fails any of the conditions.
* Claude Code can't verify the worktree's state.
* `worktree.baseRef` is `"head"`.
* The name is a pull request or merge request reference.

Before v2.1.208, when you reused a name, Claude Code always reopened the old worktree at its old tip.

### Replace worktree creation with a hook

Configure a [`WorktreeCreate` hook](<https://code.claude.com/docs/en/hooks#worktreecreate>) to replace the default `git worktree` logic entirely, including placing worktrees somewhere other than `.claude/worktrees/`. For a complete example, see [Non-git version control](<#non-git-version-control>).

## What worktrees share with the main checkout

A worktree gets its own files and branch, but it shares the following with the main checkout:

* **The repository's `.git` directory**: git commands in a worktree write to the main repository's shared `.git` directory, and [sandboxing](<https://code.claude.com/docs/en/sandboxing#filesystem-isolation>) allows those writes, so commands such as `git commit` work from inside a worktree with the sandbox enabled.
* **Plugins**: plugins installed at [project scope](<https://code.claude.com/docs/en/plugins/loading#find-where-a-plugin-is-enabled>) from the main checkout also load in worktrees of the same repository, so you don't need to reinstall them per worktree. Requires Claude Code v2.1.200 or later.
* **Permission approvals**: choosing "Yes, and don't ask again" for a Bash command in a worktree session saves the rule to the main checkout's `.claude/settings.local.json`, so it applies in the main checkout and in every other worktree of the repository, and it survives the worktree's removal. On Windows and in the other cases where Claude Code [doesn't use the repository root](<https://code.claude.com/docs/en/settings#where-claude-code-looks-for-each-file>), the rule stays with that worktree. Before v2.1.211, an approval granted in a worktree was saved inside that worktree, didn't apply elsewhere, and was lost when the worktree was removed. See [where approvals are saved](<https://code.claude.com/docs/en/permissions#permission-system>).
* **Untracked skills, agents, and commands**: when the worktree checkout has no `.claude/skills` directory at its root, for example because your `.claude/skills` is gitignored, Claude Code loads the main checkout's [project skills](<https://code.claude.com/docs/en/skills#where-skills-live>) in the worktree session. In a worktree with its own `.claude/skills` directory, only that copy loads.

  The same read-through covers `.claude/agents` and `.claude/commands`. For skills, the read-through requires Claude Code v2.1.277 or later.

All of these apply whether you create the worktree with `--worktree` or with `git worktree add`.

In a worktree session that you start from the [desktop app](<https://code.claude.com/docs/en/desktop#work-in-parallel-with-sessions>), Claude Code reads project configuration such as settings, hooks, skills, agents, commands, and [`.mcp.json`](<https://code.claude.com/docs/en/mcp#project-scope>) servers from the main checkout's root rather than from the worktree. Hook commands run in that root, and `${CLAUDE_PROJECT_DIR}` points at it. To reach the files Claude is working on, read the worktree's path from the hook's [`cwd` input field](<https://code.claude.com/docs/en/hooks#common-input-fields>). `CLAUDE.md` files and `.claude/rules/` still load from the worktree.

## Manage worktrees manually

Create worktrees with Git directly when you need to check out a specific existing branch or place the worktree outside the repository.

Create a worktree on a new branch:

```bash theme={null}
git worktree add ../project-feature-a -b feature-a
```

Create a worktree from an existing branch, replacing `fix-issue-456` with a branch that already exists in your repository:

```bash theme={null}
git worktree add ../project-bugfix fix-issue-456
```

Start Claude in the worktree:

```bash theme={null}
cd ../project-feature-a
claude
```

List your worktrees:

```bash theme={null}
git worktree list
```

Remove one when you're done with it:

```bash theme={null}
git worktree remove ../project-feature-a
```

See the [Git worktree documentation](<https://git-scm.com/docs/git-worktree>) for the full command reference.

## Non-git version control

Worktree isolation uses git by default. For SVN, Perforce, Mercurial, or other systems, configure [`WorktreeCreate` and `WorktreeRemove` hooks](<https://code.claude.com/docs/en/hooks#worktreecreate>) to provide custom creation and cleanup logic. Because the hook replaces the default git behavior, [`.worktreeinclude`](<#copy-gitignored-files-into-worktrees>) is not processed when you use `--worktree`. Copy any local configuration files inside your hook script instead.

This `WorktreeCreate` hook reads the worktree name from the JSON on stdin with `jq`, checks out a fresh SVN working copy, and prints the directory path so Claude Code can use it as the session's working directory. Add the configuration to your [`settings.json`](<https://code.claude.com/docs/en/settings#where-settings-live>):

```json theme={null}
{
  "hooks": {
    "WorktreeCreate": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "bash -c 'NAME=$(jq -r .name); DIR=\"$HOME/.claude/worktrees/$NAME\"; svn checkout https://svn.example.com/repo/trunk \"$DIR\" >&2 && echo \"$DIR\"'"
          }
        ]
      }
    ]
  }
}
```

Pair it with a `WorktreeRemove` hook to clean up when the session ends. See the [hooks reference](<https://code.claude.com/docs/en/hooks#worktreecreate>) for the input schema and a removal example.

A `WorktreeCreate` hook also lets you run [`/batch`](<https://code.claude.com/docs/en/commands#all-commands>) outside a git repository. Each `/batch` subagent then publishes its change with your project's version-control commands and, when it can't open a pull request, reports what it published instead. Running `/batch` outside a git repository requires Claude Code v2.1.281 or later.

## Troubleshooting

Claude Code reports the errors below when it creates a worktree, enters one at startup, or returns a resumed session to one.

### Claude Code can't enter the worktree at startup

When Claude Code can't enter the worktree directory at startup, it prints an error naming the path and exits with code 1. This can happen when a [`WorktreeCreate` hook](<https://code.claude.com/docs/en/hooks#worktreecreate>) prints something other than the directory it created, or when the directory was deleted after it was set up.

### Worktree creation fails on a symlinked path

Claude Code refuses to create a worktree when `.claude`, `.claude/worktrees`, or the worktree directory itself is a symlink, and the error names the symlinked path. Remove the symlink and retry. Before v2.1.212, if the repository already contained a committed symlink at one of those paths, worktree creation followed it and could create files outside the repository.

<h3 id="git-lfs-content-is-missing-from-a-worktree-claude-code-created">
  Git LFS files are pointer files in a worktree Claude Code created
</h3>

If you set up [Git LFS](<https://git-lfs.com>) with `git lfs install --local`, a worktree that Claude Code creates contains LFS pointer files instead of the real files. The `--local` flag writes the LFS filter into the repository's own `.git/config` rather than your global git config. A plain `git lfs install` writes to your global config and isn't affected. The same applies to any other [filter driver](<https://git-scm.com/docs/gitattributes>) defined in the repository's own config.

Claude Code skips the repository's own filter drivers when it creates a worktree because a filter driver is a shell command, and anything that can write to the repository, including Claude, could have put one there. Before v2.1.247, Claude Code ran those drivers during worktree creation.

To get the real files, run `git lfs pull` inside the worktree.

In four rare cases, Claude Code creates no worktree at all: it can't tell which filter drivers the repository's config defines, or it finds a setting there it can't switch off. Match the error to its fix:

* **`Could not read the repository git config to neutralize filter drivers`**: Claude Code couldn't read the repository's `.git/config`, for example because of its permissions. Fix that and retry.
* **`The repository git config defines a filter driver whose name cannot be neutralized (contains "=" or a newline)`**: rename or remove that filter driver in `.git/config` and retry.
* **`The repository git config has a conditional include (includeIf)`**: move the settings the `includeIf` in `.git/config` pulls in directly into that file, remove the `includeIf`, and retry. An `includeIf` in your global git config doesn't trigger this.
* **`Git was not run: the repository's own git config sets <key>`**: the message names a key that points Git LFS at a program to run, such as `lfs.customtransfer.<name>.path` or `lfs.standalonetransferagent`. If that setting is yours, move it to your global git config. If you don't recognize it, remove it from the repository's git config, since a tool or checkout you don't trust may have written it. Retry once the key is gone from the repository's config.

### Claude Code refuses to use a worktree

An error starting `Refusing to use <path> as an isolation worktree` means Claude Code checked the directory's git identity before adopting it as a session's or subagent's isolated checkout, and declined it. The check runs whether Claude Code is creating the worktree, entering an existing one, or reusing one from an earlier run.

In most cases the rest of the message says the directory's git metadata resolves into the main checkout: for example, its `.git` file points at the main repository's own `.git` directory, or git resolves its working tree to the main checkout through a `core.worktree` redirect. From such a directory, an ordinary git command such as `git reset --hard` would act on the main checkout instead of the worktree. Claude Code also refuses when the directory has a `.git` entry it can't read, rather than assuming the worktree is safe.

A directory with no git metadata at all, such as one your [`WorktreeCreate` hook](<#non-git-version-control>) creates, passes the check only when no git repository contains it. If the hook creates the directory inside a repository, git resolves it to that repository's checkout and Claude Code refuses it with the `git resolves its working tree to` message, so have the hook create its directories outside any repository.

Claude Code leaves the refused directory in place, since it may hold work. Match the message to its recovery, whether it follows `Refusing to use <path>` or appears in a [resume message](<#the-session-resumes-outside-its-worktree>); some endings occur only in resume messages:

* **Says `launch from the parent checkout` or `Run the resume from the project checkout`**: you launched Claude Code from inside the worktree. Launch from the main checkout instead; the worktree needs no recreation.
* **Says `it cannot be resumed or re-entered`**: nothing in this session vouches for the worktree from where you launched. Recreate it; the directory and its work remain on disk for manual recovery, and when the worktree has a parent checkout, resuming from there also works.
* **Says `it contains the protected checkout`**: the refused directory is a parent of your main checkout, such as your home directory. Don't delete it. Change the worktree path, such as the path your `WorktreeCreate` hook returns or the `EnterWorktree` target, so the worktree doesn't contain the checkout.
* **Says `the protected checkout <path> has a .git entry that could not be examined` or `has git metadata that could not be resolved`**: the problem is the main checkout's git metadata, not the worktree's. Don't delete the worktree, and ignore the message's trailing advice to recreate it, which doesn't apply to these two endings. Repair the main checkout, for example a permissions problem or a git `dubious ownership` refusal on its `.git`, and retry.
* **Says `its recorded path has a network spelling`**: Claude Code never resumes into a worktree at a network path. Recreate the worktree at a local path.
* **Any other ending**: the message names the problem and its fix, such as removing a `core.worktree` redirect or recreating the worktree; follow it. Before deleting a directory whose message says its git identity could not be verified, address the named cause first, for example a symbolic link in the worktree's path or git itself failing to run, since the directory may be healthy. When you do recreate, salvage any changes you need from the old directory first; it stays on disk.

### The session resumes outside its worktree

When you resume a session interactively and Claude Code can't return it to its worktree, Claude Code says so with one of the messages below. When Claude Code clears the worktree binding, it records the clear in the session transcript. If you [suppress transcript writes](<https://code.claude.com/docs/en/sessions#where-transcripts-are-stored>), the message says instead that the binding could not be cleared and that Claude Code will re-check the worktree on a later resume.

| Message starts with | What happened and what to do |
| :- | :- |
| `Your worktree <path> no longer exists` | The worktree directory was removed. The session continues in the current directory without isolation, and Claude Code clears the worktree binding. No action needed. |
| `Could not verify your worktree <path> this time` | Claude Code couldn't verify the worktree, usually for a transient reason; the binding is kept, and the session continues in the current directory without isolation. Resume again to retry; if it keeps happening, enter the worktree in a new session and match the refusal message under [Claude Code refuses to use a worktree](<#claude-code-refuses-to-use-a-worktree>), which can name the main checkout's metadata rather than the worktree's. |
| `Did not re-enter your worktree <path>` | Claude Code refused the worktree binding as unsafe; it clears the binding and the session continues without isolation. The message includes the specific refusal: match it under [Claude Code refuses to use a worktree](<#claude-code-refuses-to-use-a-worktree>), since the fix is recreation for some refusals and a path change for others. |
| `Could not re-enter your worktree <path>` | Claude Code couldn't vouch for the worktree from where you launched, most commonly because you launched from inside it; the binding is kept. The rest of the message names the fix; match it under [Claude Code refuses to use a worktree](<#claude-code-refuses-to-use-a-worktree>). |

In [non-interactive mode](<https://code.claude.com/docs/en/headless>) with `-p`, and on resumes that the [Agent SDK](<https://code.claude.com/docs/en/agent-sdk/sessions>) runs, Claude Code stops the resume with a stderr error for every refusal except a gone worktree, instead of continuing without isolation.

With `--output-format stream-json`, the refusal also arrives on stdout as a `result` message with subtype `error_during_execution` whose `errors` array carries the same text, so an Agent SDK application receives the reason rather than only a non-zero exit. Before v2.1.260, a worktree-resume refusal produced no `result` message.

The messages take different shapes from the interactive messages in the table:

* `Error: cannot resume into worktree <path>: ...This session was not started.` for a refusal the table shows as `Did not re-enter`. Claude Code clears the worktree binding before exiting, and the error says so; the next time you resume the conversation, the session continues in the current directory without worktree isolation. Before v2.1.260, Claude Code didn't write the cleared binding, so every retry of the same resume failed with the same error.

  If you [suppress transcript writes](<https://code.claude.com/docs/en/sessions#where-transcripts-are-stored>), the clear can't be saved. The error then says the same command will be refused again, and names `--fork-session` and starting a new conversation as ways to continue without the worktree.
* `Error: could not verify worktree <path> for this resume, so the resume was aborted...` for `Could not verify`
* `Error: ...The worktree binding is kept.` for `Could not re-enter`
* `Notice: the worktree <path> for this session no longer exists...` for a gone worktree; Claude Code prints it and continues the session, as an interactive resume does

The refusal ending embedded in each error is shared with the interactive notices, so it still matches its entry under [Claude Code refuses to use a worktree](<#claude-code-refuses-to-use-a-worktree>).

In the stream-json result, [`startup_failure_reason`](<https://code.claude.com/docs/en/agent-sdk/typescript#startup_failure_reason>) is `worktree_unverified` for the `could not verify worktree` error and `worktree_resume_refused` for the `cannot resume into worktree` and `The worktree binding is kept` errors. An application can branch on it instead of matching the error text. Before v2.1.274, the result carried no `startup_failure_reason` field.
