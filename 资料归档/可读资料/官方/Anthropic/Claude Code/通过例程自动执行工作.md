# 通过例程实现工作自动化

> 将Claude Code置于自动驾驶仪上。定义按计划运行、触发 API 调用或对来自云基础设施的 GitHub 事件做出反应的例程。



**注释：**

例程处于研究预览阶段。行为、限制和 API 表面可能会发生变化。


例程是保存的 Claude Code 配置：一个提示、一个或多个存储库和一组 [ 连接器 ](<https://code.claude.com/docs/en/mcp>)，打包一次并自动运行。例程在 Anthropic 管理的云基础设施上执行，或者在您组织的 [ 自托管环境 ](<https://code.claude.com/docs/en/self-hosted-environments>) 上路由时执行，因此当您的笔记本电脑关闭时，它们仍然可以继续工作。

每个例程可以附加一个或多个触发器：

* **计划**：以每小时、每晚或每周等重复节奏运行，或在未来的特定时间运行一次
* **API**：通过使用不记名令牌将 HTTP POST 发送到每个例程端点来按需触发
* **GitHub**：自动运行以响应存储库事件，例如拉取请求或发布

单个例程可以组合触发器。例如，PR 审核例程可以每晚运行，从部署脚本触发，并对每个新的 PR 做出反应。

Pro、Max、Team 和 Enterprise 计划提供例程。在 [claude.ai/code/routines](<https://claude.ai/code/routines>) 或从 CLI 使用 `/schedule` 创建和管理它们。

团队和企业所有者可以通过 [claude.ai/admin-settings/claude-code](<https://claude.ai/admin-settings/claude-code>) 处的例程切换来禁用所有成员的例程。禁用后，现有例程将停止运行，并且成员无法创建新例程。

本页介绍了创建例程、配置每个触发器类型、管理运行以及如何应用使用限制。

## 示例用例

每个示例都将触发类型与适合的工作例程类型配对：无人值守、可重复且与明确的结果相关。

**待办事项维护。**计划触发器每周都会通过连接器针对您的问题跟踪器运行。该例程读取自上次运行以来打开的问题，应用标签，根据引用的代码区域分配所有者，并将摘要发布到 Slack，以便团队以整理好的队列开始新的一天。

**警报分类。** 当超过错误阈值时，您的监视工具将调用例程的 API 端点，并将警报正文作为 `text` 传递。该例程的提示告诉Claude调查火灾有效负载中的警报，因此它会拉出堆栈跟踪，将其与存储库中最近的提交相关联，并打开一个草稿拉取请求，其中包含建议的修复和返回警报的链接。随时查看 PR，而不是从空白终端开始。

**定制代码审查。** GitHub 触发器在 `pull_request.opened` 上运行。该例程应用您团队自己的审核清单，为安全性、性能和风格问题留下内联注释，并添加摘要注释，以便人工审核员可以专注于设计而不是机械检查。

**部署验证。** 您的 CD 管道在每次生产部署后调用例程的 API 端点。该例程对新构建运行烟雾检查，扫描错误日志以查找回归情况，并在部署窗口关闭之前向发布通道发布是否继续的信息。

**文档漂移。** 计划触发器每周运行一次。该例程会扫描自上次运行以来合并的 PR，标记引用已更改 API 的文档，并根据文档存储库打开更新 PR 供编辑者查看。

**库端口。** GitHub 触发器在 `pull_request.closed` 上运行，过滤到一个 SDK 存储库中的合并 PR。该例程将更改移植到另一种语言的并行 SDK 并打开匹配的 PR，使两个库保持同步，而无需人工重新实现每个更改。

## 创建例程

从网络 [claude.ai/code/routines](<https://claude.ai/code/routines>)、桌面应用程序或 CLI 创建例程。所有三个表面都写入同一个云帐户，因此您在一个表面中创建的例程会立即显示在其他表面中。在桌面应用程序的 **代码 ** 选项卡中，单击边栏中的 **例程 ** 或边栏的 **更多 ** 菜单，然后单击 **新建例程**，选择**云**；选择 **Local** 会创建一个 [桌面计划任务 ](<https://code.claude.com/docs/en/desktop-scheduled-tasks>)，该任务在您的计算机上而不是在云中运行。

创建表单设置例程的提示、存储库、环境、连接器和触发器。

例程作为完整的 Claude Code 云会话自主运行：没有权限模式选择器，会话运行 shell 命令，使用提交到克隆存储库的 [ 技能 ](<https://code.claude.com/docs/en/skills>)，并调用您包含的任何连接器，除了某些 [ 工件 ](<https://code.claude.com/docs/en/artifacts>) 之外，所有这些都无需停止审批行动。

例程可以访问的内容取决于您选择的存储库、[环境的](<https://code.claude.com/docs/en/cloud-environments>)网络访问和变量以及您包含的连接器。将其中每一个的范围确定为例程实际需要的范围。

当例程的计划或 **立即运行 ** 开始运行时，Claude 仅当所有这些都成立时才重新发布现有工件而不询问：

* 您可以编辑工件，它属于您自己的组织
* 该工件未公开共享
* 如果工件与特定人员或您的组织共享，则其查看者不会自动看到每个新版本
* 发布仅包含页面，没有添加支持文件或任何其他内容，并且不会强制更新版本
* 该页面不持有超出该页面的授权，例如[连接器调用](<https://code.claude.com/docs/en/artifacts#pull-live-data-with-mcp-connectors>)

在所有其他情况下，包括发布新工件，Claude都会首先询问。当例程的工作是保持页面最新时，请为其提供您已经发布的工件。

例程属于您的个人 claude.ai 帐户。它们不会与队友共享，并且它们的运行次数会计入您帐户的 [ 使用量和限制 ](<#用途和限制>)。例程通过您连接的 GitHub 身份或连接器执行的任何操作都会显示为：提交和拉取请求携带您的 GitHub 用户，并且 Slack 消息、线性票证或其他连接器操作使用您的链接帐户来提供这些服务。

### 从网络创建



  

#### 打开创建表单

访问[claude.ai/code/routines](<https://claude.ai/code/routines>)并点击**新建例程**。
  


  

#### 命名例程并编写提示

为例程指定一个描述性名称，并编写每次运行的提示符 Claude。提示是最重要的部分：例程自主运行，因此提示必须是独立的，并且明确说明要做什么以及成功是什么样子。

当触发器触发时，会话会接收例程保存的提示作为其分配的任务并执行它，而不是将其视为在对话中到达的不受信任的内容。触发器仅证明提示是由您帐户上的授权会话提前存储的，因此触发的提示不是实时用户输入，并且不能充当运行期间对操作的批准或同意。会话在运行期间获取的内容保持其正常处理。在 v2.1.213 之前，会话收到与不受信任的后台通知相同的提示，并且可以拒绝对其采取操作。

提示输入包括模型选择器。 Claude 在每次运行时都使用选定的模型。
  


  

#### 选择存储库

添加一个或多个 GitHub 存储库以供 Claude 使用。每个存储库都会在运行开始时从默认分支开始克隆。 Claude 为其更改创建以 `claude/` 为前缀的分支。
  


  

#### 选择环境

选择 [ 云环境 ](<https://code.claude.com/docs/en/cloud-environments>) 作为例程。环境控制云会话可以访问的内容：

    * **网络访问**：设置每次运行期间可用的互联网访问级别
    * **环境变量**：提供价值 Claude 可以在每次运行期间使用。他们是 [使用该环境的任何人都可以看到](<https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup>)，因此在 Pro 和 Max 计划中，存储 API 的密钥 Claude 运行期间调用 [网络秘密](<https://code.claude.com/docs/en/cloud-environments#add-network-secrets>) 相反。该部分还列出了永远不会获得秘密的请求
    * **安装脚本**：安装例程所需的依赖项和工具。结果是 [ 缓存 ](<https://code.claude.com/docs/en/cloud-environments#environment-caching>)，因此脚本不会在每个会话上重新运行

**默认**环境提供**可信**网络访问，仅允许包注册表、云提供商API、容器注册表和通用开发域的[默认白名单](<https://code.claude.com/docs/en/cloud-environments#default-allowed-domains>)会话的网络。您添加到例程的连接器通过 Anthropic 的服务器访问其服务，因此它们不需要更改白名单。如果您的例程需要直接访问您自己的服务或该列表之外的域，请在运行之前编辑环境的 [ 网络访问 ](<https://code.claude.com/docs/en/cloud-environments#network-access>)。要使用单独的环境，请先[创建一个](<https://code.claude.com/docs/en/cloud-environments#configure-your-environment>)。
  


  

#### 选择触发器

在 ** 选择触发器 ** 下，选择例程的启动方式。您可以选择一种触发器类型或组合多种触发器类型。

    

      

#### 时间表

选择重复运行的预设频率，或安排在特定时间戳进行一次一次性运行。请参阅 [添加计划触发器 ](<#添加计划触发器>) 以进行时区处理、延迟启动、自定义 cron 间隔和一次性运行。
      


      

#### GitHub 活动

选择存储库、要响应的事件以及可选的过滤器。请参阅 [添加 GitHub 触发器 ](<#添加-github-触发器>) 以获取支持的事件和筛选字段的完整列表。
      


      

#### API

此处选择**API**，然后保存例程。 URL 和令牌是在保存例程后生成的，因为它们依赖于例程 ID。请参阅[添加API触发器](<#添加-api-触发器>)来复制URL并生成令牌。
      

    

  


  

#### 检查连接器

默认情况下，在表单底部的 ** 连接器 ** 下，包含所有已连接的 [MCP 连接器 ](<https://code.claude.com/docs/en/mcp>)。删除任何例程不需要的内容：Claude 可以使用包含的连接器中的每个工具，包括写入，而无需在运行期间请求许可。
  


  

#### 创建例程

单击**创建**。该例程出现在列表中，并在下次其触发器之一匹配时运行。要立即开始运行，请单击例程详细信息页面上的**立即运行**。

每次运行都会与其他会话一起创建一个新会话，您可以在其中查看 Claude 执行的操作、查看更改并创建拉取请求。
  


### 从 CLI 创建

在任何会话中运行 `/schedule` 以对话方式创建预定例程。您还可以直接传递描述，用于重复例程（如 `/schedule daily PR review at 9am`）或一次性例程（如 `/schedule clean up feature flag in one week`）。 Claude 遍历网络表单收集的相同信息，然后将例程保存到您的帐户。该命令也可在别名 `/routines` 下使用。

成功的开始看起来就像一场对话：Claude 在保存之前询问有关时间表、存储库和提示的后续问题。如果 Claude 回复您需要进行身份验证或无法连接到您的远程 claude.ai 帐户，则不会创建例程；请参阅[故障排除](<#故障排除>)。

CLI 中的 `/schedule` 创建预定例程。要添加 API 触发器，请在网络上编辑 [claude.ai/code/routines](<https://claude.ai/code/routines>) 上的例程。您可以从网络或 CLI 添加 [GitHub 触发器 ](<#添加-github-触发器>)。 CLI 路径需要 Claude Code v2.1.225 或更高版本。

没有计划触发器的例程（例如仅由 API 调用或 GitHub 事件启动的例程）没有下一次运行时间，并且当 Claude 保存或更新它时，CLI 不显示任何时间。在 v2.1.211 之前，CLI 报告了这些例程在一年 1 中的下一次运行时间。

## 配置触发器

当其中一个触发器匹配时，例程就会启动。您可以将计划、API 和 GitHub 触发器的任意组合附加到同一例程，并随时从例程编辑表单的 ** 选择触发器 ** 部分添加或删除它们。

### 添加计划触发器

计划触发器以重复的节奏运行例程，或者在未来的特定时间运行一次。在**选择触发器**部分中选择预设频率：每小时、每天、工作日或每周。时间会在您的本地区域中输入并自动转换，因此无论云基础设施位于何处，例程都会按照挂钟时间运行。

如果您准确地安排跑步，例如 9:00，它可能会延迟几分钟开始。要在接近预定时间开始，请选择整点过后的几分钟，例如 9:07。

对于自定义间隔（例如每两个小时或每个月的第一天），请在表单中选择最接近的预设，然后运行 CLI 中的 `/schedule update` 以设置特定的 cron 表达式。最短间隔为一小时；运行更频繁的表达式将被拒绝。

#### 安排一次性运行

一次性计划在特定时间戳触发例程一次。使用它在本周晚些时候提醒自己，在部署完成后进行清理 PR，或者在上游变更发布后开始后续任务。例程触发后，它会自动禁用，并且网络 UI 将其标记为 **Ran**。要再次运行它，请编辑例程并设置新的一次性时间。

通过用自然语言描述时间，从 CLI 创建一次性运行。 Claude 根据当前时间解析短语并在保存之前确认绝对时间戳。

```text theme={null}
/schedule tomorrow at 9am, summarize yesterday's merged PRs
```

```text theme={null}
/schedule in 2 weeks, open a cleanup PR that removes the feature flag
```

与循环计划相同的本地到 UTC 转换适用于一次性时间戳。

一次性运行与其他计划运行一样计入相同的小时限制。有关详细信息，请参阅[使用和限制](<#用途和限制>)。

### 添加 API 触发器

API 触发器为例程提供了专用的 HTTP 端点。使用例程的不记名令牌向端点进行 POST 会启动一个新会话并返回一个会话 URL。使用它将 Claude Code 连接到警报系统、部署管道、内部工具或任何可以发出经过身份验证的 HTTP 请求的地方。

API 触发器已从网络添加到现有例程中。 CLI 目前无法创建或撤销令牌。



  

#### 打开例程进行编辑

Go到[claude.ai/code/routines](<https://claude.ai/code/routines>)，通过API单击要触发的例程，然后打开例程名称旁边的菜单并选择**编辑**。
  


  

#### 添加 API 触发器

滚动到 ** 指令 ** 框下方的 ** 选择触发器 ** 部分，单击 ** 添加另一个触发器 **，然后选择 **API**。
  


  

#### 复制【URL】并生成token

该模式显示此例程的 URL 以及示例curl 命令。复制URL，然后点击**生成令牌**并立即复制令牌。该令牌仅显示一次，以后无法检索，因此请将其存储在安全的地方，例如警报工具的秘密存储区。
  


  

#### 调用端点

当您将 POST 发送到 URL 时，发送 `Authorization: Bearer` 标头中的令牌。下面的[触发例程](<#触发例程>)部分显示了一个完整的示例。
  


每个例程都有自己的令牌，其范围仅限于触发该例程。要旋转或撤销它，请返回到相同模式并单击 **重新生成** 或 **撤销**。

#### 触发例程

将 POST 请求发送到 `/fire` 端点，并在 `Authorization` 标头中包含承载令牌。请求正文接受一个可选的 `text` 字段，用于特定于运行的上下文，例如警报正文或失败日志，与保存的提示一起传递到例程。该值是自由格式文本，不会被解析：如果您发送 JSON 或其他结构化负载，例程会将其作为文字字符串接收。

`text` 值不会作为裸消息到达例程。它到达时包裹在一个 `<routine-fire-payload>` 块中，该块将其标记为不受信任的数据，并告诉 Claude 不要遵循其中的指令，除非例程自己的提示要求这样做。同样的换行适用于网络 UI 中的 **立即运行 ** 提供的文本。

这意味着例程的保存提示必须选择对火灾文本进行操作：编写提示以显式引用有效负载，例如“调查例程火灾有效负载块中描述的警报”，或者例程将文本视为惰性上下文。持有不记名令牌的任何人都可以发送 `text`，因此包装器会使来自泄漏令牌的火灾文本标记为不可信数据，而不是作为例程的直接指令。

下面的示例从 shell 触发例程。显示的例程 ID 和令牌是占位符：将它们替换为 [ 添加 API 触发器 ](<#添加-api-触发器>) 时复制的 URL 和令牌，或者请求失败并出现 `401` 身份验证错误：

```bash theme={null}
curl -X POST https://api.anthropic.com/v1/claude_code/routines/trig_01ABCDEFGHJKLMNOPQRSTUVW/fire \
  -H "Authorization: Bearer sk-ant-oat01-xxxxx" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Sentry alert SEN-4521 fired in prod. Stack trace attached."}'
```

成功的请求将返回一个 JSON 主体，其中包含新会话 ID 和 URL：

```json theme={null}
{
  "type": "routine_fire",
  "claude_code_session_id": "session_01HJKLMNOPQRSTUVWXYZ",
  "claude_code_session_url": "https://claude.ai/code/session_01HJKLMNOPQRSTUVWXYZ"
}
```

在浏览器中打开会话 URL 以实时观看运行、查看更改或手动继续对话。



**注意：**

`/fire` 端点在 `experimental-cc-routine-2026-04-01` beta 标头下发布。当该功能处于研究预览阶段时，请求和响应形状、速率限制和令牌语义可能会发生变化。重大更改在新的 Beta 标头版本后面发布，并且两个最新的先前标头版本继续工作，以便调用者有时间进行迁移。


#### API参考

有关完整的 API 参考，包括所有错误响应、验证规则和字段限制，请参阅 Claude 平台文档中的 [通过 API](<https://platform.claude.com/docs/en/api/claude-code/routines-fire>) 触发例程。

`/fire` 端点仅供 claude.ai 用户使用，不属于 Claude 平台 API 表面的一部分。

### 添加 GitHub 触发器

当连接的存储库上发生匹配事件时，GitHub 触发器会自动启动新会话。 Claude Code 不会跨事件重用会话，因此两次 PR 更新会产生两个独立的会话。



**注释：**

GitHub webhook 事件受每个例程和每个帐户的每小时上限的限制。超出限制的事件将被丢弃，直到窗口重置。


Claude GitHub 应用程序必须安装在您要订阅的存储库上，无论您从哪个表面配置触发器。

* 从网络 UI 配置 GitHub 触发器，这会在应用程序丢失时提示您安装该应用程序。请按照以下步骤在 Web 上进行配置。
* 在 CLI 中，首先从 [GitHub 应用程序页面 ](<https://github.com/apps/claude>) 安装应用程序，然后要求 Claude 将 GitHub 触发器附加到现有例程，例如 `/schedule add a GitHub trigger to my nightly review for pull requests opened in acme/webapp`。 CLI 路径需要 Claude Code v2.1.225 或更高版本。当 Claude 添加触发器时，它会回复触发器触发的例程的链接。



  

#### 打开例程进行编辑

Go 到 [claude.ai/code/routines](<https://claude.ai/code/routines>)，单击例程，然后打开例程名称旁边的菜单并选择 **编辑**。
  


  

#### 添加 GitHub 事件触发器

滚动到**选择一个触发器**部分，单击**添加另一个触发器**，然后选择**GitHub事件**。

    

**注释：**

在 CLI 中运行 `/web-setup` 授予用于克隆的存储库访问权限，但它不会安装 Claude GitHub 应用程序，也不会启用 Webhook 传递。
    

  


  

#### 配置触发器

选择存储库，从 [ 支持的事件 ](<#支持的活动>) 列表中选择一个事件，然后可以选择添加过滤器。保存触发器。
  


#### 支持的活动

GitHub 触发器可以订阅以下任一事件类别。在每个类别中，您可以选择特定操作，例如 `pull_request.opened`，或对该类别中的所有操作做出反应。

|活动|触发时间|
| :- | :- |
|拉取请求|PR 被打开、关闭、分配、标记、同步或以其他方式更新|
|发布|创建、发布、编辑或删除版本|

#### 过滤拉取请求

使用过滤器来缩小哪些拉取请求启动新会话的范围。所有过滤条件必须匹配才能触发例程。可用的过滤字段有：

|过滤器|火柴|
| :- | :- |
|作者|PR 作者的 GitHub 用户名|
|标题|PR 标题文本|
|身体|PR 描述文字|
|基地支部|分支 PR 目标|
|总行|PR 分支来自|
|标签|应用于 PR 的标签|
|是草稿|PR是否处于草稿状态|
|已合并|PR是否已合并|

每个过滤器将一个字段与一个运算符配对：等于、包含、开头为、是其中之一、不是其中之一或匹配正则表达式。

`matches regex` 运算符测试整个字段值，而不是其中的子字符串。要匹配任何包含 `hotfix` 的标题，请写入 `.*hotfix.*`。如果没有周围的 `.*`，过滤器将仅匹配完全是 `hotfix` 且前后没有任何内容的标题。对于没有正则表达式语法的字面子字符串匹配，请改用 `contains` 运算符。

一些过滤器组合示例：

* **Auth模块审查**：基础分支`main`，头分支包含`auth-provider`。将任何涉及身份验证的 PR 发送给重点审阅者。
* **仅供审核**：草稿是`false`。跳过草稿，因此例程仅在 PR 准备好供审核时运行。
* **标签门控反向移植**：标签包括`needs-backport`。仅当维护者标记 PR 时才触发端口到另一个分支例程。

## 管理日常事务

单击列表中的例程可打开其详细信息页面。详细信息页面显示例程的存储库、连接器、提示、计划、API 令牌、GitHub 触发器以及过去运行的列表。

### 查看运行并与之交互

单击任意运行即可将其作为完整会话打开。从那里您可以看到 Claude 做了什么、查看更改、创建拉取请求或继续对话。每个运行会话的工作方式与任何其他会话类似：使用会话标题旁边的下拉菜单对其进行重命名、存档或删除。



**注释：**

运行列表中的绿色状态表示会话启动和退出时没有出现基础结构错误。这并不意味着您提示中的任务成功。打开运行以读取转录本并确认 Claude 实际做了什么。被阻止的网络请求、丢失的连接器工具以及任务级故障都在此处显示，而不是在状态指示器中显示。


### 编辑和控制例程

从例程详细信息页面，您可以：

* 单击**立即运行**立即开始运行，无需等待下一个预定时间。您可以选择提供特定于运行的文本，该文本以与 API 触发器的 `text` 字段相同的方式到达例程。
* 使用页面顶部的 on/off 开关暂停或恢复计划。暂停的例程会保留其配置，但在您重新启用它们之前不会运行。
* 打开例程名称旁边的菜单，然后选择 **编辑** 以更改名称、提示、存储库、环境、连接器或任何例程的触发器。您可以在 ** 选择触发器 ** 部分添加或删除计划、API 令牌和 GitHub 事件触发器。
* 打开同一菜单并选择**删除**以删除例程。

### 从 CLI 管理例程

CLI支持管理现有例程。运行 `/schedule list` 查看所有例程，运行 `/schedule update` 更改例程，或运行 `/schedule run` 立即触发它。

您还可以询问例程的运行历史记录，例如 `/schedule why did my nightly review do nothing this morning?`。 Claude 列出了例程最近的运行及其状态以及指向 [ 在网络上打开每次运行 ](<#查看运行并与之交互>) 的链接，并读取运行日志以解释发生的情况，包括工具错误、权限拒绝和最终结果。需要 Claude Code v2.1.227 或更高版本。

### 存储库和分支权限

例程需要 GitHub 访问克隆存储库。当您使用 `/schedule` 从 CLI 创建例程时，Claude 会检查您的帐户是否具有对运行它的存储库的 GitHub 访问权限，如果没有，则会添加一个设置注释，命名如何授予它。请参阅 [GitHub 身份验证选项 ](<https://code.claude.com/docs/en/claude-code-on-the-web#github-authentication-options>) 了解授予访问权限的两种方法。

如果您的 GitHub 连接在运行到期时丢失或过期，则例程将跳过运行，直至您重新连接，最多持续 72 小时。在该窗口中重新连接 GitHub，例程将自行恢复。在没有连接的 72 小时后，例程将关闭，并在重新连接 GitHub 后将其重新打开。

您添加的每个存储库都会在每次运行时克隆。 Claude 从存储库的默认分支开始，除非您的提示另有指定。

Claude 会将其工作推送到前缀为 `claude/` 的分支，除非您的提示指示它推送到另一个分支。要控制运行可以推送到哪些分支，请使用 GitHub 上的分支保护规则或规则集。对于在 Anthropic 管理的基础设施上运行，以及通过 [Anthropic 的 git 代理 ](<https://code.claude.com/docs/en/self-hosted-environments-deploy#use-the-anthropic-git-proxy>) 推送的自托管运行，GitHub 将它们应用于您连接的 GitHub 访问，因此访问可以绕过的规则不会阻止运行的推送。相反，使用您的部署提供的 git 凭据进行推送的自托管运行会根据这些凭据进行检查。参见[配置git](<https://code.claude.com/docs/en/self-hosted-environments-deploy#configure-git>)。

### 连接器

例程可以使用连接的 MCP 连接器在每次运行期间读取和写入外部服务。例如，对支持请求进行分类的例程可能会从 Slack 通道读取数据并在 Linear 中产生问题。

连接器是您帐户上的 [claude.ai 集成 ](<https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claude-ai>)。您在 CLI 中使用 `claude mcp add` 本地添加的 MCP 服务器存储在您的计算机上，而不是您的 claude.ai 帐户上，因此它们不会出现在连接器列表中。要在例程中使用其中一台服务器，请将其添加为 [claude.ai/customize/connectors](<https://claude.ai/customize/connectors>) 处的连接器。对于具有一个存储库的例程，您可以在已提交的 [`.mcp.json`](<https://code.claude.com/docs/en/mcp#project-scope>) 中声明它，以便它成为克隆存储库的一部分。

创建例程时，默认情况下会包含所有当前连接的连接器。删除任何不需要限制 Claude 在运行期间可以访问的工具的内容。您还可以直接从例程表单添加连接器。

要在常规表单之外管理或添加连接器，请访问 [claude.ai/customize/connectors](<https://claude.ai/customize/connectors>) 或使用 CLI 中的 `/schedule update`。

### 环境和网络访问

每个例程都使用 [ 云环境 ](<https://code.claude.com/docs/en/cloud-environments>) 来控制网络访问、环境变量和设置脚本。该例程在每次运行时都会继承环境的网络策略。

## 用途和限制

例程会像交互式会话一样减少订阅使用量。在[claude.ai/settings/usage](<https://claude.ai/settings/usage>)查看您当前的消耗量。

与订阅使用分开，每种开始运行的方式都有每小时限制：

|行动|限制|计为|超过限制|
| :- | :- | :- | :- |
|预定运行，包括一次性运行|100 每小时|您的帐户|运行等待直到限制重置|
|**立即运行**，API 触发，并设置一次性例程以再次运行|30 每小时|每个例行程序，三个人共享一个计数|该操作将失败，直到限制重置|
|**立即运行**并设置一次性例程以再次运行|100 每小时|您的帐户|一样|
|API 火灾|100 每小时|您的帐户，与**立即运行**分开计算|一样|
|GitHub 事件|请参阅[添加GitHub触发器](<#添加-github-触发器>)| | |

这些每小时限制都没有超额。

当例程达到您的订阅使用限制时，打开使用积分的组织可以继续按计量超额运行例程。如果没有使用积分，额外的运行将被拒绝，直到您的使用窗口重置。在 [claude.ai/settings/usage](<https://claude.ai/settings/usage>) 打开使用积分。在团队和企业计划中，管理员通过 [claude.ai/admin-settings/usage](<https://claude.ai/admin-settings/usage>) 为组织打开它们。

当您的订阅暂停时，您的例程将被搁置并且不会运行。一旦您的订阅再次激活，请重新打开它们。

## 故障排除

<h3 id="schedule-returns-unknown-command">
 `/schedule` 返回“未知命令”
</h3>

当不满足其要求之一时，CLI 会隐藏 `/schedule`：在您键入时命令菜单显示 `No commands match "/schedule"`。提交它会返回 `Unknown command: /schedule`，但在下面的情况下会注明不同的答案。

原因通常是以下之一：

* 您通过控制台 API 密钥、[Anthropic 配置文件或联合凭证 ](<https://code.claude.com/docs/en/authentication#anthropic-profiles-and-federation-credentials>) 或云提供商（例如 Amazon Bedrock、Google 云的 Agent 平台或 Microsoft Foundry）进行身份验证。 `/schedule` 需要 claude.ai 订阅登录。使用控制台 API 密钥或配置文件，并启用功能标记提取，提交 `/schedule` 会显示 `/schedule is available with Claude for Enterprise — ask your admin about migrating from API-key access`。通过云提供商登录，您仍然会看到 `Unknown command: /schedule`。如果在 shell 中设置了 `ANTHROPIC_API_KEY` 或 `ANTHROPIC_AUTH_TOKEN`，或者在 `settings.json` 中设置了 `apiKeyHelper`，请先将其删除，因为它们优先于 claude.ai 登录。配置文件或联合凭据也优先，因此也将其关闭
* 您已完全注销，没有 API 密钥或其他凭据。启用功能标记提取后，提交 `/schedule` 显示 `/schedule requires a claude.ai subscription. Run /login to sign in with your claude.ai account.` 在 v2.1.268 之前，已注销的会话将企业消息显示为与控制台 API 密钥相同的 Claude
* 您处于云会话中，提交 `/schedule` 会回答该命令在该环境中不可用。从 [ 网络 UI](<https://claude.ai/code/routines>) 管理例程
* 您组织的策略禁用例程所需的 [ 云会话 ](<https://code.claude.com/docs/en/claude-code-on-the-web>)。在这种情况下，提交 `/schedule` 会回答 [`Cloud sessions are disabled by your organization's policy`](<https://code.claude.com/docs/en/errors#cloud-sessions-are-disabled-by-your-organizations-policy>)。在v2.1.268之前，返回了`Unknown command: /schedule`
* 所有者 [ 关闭了您的团队或企业组织的例程 ](<#routines-are-disabled-by-your-organizations-policy>)。在v2.1.227之前，该命令仍然出现在这种情况下，并且当Claude尝试创建或运行该例程时，claude.ai拒绝了该例程

除非您的组织的策略禁用例程或云会话，否则无论 CLI 如何配置，您都可以在 [claude.ai/code/routines](<https://claude.ai/code/routines>) 创建和管理例程。

<h3 id="routines-are-disabled-by-your-organizations-policy">
“您的组织的策略已禁用例程”
</h3>

您的团队或企业组织中的所有者可能已关闭 **例程** 切换于 [claude.ai/admin-settings/claude-code](<https://claude.ai/admin-settings/claude-code>)。开 Claude Code v2.1.227 或更高版本，相同的切换也会隐藏 `/schedule` 在 CLI。这是服务器端组织设置，因此无法从本地配置中覆盖它。请求所有者为您的组织启用例程。

# Automate work with routines

> Put Claude Code on autopilot. Define routines that run on a schedule, trigger on API calls, or react to GitHub events from cloud infrastructure.



**注释：**

  Routines are in research preview. Behavior, limits, and the API surface may change.


A routine is a saved Claude Code configuration: a prompt, one or more repositories, and a set of [connectors](<https://code.claude.com/docs/en/mcp>), packaged once and run automatically. Routines execute on Anthropic-managed cloud infrastructure, or on your organization's [self-hosted environment](<https://code.claude.com/docs/en/self-hosted-environments>) when routed there, so they keep working when your laptop is closed.

Each routine can have one or more triggers attached to it:

* **Scheduled**: run on a recurring cadence like hourly, nightly, or weekly, or once at a specific future time
* **API**: trigger on demand by sending an HTTP POST to a per-routine endpoint with a bearer token
* **GitHub**: run automatically in response to repository events such as pull requests or releases

A single routine can combine triggers. For example, a PR review routine can run nightly, trigger from a deploy script, and also react to every new PR.

Routines are available on Pro, Max, Team, and Enterprise plans. Create and manage them at [claude.ai/code/routines](<https://claude.ai/code/routines>), or from the CLI with `/schedule`.

Team and Enterprise Owners can disable routines for all members with the Routines toggle at [claude.ai/admin-settings/claude-code](<https://claude.ai/admin-settings/claude-code>). When disabled, existing routines stop running and members cannot create new ones.

This page covers creating a routine, configuring each trigger type, managing runs, and how usage limits apply.

## Example use cases

Each example pairs a trigger type with the kind of work routines are suited to: unattended, repeatable, and tied to a clear outcome.

**Backlog maintenance.** A schedule trigger runs every weeknight against your issue tracker via a connector. The routine reads issues opened since the last run, applies labels, assigns owners based on the area of code referenced, and posts a summary to Slack so the team starts the day with a groomed queue.

**Alert triage.** Your monitoring tool calls the routine's API endpoint when an error threshold is crossed, passing the alert body as `text`. The routine's prompt tells Claude to investigate the alert in the fire payload, so it pulls the stack trace, correlates it with recent commits in the repository, and opens a draft pull request with a proposed fix and a link back to the alert. On-call reviews the PR instead of starting from a blank terminal.

**Bespoke code review.** A GitHub trigger runs on `pull_request.opened`. The routine applies your team's own review checklist, leaves inline comments for security, performance, and style issues, and adds a summary comment so human reviewers can focus on design instead of mechanical checks.

**Deploy verification.** Your CD pipeline calls the routine's API endpoint after each production deploy. The routine runs smoke checks against the new build, scans error logs for regressions, and posts a go or no-go to the release channel before the deploy window closes.

**Docs drift.** A schedule trigger runs weekly. The routine scans merged PRs since the last run, flags documentation that references changed APIs, and opens update PRs against the docs repository for an editor to review.

**Library port.** A GitHub trigger runs on `pull_request.closed` filtered to merged PRs in one SDK repository. The routine ports the change to a parallel SDK in another language and opens a matching PR, keeping the two libraries in step without a human re-implementing each change.

## Create a routine

Create a routine from the web at [claude.ai/code/routines](<https://claude.ai/code/routines>), from the Desktop app, or from the CLI. All three surfaces write to the same cloud account, so a routine you create in one shows up in the others immediately. In the Desktop app's **Code** tab, click **Routines** in the sidebar or in the sidebar's **More** menu, then **New routine**, and choose **Cloud**; choosing **Local** instead creates a [Desktop scheduled task](<https://code.claude.com/docs/en/desktop-scheduled-tasks>), which runs on your machine rather than in the cloud.

The creation form sets up the routine's prompt, repositories, environment, connectors, and triggers.

Routines run autonomously as full Claude Code cloud sessions: there is no permission-mode picker, and the session runs shell commands, uses [skills](<https://code.claude.com/docs/en/skills>) committed to the cloned repository, and calls any connectors you include, all without stopping for approval apart from some [artifact](<https://code.claude.com/docs/en/artifacts>) actions.

What a routine can reach is determined by the repositories you select, the [environment's](<https://code.claude.com/docs/en/cloud-environments>) network access and variables, and the connectors you include. Scope each of those to what the routine actually needs.

When the routine's schedule or **Run now** starts a run, Claude republishes an existing artifact without asking only when all of these hold:

* You can edit the artifact and it belongs to your own organization
* The artifact isn't shared publicly
* If the artifact is shared with specific people or your organization, its viewers don't automatically see each new version
* The publish carries only the page, with no supporting files or anything else added, and doesn't force over a newer version
* The page holds no grant that reaches beyond the page, such as [connector calls](<https://code.claude.com/docs/en/artifacts#pull-live-data-with-mcp-connectors>)

In every other case, including publishing a new artifact, Claude asks first. When a routine's job is to keep a page current, give it an artifact you already published.

Routines belong to your individual claude.ai account. They are not shared with teammates, and their runs count against your account's [usage and limits](<#usage-and-limits>). Anything a routine does through your connected GitHub identity or connectors appears as you: commits and pull requests carry your GitHub user, and Slack messages, Linear tickets, or other connector actions use your linked accounts for those services.

### Create from the web



  

#### Open the creation form

    Visit [claude.ai/code/routines](<https://claude.ai/code/routines>) and click **New routine**.
  


  

#### Name the routine and write the prompt

    Give the routine a descriptive name and write the prompt Claude runs each time. The prompt is the most important part: the routine runs autonomously, so the prompt must be self-contained and explicit about what to do and what success looks like.

    When a trigger fires, the session receives the routine's saved prompt as its assigned task and carries it out, rather than treating it as untrusted content that arrived mid-conversation. The trigger attests only that the prompt was stored ahead of time by an authorized session on your account, so the fired prompt is not live user input and can't act as approval or consent for actions during the run. Content the session fetches during the run keeps its normal handling. Before v2.1.213, the session received the same prompt framed as an untrusted background notification and could refuse to act on it.

    The prompt input includes a model selector. Claude uses the selected model on every run.
  


  

#### Select repositories

    Add one or more GitHub repositories for Claude to work in. Each repository is cloned at the start of a run, starting from the default branch. Claude creates `claude/`-prefixed branches for its changes.
  


  

#### Select an environment

    Pick a [cloud environment](<https://code.claude.com/docs/en/cloud-environments>) for the routine. Environments control what the cloud session has access to:

    * **Network access**: set the level of internet access available during each run
    * **Environment variables**: provide values Claude can use during each run. They're [visible to anyone who uses the environment](<https://code.claude.com/docs/en/cloud-environments#what-carries-over-from-your-setup>), so on Pro and Max plans, store keys for the APIs Claude calls during a run as [network secrets](<https://code.claude.com/docs/en/cloud-environments#add-network-secrets>) instead. That section also lists the requests that never get a secret
    * **Setup script**: install dependencies and tools the routine needs. The result is [cached](<https://code.claude.com/docs/en/cloud-environments#environment-caching>), so the script doesn't re-run on every session

    A **Default** environment is provided with **Trusted** network access, which allows only the [default allowlist](<https://code.claude.com/docs/en/cloud-environments#default-allowed-domains>) of package registries, cloud provider APIs, container registries, and common development domains through the session's network. Connectors you add to the routine reach their services through Anthropic's servers, so they don't need allowlist changes. If your routine needs to reach your own services directly, or a domain outside that list, edit the environment's [network access](<https://code.claude.com/docs/en/cloud-environments#network-access>) before running. To use a separate environment, [create one](<https://code.claude.com/docs/en/cloud-environments#configure-your-environment>) first.
  


  

#### Select a trigger

    Under **Select a trigger**, choose how the routine starts. You can pick one trigger type or combine several.

    

      

#### Schedule

        Pick a preset frequency for a recurring run, or schedule a single one-off run at a specific timestamp. See [Add a schedule trigger](<#add-a-schedule-trigger>) for timezone handling, late starts, custom cron intervals, and one-off runs.
      


      

#### GitHub event

        Select the repository, the event to react to, and optional filters. See [Add a GitHub trigger](<#add-a-github-trigger>) for the full list of supported events and filter fields.
      


      

#### API

        Select **API** here, then save the routine. The URL and token are generated after the routine is saved, since they depend on the routine ID. See [Add an API trigger](<#add-an-api-trigger>) to copy the URL and generate a token.
      

    

  


  

#### Review connectors

    Under **Connectors** at the bottom of the form, all of your connected [MCP connectors](<https://code.claude.com/docs/en/mcp>) are included by default. Remove any the routine doesn't need: Claude can use every tool from an included connector, including writes, without asking for permission during a run.
  


  

#### Create the routine

    Click **Create**. The routine appears in the list and runs the next time one of its triggers matches. To start a run immediately, click **Run now** on the routine's detail page.

    Each run creates a new session alongside your other sessions, where you can see what Claude did, review changes, and create a pull request.
  


### Create from the CLI

Run `/schedule` in any session to create a scheduled routine conversationally. You can also pass a description directly, for a recurring routine like `/schedule daily PR review at 9am` or a one-off like `/schedule clean up feature flag in one week`. Claude walks through the same information the web form collects, then saves the routine to your account. The command is also available under the alias `/routines`.

A successful start looks like a conversation: Claude asks follow-up questions about the schedule, repositories, and prompt before saving. If Claude instead replies that you need to authenticate or that it can't connect to your remote claude.ai account, no routine was created; see [Troubleshooting](<#troubleshooting>).

`/schedule` in the CLI creates scheduled routines. To add an API trigger, edit the routine on the web at [claude.ai/code/routines](<https://claude.ai/code/routines>). You can add a [GitHub trigger](<#add-a-github-trigger>) from the web or from the CLI. The CLI path requires Claude Code v2.1.225 or later.

A routine with no schedule trigger, such as one started only by API calls or GitHub events, has no next run time, and the CLI shows none when Claude saves or updates it. Before v2.1.211, the CLI reported a next run time in the year 1 for these routines.

## Configure triggers

A routine starts when one of its triggers matches. You can attach any combination of schedule, API, and GitHub triggers to the same routine, and add or remove them at any time from the **Select a trigger** section of the routine's edit form.

### Add a schedule trigger

A schedule trigger runs the routine on a recurring cadence, or once at a specific future time. Pick a preset frequency in the **Select a trigger** section: hourly, daily, weekdays, or weekly. Times are entered in your local zone and converted automatically, so the routine runs at that wall-clock time regardless of where the cloud infrastructure is located.

If you schedule a run exactly on the hour, such as 9:00, it can start several minutes late. To start close to the scheduled time, pick a few minutes past the hour, for example 9:07.

For a custom interval such as every two hours or the first of each month, pick the closest preset in the form, then run `/schedule update` in the CLI to set a specific cron expression. The minimum interval is one hour; expressions that run more frequently are rejected.

#### Schedule a one-off run

A one-off schedule fires the routine a single time at a specific timestamp. Use it to remind yourself later in the week, to open a cleanup PR after a rollout finishes, or to start a follow-up task after an upstream change ships. After the routine fires, it auto-disables and the web UI marks it as **Ran**. To run it again, edit the routine and set a new one-off time.

Create a one-off run from the CLI by describing the time in natural language. Claude resolves the phrase against the current time and confirms the absolute timestamp before saving.

```text theme={null}
/schedule tomorrow at 9am, summarize yesterday's merged PRs
```

```text theme={null}
/schedule in 2 weeks, open a cleanup PR that removes the feature flag
```

The same local-to-UTC conversion as recurring schedules applies to one-off timestamps.

One-off runs count against the same hourly limit as other scheduled runs. See [Usage and limits](<#usage-and-limits>) for details.

### Add an API trigger

An API trigger gives a routine a dedicated HTTP endpoint. POSTing to the endpoint with the routine's bearer token starts a new session and returns a session URL. Use this to wire Claude Code into alerting systems, deploy pipelines, internal tools, or anywhere you can make an authenticated HTTP request.

API triggers are added to an existing routine from the web. The CLI cannot currently create or revoke tokens.



  

#### Open the routine for editing

    Go to [claude.ai/code/routines](<https://claude.ai/code/routines>), click the routine you want to trigger via API, then open the menu next to the routine's name and select **Edit**.
  


  

#### Add an API trigger

    Scroll to the **Select a trigger** section below the **Instructions** box, click **Add another trigger**, and choose **API**.
  


  

#### Copy the URL and generate a token

    The modal shows the URL for this routine along with a sample curl command. Copy the URL, then click **Generate token** and copy the token immediately. The token is shown once and cannot be retrieved later, so store it somewhere secure such as your alerting tool's secret store.
  


  

#### Call the endpoint

    Send the token in the `Authorization: Bearer` header when you POST to the URL. The [Trigger a routine](<#trigger-a-routine>) section below shows a complete example.
  


Each routine has its own token, scoped to triggering that routine only. To rotate or revoke it, return to the same modal and click **Regenerate** or **Revoke**.

#### Trigger a routine

Send a POST request to the `/fire` endpoint with the bearer token in the `Authorization` header. The request body accepts an optional `text` field for run-specific context such as an alert body or a failing log, passed to the routine alongside its saved prompt. The value is freeform text and is not parsed: if you send JSON or another structured payload, the routine receives it as a literal string.

The `text` value doesn't reach the routine as a bare message. It arrives wrapped in a `<routine-fire-payload>` block that labels it as untrusted data and tells Claude not to follow instructions inside it unless the routine's own prompt says to. The same wrapping applies to text supplied with **Run now** in the web UI.

This means a routine's saved prompt must opt in to acting on fire text: write the prompt to reference the payload explicitly, for example "Investigate the alert described in the routine-fire-payload block", or the routine treats the text as inert context. Anyone holding the bearer token can send `text`, so the wrapper makes fire text from a leaked token arrive labeled as untrusted data rather than as direct instructions to your routine.

The example below triggers a routine from a shell. The routine ID and token shown are placeholders: replace them with the URL and token you copied when [adding the API trigger](<#add-an-api-trigger>), or the request fails with a `401` authentication error:

```bash theme={null}
curl -X POST https://api.anthropic.com/v1/claude_code/routines/trig_01ABCDEFGHJKLMNOPQRSTUVW/fire \
  -H "Authorization: Bearer sk-ant-oat01-xxxxx" \
  -H "anthropic-beta: experimental-cc-routine-2026-04-01" \
  -H "anthropic-version: 2023-06-01" \
  -H "Content-Type: application/json" \
  -d '{"text": "Sentry alert SEN-4521 fired in prod. Stack trace attached."}'
```

A successful request returns a JSON body with the new session ID and URL:

```json theme={null}
{
  "type": "routine_fire",
  "claude_code_session_id": "session_01HJKLMNOPQRSTUVWXYZ",
  "claude_code_session_url": "https://claude.ai/code/session_01HJKLMNOPQRSTUVWXYZ"
}
```

Open the session URL in a browser to watch the run in real time, review changes, or continue the conversation manually.



**注意：**

  The `/fire` endpoint ships under the `experimental-cc-routine-2026-04-01` beta header. Request and response shapes, rate limits, and token semantics may change while the feature is in research preview. Breaking changes ship behind new dated beta header versions, and the two most recent previous header versions continue to work so that callers have time to migrate.


#### API reference

For the full API reference, including all error responses, validation rules, and field limits, see [Trigger a routine via API](<https://platform.claude.com/docs/en/api/claude-code/routines-fire>) in the Claude Platform documentation.

The `/fire` endpoint is available to claude.ai users only and is not part of the Claude Platform API surface.

### Add a GitHub trigger

A GitHub trigger starts a new session automatically when a matching event occurs on a connected repository. Claude Code doesn't reuse sessions across events, so two PR updates produce two independent sessions.



**注释：**

  GitHub webhook events are subject to per-routine and per-account hourly caps. Events beyond the limit are dropped until the window resets.


The Claude GitHub App must be installed on the repository you want to subscribe to, whichever surface you configure the trigger from.

* Configure GitHub triggers from the web UI, which prompts you to install the app when it's missing. Follow the steps below to configure one on the web.
* From the CLI, install the app from the [GitHub App page](<https://github.com/apps/claude>) first, then ask Claude to attach a GitHub trigger to an existing routine, for example `/schedule add a GitHub trigger to my nightly review for pull requests opened in acme/webapp`. The CLI path requires Claude Code v2.1.225 or later. When Claude adds the trigger, it replies with a link to the routine the trigger fires.



  

#### Open the routine for editing

    Go to [claude.ai/code/routines](<https://claude.ai/code/routines>), click the routine, then open the menu next to the routine's name and select **Edit**.
  


  

#### Add a GitHub event trigger

    Scroll to the **Select a trigger** section, click **Add another trigger**, and choose **GitHub event**.

    

**注释：**

      Running `/web-setup` in the CLI grants repository access for cloning, but it does not install the Claude GitHub App and does not enable webhook delivery.
    

  


  

#### Configure the trigger

    Select the repository, choose an event from the [supported events](<#supported-events>) list, and optionally add filters. Save the trigger.
  


#### Supported events

GitHub triggers can subscribe to either of the following event categories. Within each category you can pick a specific action, such as `pull_request.opened`, or react to all actions in the category.

| Event | Triggers when |
| :- | :- |
| Pull request | A PR is opened, closed, assigned, labeled, synchronized, or otherwise updated |
| Release | A release is created, published, edited, or deleted |

#### Filter pull requests

Use filters to narrow which pull requests start a new session. All filter conditions must match for the routine to trigger. The available filter fields are:

| Filter | Matches |
| :- | :- |
| Author | PR author's GitHub username |
| Title | PR title text |
| Body | PR description text |
| Base branch | Branch the PR targets |
| Head branch | Branch the PR comes from |
| Labels | Labels applied to the PR |
| Is draft | Whether the PR is in draft state |
| Is merged | Whether the PR has been merged |

Each filter pairs a field with an operator: equals, contains, starts with, is one of, is not one of, or matches regex.

The `matches regex` operator tests the entire field value, not a substring within it. To match any title containing `hotfix`, write `.*hotfix.*`. Without the surrounding `.*`, the filter matches only a title that is exactly `hotfix` with nothing before or after. For literal substring matching without regex syntax, use the `contains` operator instead.

A few example filter combinations:

* **Auth module review**: base branch `main`, head branch contains `auth-provider`. Sends any PR that touches authentication to a focused reviewer.
* **Ready-for-review only**: is draft is `false`. Skips drafts so the routine only runs when the PR is ready for review.
* **Label-gated backport**: labels include `needs-backport`. Triggers a port-to-another-branch routine only when a maintainer tags the PR.

## Manage routines

Click a routine in the list to open its detail page. The detail page shows the routine's repositories, connectors, prompt, schedule, API tokens, GitHub triggers, and a list of past runs.

### View and interact with runs

Click any run to open it as a full session. From there you can see what Claude did, review changes, create a pull request, or continue the conversation. Each run session works like any other session: use the dropdown menu next to the session title to rename, archive, or delete it.



**注释：**

  A green status in the run list means the session started and exited without an infrastructure error. It does not mean the task in your prompt succeeded. Open the run to read the transcript and confirm what Claude actually did. Blocked network requests, missing connector tools, and task-level failures all surface there rather than in the status indicator.


### Edit and control routines

From the routine detail page you can:

* Click **Run now** to start a run immediately without waiting for the next scheduled time. You can optionally supply run-specific text, which reaches the routine the same way as the API trigger's `text` field.
* Use the on/off switch at the top of the page to pause or resume the schedule. Paused routines keep their configuration but don't run until you re-enable them.
* Open the menu next to the routine's name and select **Edit** to change the name, prompt, repositories, environment, connectors, or any of the routine's triggers. The **Select a trigger** section is where you add or remove schedules, API tokens, and GitHub event triggers.
* Open the same menu and select **Delete** to delete the routine.

### Manage routines from the CLI

The CLI supports managing existing routines. Run `/schedule list` to see all routines, `/schedule update` to change one, or `/schedule run` to trigger it immediately.

You can also ask about a routine's run history, for example `/schedule why did my nightly review do nothing this morning?`. Claude lists the routine's recent runs with their status and a link to [open each run on the web](<#view-and-interact-with-runs>), and reads a run's log to explain what happened, including tool errors, permission denials, and the final result. Requires Claude Code v2.1.227 or later.

### Repositories and branch permissions

Routines need GitHub access to clone repositories. When you create a routine from the CLI with `/schedule`, Claude checks whether your account has GitHub access for the repository you ran it from and, if it doesn't, adds a setup note naming how to grant it. See [GitHub authentication options](<https://code.claude.com/docs/en/claude-code-on-the-web#github-authentication-options>) for the two ways to grant access.

If your GitHub connection is missing or expired when a run is due, the routine skips runs until you reconnect, for up to 72 hours. Reconnect GitHub within that window and the routine resumes on its own. After 72 hours without a connection, the routine turns off, and you turn it back on after reconnecting GitHub.

Each repository you add is cloned on every run. Claude starts from the repository's default branch unless your prompt specifies otherwise.

Claude pushes its work to a branch prefixed with `claude/` unless your prompt directs it to push to another branch. To control which branches a run can push to, use branch protection rules or rulesets on GitHub. For runs on Anthropic-managed infrastructure, and for self-hosted runs that push through [Anthropic's git proxy](<https://code.claude.com/docs/en/self-hosted-environments-deploy#use-the-anthropic-git-proxy>), GitHub applies them to the GitHub access you connected, so a rule that access can bypass doesn't block a run's push. A self-hosted run that pushes with the git credentials your deployment provides is checked against those instead. See [Configure git](<https://code.claude.com/docs/en/self-hosted-environments-deploy#configure-git>).

### Connectors

Routines can use your connected MCP connectors to read from and write to external services during each run. For example, a routine that triages support requests might read from a Slack channel and create issues in Linear.

Connectors are the [claude.ai integrations](<https://code.claude.com/docs/en/mcp#use-mcp-servers-from-claude-ai>) on your account. MCP servers you added locally in the CLI with `claude mcp add` are stored on your machine rather than your claude.ai account, so they do not appear in the connectors list. To use one of those servers in a routine, add it as a connector at [claude.ai/customize/connectors](<https://claude.ai/customize/connectors>). For a routine with one repository, you can instead declare it in a committed [`.mcp.json`](<https://code.claude.com/docs/en/mcp#project-scope>) so it is part of the cloned repository.

When you create a routine, all of your currently connected connectors are included by default. Remove any that aren't needed to limit which tools Claude has access to during the run. You can also add connectors directly from the routine form.

To manage or add connectors outside of the routine form, visit [claude.ai/customize/connectors](<https://claude.ai/customize/connectors>) or use `/schedule update` in the CLI.

### Environments and network access

Each routine uses a [cloud environment](<https://code.claude.com/docs/en/cloud-environments>) that controls network access, environment variables, and setup scripts. The routine inherits the environment's network policy on every run.

The **Default** environment uses **Trusted** network access, which allows only the [default allowlist](<https://code.claude.com/docs/en/cloud-environments#default-allowed-domains>) through the session's network. Requests on that path to hosts outside the allowlist fail with `403` and `x-deny-reason: host_not_allowed`. MCP connector traffic is routed through Anthropic's servers rather than that path, so the connectors you add to the routine work without adding their hosts to **Allowed domains**. Remove any connectors you don't need under [Connectors](<#connectors>).

To allow additional domains on one of your own environments, follow these steps. An [organization-shared environment](<https://code.claude.com/docs/en/cloud-environments#organization-shared-environments>) opens read-only here, so an Owner changes its network access from the **Cloud environments** page in [admin settings](<https://claude.ai/admin-settings>) instead.



  

#### Open the routine for editing

    On the routine's detail page, open the menu next to the routine's name and select **Edit**.
  


  

#### Open the environment selector

    Below the **Instructions** box, select the cloud icon showing your environment's name, such as **Default**.
  


  

#### Open the environment settings

    Hover over the environment in the list and click the settings icon that appears on the right.
  


  

#### Change the network access level

    In the **Edit environment** dialog, change **Network access** to **Custom** and enter your domains in **Allowed domains**. Check **Also include default list of common package managers** to keep the [default allowlist](<https://code.claude.com/docs/en/cloud-environments#default-allowed-domains>) alongside your custom domains. Select **Full** instead for unrestricted access.
  


  

#### Save

    Click **Save changes**. The new policy applies from the next run.
  


See [Network access](<https://code.claude.com/docs/en/cloud-environments#network-access>) for details on access levels and the default allowlist.

## Usage and limits

Routines draw down subscription usage the same way interactive sessions do. See your current consumption at [claude.ai/settings/usage](<https://claude.ai/settings/usage>).

Separately from subscription usage, each way of starting a run has an hourly limit:

| Action | Limit | Counted for | Over the limit |
| :- | :- | :- | :- |
| Scheduled runs, including one-off runs | 100 per hour | Your account | The run waits until the limit resets |
| **Run now**, API fires, and setting a one-off routine to run again | 30 per hour | Each routine, one count shared by all three | The action fails until the limit resets |
| **Run now** and setting a one-off routine to run again | 100 per hour | Your account | Same |
| API fires | 100 per hour | Your account, counted separately from **Run now** | Same |
| GitHub events | See [Add a GitHub trigger](<#add-a-github-trigger>) | | |

None of these hourly limits has overage.

When a routine hits your subscription usage limit, organizations with usage credits turned on can keep running routines on metered overage. Without usage credits, additional runs are rejected until your usage window resets. Turn on usage credits at [claude.ai/settings/usage](<https://claude.ai/settings/usage>). On Team and Enterprise plans, an admin turns them on for the organization at [claude.ai/admin-settings/usage](<https://claude.ai/admin-settings/usage>).

While your subscription is paused, your routines are put on hold and don't run. Once your subscription is active again, turn them back on.

## Troubleshooting

<h3 id="schedule-returns-unknown-command">
  `/schedule` returns "Unknown command"
</h3>

The CLI hides `/schedule` when one of its requirements isn't met: the command menu shows `No commands match "/schedule"` while you type. Submitting it returns `Unknown command: /schedule`, except in the cases below that note a different answer.

The cause is usually one of the following:

* You are authenticated with a Console API key, an [Anthropic profile or federation credential](<https://code.claude.com/docs/en/authentication#anthropic-profiles-and-federation-credentials>), or a cloud provider such as Amazon Bedrock, Google Cloud's Agent Platform, or Microsoft Foundry. `/schedule` requires a claude.ai subscription login. With a Console API key or a profile, and feature-flag fetching enabled, submitting `/schedule` instead shows `/schedule is available with Claude for Enterprise — ask your admin about migrating from API-key access`. With a cloud-provider login, you still see `Unknown command: /schedule`. If `ANTHROPIC_API_KEY` or `ANTHROPIC_AUTH_TOKEN` is set in your shell, or `apiKeyHelper` is set in `settings.json`, remove it first, since these take precedence over a claude.ai login. A profile or federation credential takes precedence too, so switch that off as well
* You are fully signed out, with no API key or other credential. With feature-flag fetching enabled, submitting `/schedule` shows `/schedule requires a claude.ai subscription. Run /login to sign in with your claude.ai account.` Before v2.1.268, a signed-out session showed the same Claude for Enterprise message as a Console API key
* You are inside a cloud session, where submitting `/schedule` answers that the command isn't available in that environment. Manage routines from the [web UI](<https://claude.ai/code/routines>) instead
* Your organization's policy disables [cloud sessions](<https://code.claude.com/docs/en/claude-code-on-the-web>), which routines require. In this case, submitting `/schedule` answers [`Cloud sessions are disabled by your organization's policy`](<https://code.claude.com/docs/en/errors#cloud-sessions-are-disabled-by-your-organizations-policy>) instead. Before v2.1.268, it returned `Unknown command: /schedule`
* An Owner [turned off routines](<#routines-are-disabled-by-your-organizations-policy>) for your Team or Enterprise organization. Before v2.1.227, the command still appeared in this case, and claude.ai rejected the routine when Claude tried to create or run it

Unless your organization's policy disables routines or cloud sessions, you can create and manage routines at [claude.ai/code/routines](<https://claude.ai/code/routines>) regardless of how the CLI is configured.

<h3 id="routines-are-disabled-by-your-organizations-policy">
  "Routines are disabled by your organization's policy"
</h3>

An Owner in your Team or Enterprise organization has likely turned off the **Routines** toggle at [claude.ai/admin-settings/claude-code](<https://claude.ai/admin-settings/claude-code>). On Claude Code v2.1.227 or later, the same toggle also hides `/schedule` in the CLI. This is a server-side organization setting, so it cannot be overridden from your local configuration. Ask an Owner to enable routines for your organization.
