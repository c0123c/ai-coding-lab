# 使用 AI 测试现有代码

---

向现有项目添加测试不仅仅涉及生成测试代码。您需要确定哪些行为重要，遵循项目的约定，并验证断言是否捕获了错误的结果。

本指南向您展示如何使用 Visual Studio Code 中的 agent 为现有代码添加测试、运行它们、调查故障并查看结果。从一个功能或模块开始，然后在验证第一组测试后扩大覆盖范围。

## 先决条件

* [启用VS Code](<https://code.visualstudio.com/docs/getstarted/overview#_enable-ai-features>)中的AI功能。
* 打开 VS Code 中的现有项目。
* 安装项目的依赖项以及运行其测试所需的任何运行时。

测试扩展对于在终端中运行测试是可选的。要在测试资源管理器中发现并运行测试，请安装适当的 [ 测试扩展 ](<https://code.visualstudio.com/docs/debugtest/testing#_extensions-for-testing>)。

## 确定测试设置

重用项目的框架和测试约定，而不是引入新的测试运行程序。这有助于新测试与现有测试命令一起使用，并避免添加第二个设置来维护。

1. 打开聊天视图 (⌃⌘I (Windows、Linux Ctrl+Alt+I))，然后从 agent 选择器中选择 **Agent**。
2. 请 agent 在进行更改之前检查项目：

   ```
   Inspect this project's testing setup. Identify the test framework,
   where tests belong, and the commands for running a single test file
   and the related suite. Find an existing test that demonstrates the
   project's naming, assertions, and mocking conventions.
   Do not edit files or install dependencies.
   ```
3. 查看已识别的命令并要求 agent 运行相关的现有测试作为基准。记录所有故障，以便您可以将它们与新测试引入的故障区分开来。

如果项目没有测试，请首先要求agent提出一个框架和最小设置。在要求建议安装依赖项或更改配置之前，请先查看该建议。

提示

要跨会话重复使用测试约定和保护措施，请参阅[使工作流程可重复](<#_make-the-workflow-repeatable>)。

## 定义要测试的行为

选择一个小范围并描述其预期行为。一组有针对性的测试更容易检查缺失的情况和不正确的假设。包括源文件和代表性的现有测试 [提示中的上下文](<https://code.visualstudio.com/docs/chat/chat-overview#_add-context-to-your-prompts>) 所以 agent 可以遵循项目的模式。

使用需求或记录的行为来定义预期结果。要求 agent 从实现中推断出每一个期望，会带来生成保留现有错误的测试的风险。

例如，如果您的项目有一个具有以下要求的用户名验证器，请根据其功能和文件名调整此提示：

```
Propose unit tests for `validateUsername` without editing files yet.
The requirements are:
* Accept names containing 3 to 20 ASCII letters, digits, or underscores.
* Reject names outside that length range.
* Reject spaces and other characters.

Include valid examples, both length boundaries, and invalid inputs.
Compare the proposed cases with existing tests and identify missing
coverage. Flag any behavior that needs clarification.
```

在生成代码之前检查建议的案例。对于此示例，有用的边界情况包括 2、3、20 和 21 的长度。在每个限制处和刚好超出每个限制处进行测试有助于捕获小一错误。如果合同未指定诸如 `null` 之类的输入，则单独决定它们应如何表现，因此 agent 不会发明要求。

## 添加测试而不更改实现代码

保持实现代码不变可以让测试暴露现有的错误，并单独保留任何修复以供审查。在您同意这些情况后，要求agent仅实施**测试：

```
Add the agreed tests using the existing framework and test conventions.
Reuse existing test helpers where appropriate. Do not change implementation
code, add dependencies, or refactor unrelated tests.
Keep expected results explicit rather than computing them with the
function under test.
```

检查生成的测试。检查它们是否调用了预期的代码并断言可观察的结果，而不是仅检查执行是否完成。保持预期结果独立于被测函数：如果测试使用该函数来计算预期值，则相同的错误可能会影响这两个值并使测试通过。

## 运行测试并调查故障

从涵盖更改的最小测试选择开始，以获得更快的反馈并使故障更容易隔离。询问agent：

```
Run the new tests with the project's existing test command. Report the
command, the pass and fail counts, and any skipped tests. If tests fail,
explain whether the cause is test setup, an incorrect expectation, or
a possible implementation bug. Do not change implementation code or weaken
assertions to make the tests pass.
```

agent 可以使用可用的 [ 工具 ](<https://code.visualstudio.com/docs/agents/run/tools>) 来运行测试并检查其输出。在批准执行之前检查命令。如果执行受阻或者所需环境不可用，请自行运行该命令并提供失败输出。将未运行的测试视为未经验证。

在接受修复之前先找出原因。失败的测试可能会揭示错误，但它也可能反映出错误的测试设置或不正确的期望：

* **测试设置问题**：正确导入、固定装置或配置，然后重新运行测试。
* **不正确的期望**：在更改之前将断言与商定的要求进行比较。
* **实现错误**：保留暴露缺陷的测试并决定是否将修复实现作为单独的步骤。

不要仅仅为了获得通过的结果而接受删除的断言、跳过的测试或更改的预期值。目标测试通过后，运行相关套件以检查与现有测试的交互。

### 使用测试资源管理器帮助

如果测试扩展在测试资源管理器中公开了失败的测试，请将鼠标悬停在失败的测试上，然后选择 ** 修复测试失败 **（闪烁图标）以向 Copilot 请求帮助。在接受之前根据预期行为检查建议的更改，然后重新运行测试。

## 审查断言和覆盖范围

在保留更改之前，[查看差异](<https://code.visualstudio.com/docs/agents/run/review-code-edits>)并测试输出：

* 确认每个断言都检查商定的要求，包括相关的边界和错误情况。
* 检查测试是否独立，并且不依赖实时服务、共享可变状态或计时，除非这些依赖项是故意的。偶然的依赖关系可能会使测试通过或失败，具体取决于执行顺序或环境。
* 验证模拟不会取代测试应该执行的行为。否则，通过的测试可能只能确认模拟的配置响应。
* 确认实现代码和无关文件保持不变。
* 检查实际的执行结果，包括失败和跳过的测试，而不是仅依赖于agent的摘要。

如果您的运行程序支持 [ 测试覆盖范围 ](<https://code.visualstudio.com/docs/debugtest/testing#_test-coverage>)，请使用它来查找未经测试的分支并决定下一步要覆盖哪些行为。覆盖率显示执行了哪些代码，而不是断言是否正确。一个通过的套件，即使具有高覆盖率，也不能证明实现是正确的。

## 使工作流程可重复

将测试命令、框架、模拟约定和测试质量保障保存在项目的 [ 自定义指令 ](<https://code.visualstudio.com/docs/agent-customization/custom-instructions>) 中。这有助于 agent 在各个会话中遵循相同的指导，而无需您在每个提示中重复它。将说明保留在版本控制中，以便与您的团队共享。

除了项目约定外，还应包括以下保障措施：

```
* Do not delete or weaken assertions, skip tests, or change expected
  values solely to make failing tests pass.
* If an assertion appears incorrect, explain why and ask for confirmation
  before changing it.
* Run the relevant tests after changes. Report failures, skipped tests,
  and tests you could not run.
```

自定义指令指导 agent，但不强制执行这些保护措施。即使有说明，也要检查差异和测试结果。

---

Adding tests to an existing project involves more than generating test code. You need to identify which behavior matters, follow the project's conventions, and verify that the assertions catch incorrect results.

This guide shows you how to use an agent in Visual Studio Code to add tests for existing code, run them, investigate failures, and review the result. Start with one function or module, then expand coverage after you validate the first set of tests.

## Prerequisites

* [Enable AI features in VS Code](<https://code.visualstudio.com/docs/getstarted/overview#_enable-ai-features>).
* Open an existing project in VS Code.
* Install the project's dependencies and any runtime needed to run its tests.

A testing extension is optional for running tests in the terminal. To discover and run tests in the Test Explorer, install an appropriate [testing extension](<https://code.visualstudio.com/docs/debugtest/testing#_extensions-for-testing>).

## Identify the testing setup

Reuse the project's framework and test conventions instead of introducing a new test runner. This helps new tests work with existing test commands and avoids adding a second setup to maintain.

1. Open the Chat view (⌃⌘I (Windows, Linux Ctrl+Alt+I)) and select **Agent** from the agent picker.
2. Ask the agent to inspect the project before making changes:

   ```
   Inspect this project's testing setup. Identify the test framework,
   where tests belong, and the commands for running a single test file
   and the related suite. Find an existing test that demonstrates the
   project's naming, assertions, and mocking conventions.
   Do not edit files or install dependencies.
   ```
3. Review the identified commands and ask the agent to run the relevant existing tests as a baseline. Record any failures so you can distinguish them from failures introduced by new tests.

If the project has no tests, ask the agent to propose a framework and a minimal setup first. Review the proposal before asking it to install dependencies or change configuration.

Tip

To reuse your testing conventions and safeguards across sessions, see [Make the workflow repeatable](<#_make-the-workflow-repeatable>).

## Define the behavior to test

Choose a small scope and describe its expected behavior. A focused set of tests is easier to review for missing cases and incorrect assumptions. Include the source file and a representative existing test as [context in your prompt](<https://code.visualstudio.com/docs/chat/chat-overview#_add-context-to-your-prompts>) so the agent can follow the project's patterns.

Use requirements or documented behavior to define expected results. Asking the agent to infer every expectation from the implementation risks generating tests that preserve an existing bug.

For example, if your project has a username validator with the following requirements, adapt this prompt to its function and file names:

```
Propose unit tests for `validateUsername` without editing files yet.
The requirements are:
* Accept names containing 3 to 20 ASCII letters, digits, or underscores.
* Reject names outside that length range.
* Reject spaces and other characters.

Include valid examples, both length boundaries, and invalid inputs.
Compare the proposed cases with existing tests and identify missing
coverage. Flag any behavior that needs clarification.
```

Review the proposed cases before generating code. For this example, useful boundary cases include lengths of 2, 3, 20, and 21. Testing at and just outside each limit helps catch off-by-one errors. Decide separately how inputs such as `null` should behave if the contract doesn't specify them, so the agent doesn't invent a requirement.

## Add tests without changing implementation code

Keeping implementation code unchanged lets the tests expose existing bugs and keeps any fixes separate for review. After you agree on the cases, ask the agent to implement *only* the tests:

```
Add the agreed tests using the existing framework and test conventions.
Reuse existing test helpers where appropriate. Do not change implementation
code, add dependencies, or refactor unrelated tests.
Keep expected results explicit rather than computing them with the
function under test.
```

Inspect the generated tests. Check that they call the intended code and assert observable results, rather than only checking that execution completes. Keep expected results independent of the function under test: if the test uses that function to calculate the expected value, the same bug can affect both values and let the test pass.

## Run tests and investigate failures

Start with the smallest test selection that covers the changes to get faster feedback and make failures easier to isolate. Ask the agent:

```
Run the new tests with the project's existing test command. Report the
command, the pass and fail counts, and any skipped tests. If tests fail,
explain whether the cause is test setup, an incorrect expectation, or
a possible implementation bug. Do not change implementation code or weaken
assertions to make the tests pass.
```

The agent can use available [tools](<https://code.visualstudio.com/docs/agents/run/tools>) to run tests and inspect their output. Review commands before approving execution. If execution is blocked or the required environment is unavailable, run the command yourself and provide the failure output. Treat tests that weren't run as unverified.

Identify the cause before accepting a fix. A failing test can reveal a bug, but it can also reflect faulty test setup or an incorrect expectation:

* **Test setup problem**: correct imports, fixtures, or configuration, then rerun the tests.
* **Incorrect expectation**: compare the assertion with the agreed requirements before changing it.
* **Implementation bug**: keep the test that exposes the defect and decide whether to fix the implementation as a separate step.

Don't accept deleted assertions, skipped tests, or changed expected values solely to obtain a passing result. After the targeted tests pass, run the related suite to check for interactions with existing tests.

### Use Test Explorer assistance

If a testing extension exposes a failing test in the Test Explorer, hover over the failed test and select **Fix Test Failure** (sparkle icon) to request help from Copilot. Review the suggested change against the expected behavior before accepting it, then rerun the test.

## Review assertions and coverage

Before keeping the changes, [review the diff](<https://code.visualstudio.com/docs/agents/run/review-code-edits>) and test output:

* Confirm that each assertion checks an agreed requirement, including relevant boundary and error cases.
* Check that tests are independent and don't rely on live services, shared mutable state, or timing unless those dependencies are intentional. Accidental dependencies can make tests pass or fail depending on execution order or environment.
* Verify that mocks don't replace the behavior the tests are supposed to exercise. Otherwise, a passing test might only confirm the mock's configured response.
* Confirm that implementation code and unrelated files remain unchanged.
* Check the actual execution results, including failures and skipped tests, rather than relying only on the agent's summary.

If your runner supports [test coverage](<https://code.visualstudio.com/docs/debugtest/testing#_test-coverage>), use it to find untested branches and decide which behavior to cover next. Coverage shows which code executed, not whether the assertions are correct. A passing suite, even with high coverage, doesn't prove that the implementation is correct.

## Make the workflow repeatable

Save the test commands, framework, mocking conventions, and test-quality safeguards in your project's [custom instructions](<https://code.visualstudio.com/docs/agent-customization/custom-instructions>). This helps the agent follow the same guidance across sessions without you repeating it in every prompt. Keep the instructions in version control to share them with your team.

Alongside your project's conventions, include safeguards such as:

```
* Do not delete or weaken assertions, skip tests, or change expected
  values solely to make failing tests pass.
* If an assertion appears incorrect, explain why and ask for confirmation
  before changing it.
* Run the relevant tests after changes. Report failures, skipped tests,
  and tests you could not run.
```

Custom instructions guide the agent but don't enforce these safeguards. Review the diff and test results even when instructions are in place.
