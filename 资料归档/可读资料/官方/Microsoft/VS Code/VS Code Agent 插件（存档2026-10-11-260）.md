Agent 插件将相关定制捆绑到一个可安装的设置中。使用插件采用共享工作流程，而不是单独组装其技能、agents 和工具集成。例如，测试插件可以打包测试运行技能、审查 agent 以及旨在协同工作的报告集成。

如果您只需要一个项目规则或一项技能，请从[个性化定制](<https://code.visualstudio.com/docs/agents/concepts/customization#_customization-options-at-a-glance>)开始。当其组件支持您想要一起采用的工作流程时，请选择一个捆绑包。

您可以从Visual Studio Code中的插件市场发现并安装插件。插件与您本地定义的自定义一起工作。当您安装插件时，其支持的自定义将在相关的 agent 界面中可用。

Agent 插件是一个 [ 开放标准 ](<https://agent-plugins.org/>)，用于打包 [agent skills](<https://code.visualstudio.com/docs/agent-customization/agent-skills>) 和 [MCP 服务器 ](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>)，可跨多个 AI agents 使用，包括VS Code、GitHub Copilot CLI 中的 GitHub Copilot 和 GitHub Copilot 应用程序。
VS Code 还支持客户端特定的插件功能，包括斜线命令、[自定义 agents](<https://code.visualstudio.com/docs/agent-customization/custom-agents>)、规则、[挂钩](<https://code.visualstudio.com/docs/agent-customization/hooks>)和[自动化模板](<#_automations-in-plugins>)。在 Agent 插件包中，大部分功能来自 `com.github.copilot` 命名空间。现有的 Copilot 和 Claude 插件格式保留自己的布局。

有关插件如何适应更广泛的自定义选项集的信息，请参阅[自定义概念](<https://code.visualstudio.com/docs/agents/concepts/customization>)。

## 插件提供什么

Agent 插件 1.0 将技能和 MCP 服务器定义为可移植组件类型。其他功能是特定于客户端的，并使用标准的反向域[客户端扩展命名空间](<https://agent-plugins.org/plugin-authors/client-extensions>)。 VS Code 从 `com.github.copilot` 命名空间读取 Copilot 特定组件，并忽略其他客户端拥有的命名空间。

|能力|描述|客户特定|标准型|
| --- | --- | --- | --- |
|[MCP 服务器](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>)|外部工具集成|  | ✓ |
|[技能](<https://code.visualstudio.com/docs/agent-customization/agent-skills>)|按需加载的指令、脚本和资源|  | ✓ |
| [Agents](<https://code.visualstudio.com/docs/agent-customization/custom-agents>) |专门的角色和工具配置| ✓ |  |
|[挂钩](<https://code.visualstudio.com/docs/agent-customization/hooks>)|在 agent 生命周期点执行的 Shell 命令| ✓ |  |
|[自动化模板](<#_automations-in-plugins>)|agent 任务的可重复使用的提示和时间表| ✓ |  |
|斜杠命令|您可以在聊天中使用 `/` 调用的命令| ✓ |  |

例如，测试插件可能包括带有脚本的 `test-runner` 技能、带有只读工具的 `test-reviewer` agent 以及用于测试报告仪表板的 MCP 服务器。在 Agent Plugins 格式中，目录结构如下所示：

```
my-testing-plugin/
  plugin.json              # Plugin metadata and configuration
  skills/
    test-runner/
      SKILL.md             # Testing skill instructions
      run-tests.sh         # Supporting script
  mcp.json                 # MCP server definitions
  automations/
    review.automation.md   # Automation template
  scripts/
    validate-tests.sh      # Hook script
  com.github.copilot/
    agents/
      test-reviewer.agent.md  # Code review agent
    hooks/
      hooks.json           # Hook configuration
```

Copilot 和 Claude 格式的插件在不同位置提供相同的功能。请参阅[插件格式](<#_plugin-formats>)。

安装后，插件提供的自定义项将与您本地定义的自定义项一起显示。例如，插件中的技能显示在**配置技能**菜单中，插件中的MCP服务器显示在MCP服务器列表中。

注意事项

插件可以包括在您的计算机上运行代码的挂钩和 MCP 服务器。安装前检查插件内容和发布者，尤其是来自社区市场的插件。

## 插件清单（plugin.json）

Agent 插件 1.0 包的根目录中有一个 `plugin.json` 文件，该文件声明了标准的架构：

```
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "my-dev-tools",
  "description": "React development utilities",
  "version": "1.2.0"
}
```

|领域|类型|必填|描述|
| --- | --- | --- | --- |
| `$schema` |字符串|是的|Canonical Agent 插件架构标识符。|
| `name` |字符串|是的|插件名称和包标识符。|
| `version` |字符串|否|插件版本。建议使用语义版本控制。|
| `description` |字符串|否|插件的简要说明。|
| `author` |对象|否|带有可选 `name`、`email` 和 `url` 字段的作者信息。|
| `homepage` |字符串|否|文档或主页。|
| `repository` |字符串|否|源存储库。|
| `license` |字符串|否|许可证标识符。建议使用 SPDX 标识符。|
| `keywords` |字符串[]|否|搜索和发现术语。|
| `extensions` |对象|否|由反向域命名空间键入的客户端特定数据。|

技能是从 `skills/` 文件夹中发现的，MCP 服务器配置是从 `mcp.json` 文件中发现的。您没有在清单中列出这些组件路径。自定义 agents、挂钩、命令和 MCP 服务器定义不是可移植的顶级清单字段。

Copilot 特定组件位于插件根目录的 `com.github.copilot` 目录中，Copilot 特定清单数据位于 `extensions` 中的匹配键下：

```
my-plugin/
  plugin.json              # $schema declares Agent Plugins 1.0
  skills/                  # Portable: agent skills
  mcp.json                 # Portable: MCP server configuration
  com.github.copilot/      # Copilot-specific components
    agents/
    commands/
    rules/
    hooks/
      hooks.json
```

其他客户端忽略 `com.github.copilot` 命名空间，因此包在保持其 Copilot 功能的同时保持可移植性。

有关完整的字段约束和验证规则，请参阅 [Agent 插件清单文档 ](<https://agent-plugins.org/plugin-authors/manifest>)。

注意事项

未声明 Agent 插件架构的现有 Copilot 格式插件仍受支持。有关其清单字段，请参阅 [GitHub Copilot CLI 插件参考 ](<https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference#pluginjson>)。

## 插件格式

VS Code 通过检查根清单和特定于格式的清单路径来自动检测插件格式。声明规范 Agent 插件 `$schema` 的根 `plugin.json` 使用 Agent 插件语义。当未找到其他格式标记时，将使用 Copilot 格式作为默认格式。

|插件格式|插件清单|
| --- | --- |
|Agent 插件 1.0|`plugin.json`，其中 `$schema` 设置为 `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json`|
| Copilot | `plugin.json` |
| Claude | `.claude-plugin/plugin.json` |
|旧版 OpenPlugin| `.plugin/plugin.json` |

### 插件环境变量

某些插件格式提供根令牌，您可以在挂钩命令和 MCP 服务器配置中使用该令牌来引用插件目录中的文件。 VS Code 在运行时扩展令牌，并将其设置为挂钩或服务器进程中的环境变量。

|插件格式|插件根目录|
| --- | --- |
|Agent 插件 1.0| `${PLUGIN_ROOT}` |
| Claude | `${CLAUDE_PLUGIN_ROOT}` |
| Copilot |`${PLUGIN_ROOT}` 或 `${CLAUDE_PLUGIN_ROOT}`|
|旧版 OpenPlugin| `${PLUGIN_ROOT}` |

Agent 插件 1.0 还为打包文件定义了 `${PLUGIN_ROOT}`，为在插件更新期间持续存在的可写状态定义了 `${PLUGIN_DATA}`。 VS Code 保留这些占位符以供插件运行时扩展。有关支持占位符的详细信息，请参阅[Agent插件规范](<https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md#9-environment-variables-and-placeholder-expansion>)。

## 插件中的自动化

Agent 插件可以提供出现在下面的自动化模板 **来自插件的模板** 在 [Agents 窗户](<https://code.visualstudio.com/docs/agents/run/automations#_start-from-a-template>)。模板提供可重用的名称、提示和时间表。安装插件时，它不会创建或启用自动化。

注意事项

自动化模板是 VS Code 特定的插件功能，而不是可移植的 Agent 插件 1.0 组件类型。

### 自动化模板位置

将自动化模板存储在 Agent 插件包根部的 `automations/` 文件夹中。每个文件必须使用 `.automation.md` 后缀：

```
my-plugin/
  plugin.json
  automations/
    daily-review.automation.md
    weekly-review.automation.md
```

要从其他文件夹添加模板，请在`plugin.json`中配置`extensions.com.github.copilot.automations.paths`。这些路径相对于 `com.github.copilot/` 文件夹，并补充默认的 `automations/` 文件夹：

```
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "my-dev-tools",
  "version": "1.2.0",
  "extensions": {
    "com.github.copilot": {
      "automations": {
        "paths": ["./team-automations/"]
      }
    }
  }
}
```

将 `exclusive` 与 `paths` 一起设置为 `true`，以仅从配置的文件夹加载模板并跳过默认的 `automations/` 文件夹。

### 自动化模板格式

自动化模板是一个带有 YAML frontmatter 的 Markdown 文件。 Markdown 正文是提示：

```
---
version: 1
id: weekly-review
name: Weekly review
description: Review the workspace for regressions.
schedule:
  kind: cron
  expression: "30 10 * * 5"
  timeZone: local
---
Review the workspace changes from the past week.
Identify regressions and suggest follow-up actions.
```

frontmatter 支持这些字段：

|领域|必填|描述|
| --- | --- | --- |
| `version` |是的|文件格式版本。使用`1`。|
| `id` |是的|插件内唯一的标识符。使用小写字母、数字、句点或连字符，最多 64 个字符。|
| `name` |是的|模板的显示名称。|
| `description` |否|自动化目的的简短描述。|
| `schedule` |是的|手动、每小时、每天或每周计划。|

使用以下计划格式之一：

|时间表| YAML |
| --- | --- |
|手册| `kind: manual` |
|每小时| `kind: hourly` |
|每日|`kind: cron`，五字段表达式，例如 `"0 9 * * *"` 和 `timeZone: local`|
|每周|`kind: cron`，五字段表达式，例如 `"30 10 * * 5"` 和 `timeZone: local`|

五个 cron 字段分别代表分钟、小时、月份中的某一天、月份和星期几。仅支持表示每日或每周计划的本地时间 cron 表达式。 VS Code 忽略无效模板而不是更改其计划。

插件模板无法指定工作区、提供程序、模型、权限、启用状态或运行历史记录。当有人选择模板时，**新自动化**对话框将打开，以便他们可以查看提示并选择执行配置。默认情况下，**启用**复选框处于清除状态。

禁用插件将从自动化视图中删除其模板。之前从这些模板创建的自动化及其运行历史记录仍然可用。

## MCP 插件中的服务器

插件可以捆绑[MCP服务器](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>)，为agents提供额外的工具和数据源。插件 MCP 服务器在启用插件时自动启动，在禁用插件时停止。

### MCP配置文件

将 MCP 服务器定义放在插件根目录的 `mcp.json` 文件中，并遵循 [ 可移植 MCP 配置格式 ](<https://agent-plugins.org/plugin-authors/mcp-servers>)。

```
my-plugin/
  plugin.json             # Plugin metadata and configuration
  skills/
  mcp.json              # MCP server definitions
  servers/
    db-server             # Server executable
  config.json             # Server configuration
```

将 MCP 服务器定义放置在插件根目录的 `.mcp.json` 文件中。 VS Code 加载插件时会自动发现此文件。

```
my-plugin/
  plugin.json             # Plugin metadata and configuration
  skills/
  .mcp.json              # MCP server definitions
  servers/
    db-server             # Server executable
  config.json             # Server configuration
```

在 `.mcp.json` 文件中，MCP 服务器在顶级 `mcpServers` 对象中定义。每个服务器条目指定一个命令、参数和可选的环境变量：

```
{
  "mcpServers": {
    "plugin-database": {
      "command": "${CLAUDE_PLUGIN_ROOT}/servers/db-server",
      "args": ["--config", "${CLAUDE_PLUGIN_ROOT}/config.json"],
      "env": {
        "DB_PATH": "${CLAUDE_PLUGIN_ROOT}/data"
      }
    },
    "plugin-api": {
      "command": "npx",
      "args": ["@company/mcp-server", "--plugin-mode"],
      "cwd": "${CLAUDE_PLUGIN_ROOT}"
    }
  }
}
```

### 服务器配置中参考插件路径

对于 Claude 格式的插件，请使用 MCP 服务器字段中的 `${CLAUDE_PLUGIN_ROOT}` 令牌来引用插件目录中的可执行文件和文件。 VS Code 在以下字段中扩展此标记：

* `command`：可执行路径
* `args`：命令行参数
* `cwd`：工作目录
* `env`：环境变量值
* `envFile`：环境文件的路径
* `url`：用于基于HTTP-的MCP服务器
* `headers`：HTTP 标头值

VS Code 还将 `CLAUDE_PLUGIN_ROOT` 环境变量注入服务器进程，以便服务器代码可以在运行时访问插件路径。

### 插件 MCP 服务器如何与其他服务器交互

插件 MCP 服务器与工作区和用户级 MCP 服务器一起出现。您可以通过相同的工具来管理它们：

* 在聊天视图中选择 ** 配置工具 ** 以查看来自所有 MCP 服务器（包括插件服务器）的工具。
* 运行 **MCP：从命令面板列出服务器 ** 以查看插件服务器以及其他服务器。

当您安装插件时，插件 MCP 服务器将被隐式信任。与工作区 MCP 服务器不同，它们在启动时不会显示单独的信任提示。

禁用插件会停止其 MCP 服务器。已停止的服务器提供的工具在聊天中不再可用。

## 插件中的钩子

插件可以包含在 agent 生命周期点运行 shell 命令的 [ 钩子 ](<https://code.visualstudio.com/docs/agent-customization/hooks>)。插件范围的挂钩与您的工作区和用户级挂钩一起工作。启用插件后，除了为同一事件配置的任何其他挂钩之外，还会触发这些挂钩。

注意事项

挂钩是特定于客户端的，不是可移植的 Agent 插件 1.0 组件类型。在 Agent 插件包中，它们来自 `com.github.copilot` 命名空间。

组织可以通过插件分发批准的挂钩。当托管设置指定 `allowManagedHooksOnly: true` 时，插件挂钩仅在托管 `enabledPlugins["plugin@marketplace"]: true` 条目强制启用插件时运行。仅用户启用是不够的，`allowManagedHooksOnly` 本身并不启用该插件。请参阅[通过托管插件部署挂钩](<https://code.visualstudio.com/docs/enterprise/manage-ai-settings#_deploy-hooks-through-managed-plugins>)。

挂钩配置和有效负载取决于会话的工具。下面描述的事件和匹配器行为适用于本地线束。从 [ 开始，为 Copilot、Claude 和 Codex 会话选择钩子实现 ](<https://code.visualstudio.com/docs/agent-customization/hooks#_choose-the-hook-implementation-for-your-session>)。

### 挂钩文件位置

挂钩文件位置取决于插件格式：

|插件格式|挂钩文件路径|
| --- | --- |
|Agent 插件 1.0| `com.github.copilot/hooks/hooks.json` |
| Claude | `hooks/hooks.json` |
| Copilot |`hooks.json`（位于插件根目录）|

VS Code自动检测插件格式并自动发现hook文件。

```
my-plugin/
  plugin.json
  com.github.copilot/
    hooks/
      hooks.json         # Hook configuration (Agent Plugins format)
  scripts/
    format.sh            # Hook script referenced by hooks.json
```

### 钩子配置格式

对于本地线束，插件挂钩使用与 [ 工作空间挂钩 ](<https://code.visualstudio.com/docs/agent-customization/hooks#_local-hook-configuration-formats>) 相同的基本格式。本地解析器接受 Claude 挂钩配置，包括匹配器语法，但忽略匹配器值。因此，事件的所有嵌套命令都在本地会话中运行。

**平面格式**（与工作区挂钩相同）：

```
{
  "hooks": {
    "PostToolUse": [
      {
        "type": "command",
        "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
      }
    ]
  }
}
```

**匹配器格式**（Claude兼容性语法）：

```
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
          }
        ]
      }
    ]
  }
}
```

本地线束解析 `matcher` 字段以与 Claude Code 兼容，但忽略匹配器值。要过滤本地挂钩行为，请检查挂钩脚本内的事件输入。

### 在钩子命令中引用插件路径

在本地挂钩命令中使用插件根令牌来引用捆绑的脚本和文件，而无需对插件的安装路径进行硬编码。

|插件格式|代币|环境变量|
| --- | --- | --- |
| Claude | `${CLAUDE_PLUGIN_ROOT}` | `CLAUDE_PLUGIN_ROOT` |
|旧版 OpenPlugin| `${PLUGIN_ROOT}` | `PLUGIN_ROOT` |

VS Code 将令牌扩展为挂钩命令中插件的绝对路径和 `env` 值。这包括 `command`、`bash`、`powershell` 和特定于平台的命令字段。扩展命令路径是 shell 引用的，因此插件路径可以包含空格。

钩子进程还接收匹配的根环境变量。例如，Node.js脚本可以读取`process.env.CLAUDE_PLUGIN_ROOT`。当在不同位置发现插件时，这些引用解析为新的根。

```
{
  "hooks": {
```

## 跨工具兼容性

Agent 插件 1.0 是一个为跨工具兼容性而设计的开放标准。符合标准的插件使用根`plugin.json`，将技能放在`skills/`中，并将MCP服务器配置放在`mcp.json`中。兼容的客户端可以从同一包中发现它们支持的可移植组件类型。

Agent 插件还可以在稳定的反向域命名空间下包含特定于客户端的清单数据和文件。客户端会忽略它们未实现的命名空间，因此特定于客户端的功能不会阻止其他客户端加载可移植组件。 VS Code 从 `com.github.copilot` 命名空间读取自定义 agents、斜杠命令、规则、挂钩和自动化路径配置。其他客户端仅使用它们支持的名称空间中的功能。

例如：

```
my-plugin/
  plugin.json
  skills/
  mcp.json
  com.github.copilot/      # Read by VS Code and other Copilot clients
  com.example.client/      # Ignored by VS Code
```

VS Code 继续支持现有的 Copilot、Claude 和旧版 OpenPlugin 格式。未声明 [​​Agent 插件架构的插件将继续使用其现有的特定于格式的发现规则。

有关可移植格式的详细信息，请参阅[Agent插件规范](<https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md>)。对于其他格式，请参阅 [GitHub Copilot CLI 插件参考 ](<https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference>) 和 [Claude Code 插件市场文档 ](<https://code.claude.com/docs/en/plugin-marketplaces>)。

Agent plugins bundle related customizations into one installable setup. Use a plugin to adopt a shared workflow instead of assembling its skills, agents, and tool integrations individually. For example, a testing plugin can package a test-running skill, review agent, and reporting integration that are intended to work together.

If you only need a project rule or a single skill, start with an [individual customization](<https://code.visualstudio.com/docs/agents/concepts/customization#_customization-options-at-a-glance>). Choose a bundle when its components support a workflow you want to adopt together.

You can discover and install plugins from plugin marketplaces in Visual Studio Code. Plugins work alongside your locally defined customizations. When you install a plugin, its supported customizations become available in the relevant agent interfaces.

Agent Plugins is an [open standard](<https://agent-plugins.org/>) for packaging [agent skills](<https://code.visualstudio.com/docs/agent-customization/agent-skills>) and [MCP servers](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>) that works across multiple AI agents, including GitHub Copilot in VS Code, GitHub Copilot CLI, and the GitHub Copilot app.
VS Code also supports client-specific plugin capabilities, including slash commands, [custom agents](<https://code.visualstudio.com/docs/agent-customization/custom-agents>), rules, [hooks](<https://code.visualstudio.com/docs/agent-customization/hooks>), and [automation templates](<#_automations-in-plugins>). In an Agent Plugins package, most of these capabilities come from the `com.github.copilot` namespace. The existing Copilot and Claude plugin formats keep their own layouts.

## What plugins provide

Agent Plugins 1.0 defines skills and MCP servers as portable component types. Other capabilities are client-specific and use the standard's reverse-domain [client extension namespaces](<https://agent-plugins.org/plugin-authors/client-extensions>). VS Code reads Copilot-specific components from the `com.github.copilot` namespace and ignores namespaces owned by other clients.

| Capability | Description | Client-specific | Standard |
| --- | --- | --- | --- |
| [MCP servers](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>) | External tool integrations |  | ✓ |
| [Skills](<https://code.visualstudio.com/docs/agent-customization/agent-skills>) | Instructions, scripts, and resources that load on-demand |  | ✓ |
| [Agents](<https://code.visualstudio.com/docs/agent-customization/custom-agents>) | Specialized personas and tool configurations | ✓ |  |
| [Hooks](<https://code.visualstudio.com/docs/agent-customization/hooks>) | Shell commands that execute at agent lifecycle points | ✓ |  |
| [Automation templates](<#_automations-in-plugins>) | Reusable prompts and schedules for agent tasks | ✓ |  |
| Slash commands | Commands you can invoke with `/` in chat | ✓ |  |

For example, a testing plugin might include a `test-runner` skill with scripts, a `test-reviewer` agent with read-only tools, and an MCP server for a test reporting dashboard. In the Agent Plugins format, the directory structure looks like this:

```
my-testing-plugin/
  plugin.json              # Plugin metadata and configuration
  skills/
    test-runner/
      SKILL.md             # Testing skill instructions
      run-tests.sh         # Supporting script
  mcp.json                 # MCP server definitions
  automations/
    review.automation.md   # Automation template
  scripts/
    validate-tests.sh      # Hook script
  com.github.copilot/
    agents/
      test-reviewer.agent.md  # Code review agent
    hooks/
      hooks.json           # Hook configuration
```

Plugins in the Copilot and Claude formats provide the same capabilities from different locations. See [Plugin formats](<#_plugin-formats>).

Once installed, plugin-provided customizations appear alongside your locally defined ones. For example, skills from a plugin show up in the **Configure Skills** menu, and MCP servers from a plugin appear in the MCP server list.

Caution

Plugins can include hooks and MCP servers that run code on your machine. Review the plugin contents and publisher before installing, especially for plugins from community marketplaces.

## Plugin manifest (plugin.json)

An Agent Plugins 1.0 package has a `plugin.json` file at its root that declares the standard's schema:

```
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "my-dev-tools",
  "description": "React development utilities",
  "version": "1.2.0"
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `$schema` | string | Yes | Canonical Agent Plugins schema identifier. |
| `name` | string | Yes | Plugin name and package identifier. |
| `version` | string | No | Plugin version. Semantic Versioning is recommended. |
| `description` | string | No | Brief description of the plugin. |
| `author` | object | No | Author information with optional `name`, `email`, and `url` fields. |
| `homepage` | string | No | Documentation or homepage. |
| `repository` | string | No | Source repository. |
| `license` | string | No | License identifier. An SPDX identifier is recommended. |
| `keywords` | string[] | No | Search and discovery terms. |
| `extensions` | object | No | Client-specific data keyed by reverse-domain namespace. |

Skills are discovered from the `skills/` folder, and MCP server configuration is discovered from the `mcp.json` file. You don't list these component paths in the manifest. Custom agents, hooks, commands, and MCP server definitions are not portable top-level manifest fields.

Copilot-specific components live in the `com.github.copilot` directory at the plugin root, and Copilot-specific manifest data goes under the matching key in `extensions`:

```
my-plugin/
  plugin.json              # $schema declares Agent Plugins 1.0
  skills/                  # Portable: agent skills
  mcp.json                 # Portable: MCP server configuration
  com.github.copilot/      # Copilot-specific components
    agents/
    commands/
    rules/
    hooks/
      hooks.json
```

Other clients ignore the `com.github.copilot` namespace, so a package stays portable while keeping its Copilot capabilities.

For the full field constraints and validation rules, see the [Agent Plugins manifest documentation](<https://agent-plugins.org/plugin-authors/manifest>).

Note

Existing Copilot-format plugins that don't declare the Agent Plugins schema remain supported. For their manifest fields, see the [GitHub Copilot CLI plugin reference](<https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference#pluginjson>).

## Plugin formats

VS Code auto-detects the plugin format by checking the root manifest and format-specific manifest paths. A root `plugin.json` that declares the canonical Agent Plugins `$schema` uses Agent Plugins semantics. The Copilot format is used as the default when no other format marker is found.

| Plugin format | Plugin manifest |
| --- | --- |
| Agent Plugins 1.0 | `plugin.json` with `$schema` set to `https://agent-plugins.org/schemas/1.0.0/plugin.schema.json` |
| Copilot | `plugin.json` |
| Claude | `.claude-plugin/plugin.json` |
| Legacy OpenPlugin | `.plugin/plugin.json` |

### Plugin environment variables

Some plugin formats provide a root token that you can use in hook commands and MCP server configurations to reference files within the plugin directory. VS Code expands the token at runtime and also sets it as an environment variable in the hook or server process.

| Plugin format | Plugin root |
| --- | --- |
| Agent Plugins 1.0 | `${PLUGIN_ROOT}` |
| Claude | `${CLAUDE_PLUGIN_ROOT}` |
| Copilot | `${PLUGIN_ROOT}` or `${CLAUDE_PLUGIN_ROOT}` |
| Legacy OpenPlugin | `${PLUGIN_ROOT}` |

Agent Plugins 1.0 also defines `${PLUGIN_ROOT}` for packaged files and `${PLUGIN_DATA}` for writable state that persists across plugin updates. VS Code preserves these placeholders for the plugin runtime to expand. For details about where placeholders are supported, see the [Agent Plugins specification](<https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md#9-environment-variables-and-placeholder-expansion>).

## Automations in plugins

Agent Plugins can contribute automation templates that appear under **Templates from Plugins** in the [Agents window](<https://code.visualstudio.com/docs/agents/run/automations#_start-from-a-template>). A template provides a reusable name, prompt, and schedule. It doesn't create or enable an automation when the plugin is installed.

Note

Automation templates are a VS Code-specific plugin capability, not a portable Agent Plugins 1.0 component type.

### Automation template location

Store automation templates in an `automations/` folder at the root of an Agent Plugins package. Each file must use the `.automation.md` suffix:

```
my-plugin/
  plugin.json
  automations/
    daily-review.automation.md
    weekly-review.automation.md
```

To add templates from other folders, configure `extensions.com.github.copilot.automations.paths` in `plugin.json`. These paths are relative to the `com.github.copilot/` folder and supplement the default `automations/` folder:

```
{
  "$schema": "https://agent-plugins.org/schemas/1.0.0/plugin.schema.json",
  "name": "my-dev-tools",
  "version": "1.2.0",
  "extensions": {
    "com.github.copilot": {
      "automations": {
        "paths": ["./team-automations/"]
      }
    }
  }
}
```

Set `exclusive` to `true` alongside `paths` to load templates only from the configured folders and skip the default `automations/` folder.

### Automation template format

An automation template is a Markdown file with YAML frontmatter. The Markdown body is the prompt:

```
---
version: 1
id: weekly-review
name: Weekly review
description: Review the workspace for regressions.
schedule:
  kind: cron
  expression: "30 10 * * 5"
  timeZone: local
---
Review the workspace changes from the past week.
Identify regressions and suggest follow-up actions.
```

The frontmatter supports these fields:

| Field | Required | Description |
| --- | --- | --- |
| `version` | Yes | File format version. Use `1`. |
| `id` | Yes | Identifier that is unique within the plugin. Use lowercase letters, numbers, periods, or hyphens, with a maximum of 64 characters. |
| `name` | Yes | Display name for the template. |
| `description` | No | Short description of the automation's purpose. |
| `schedule` | Yes | Manual, hourly, daily, or weekly schedule. |

Use one of these schedule formats:

| Schedule | YAML |
| --- | --- |
| Manual | `kind: manual` |
| Hourly | `kind: hourly` |
| Daily | `kind: cron`, a five-field expression such as `"0 9 * * *"`, and `timeZone: local` |
| Weekly | `kind: cron`, a five-field expression such as `"30 10 * * 5"`, and `timeZone: local` |

The five cron fields represent minute, hour, day of month, month, and day of week. Only local-time cron expressions that represent a daily or weekly schedule are supported. VS Code ignores invalid templates rather than changing their schedule.

Plugin templates can't specify a workspace, provider, model, permissions, enabled state, or run history. When someone selects a template, the **New Automation** dialog opens so they can review the prompt and choose the execution configuration. The **Enabled** checkbox is cleared by default.

Disabling a plugin removes its templates from the Automations view. Automations that were previously created from those templates and their run history remain available.

## MCP servers in plugins

Plugins can bundle [MCP servers](<https://code.visualstudio.com/docs/agent-customization/mcp-servers>) to provide agents with additional tools and data sources. Plugin MCP servers start automatically when the plugin is enabled and stop when the plugin is disabled.

### MCP configuration file

Place MCP server definitions in the `mcp.json` file at the plugin root and follow the [portable MCP configuration format](<https://agent-plugins.org/plugin-authors/mcp-servers>).

```
my-plugin/
  plugin.json             # Plugin metadata and configuration
  skills/
  mcp.json              # MCP server definitions
  servers/
    db-server             # Server executable
  config.json             # Server configuration
```

Place MCP server definitions in the `.mcp.json` file at the plugin root. VS Code discovers this file automatically when it loads the plugin.

```
my-plugin/
  plugin.json             # Plugin metadata and configuration
  skills/
  .mcp.json              # MCP server definitions
  servers/
    db-server             # Server executable
  config.json             # Server configuration
```

In the `.mcp.json` file, MCP servers are defined in a top-level `mcpServers` object. Each server entry specifies a command, arguments, and optional environment variables:

```
{
  "mcpServers": {
    "plugin-database": {
      "command": "${CLAUDE_PLUGIN_ROOT}/servers/db-server",
      "args": ["--config", "${CLAUDE_PLUGIN_ROOT}/config.json"],
      "env": {
        "DB_PATH": "${CLAUDE_PLUGIN_ROOT}/data"
      }
    },
    "plugin-api": {
      "command": "npx",
      "args": ["@company/mcp-server", "--plugin-mode"],
      "cwd": "${CLAUDE_PLUGIN_ROOT}"
    }
  }
}
```

### Reference plugin paths in server configuration

For Claude-format plugins, use the `${CLAUDE_PLUGIN_ROOT}` token in MCP server fields to reference executables and files within the plugin directory. VS Code expands this token in the following fields:

* `command`: the executable path
* `args`: command-line arguments
* `cwd`: working directory
* `env`: environment variable values
* `envFile`: path to an environment file
* `url`: for HTTP-based MCP servers
* `headers`: HTTP header values

VS Code also injects a `CLAUDE_PLUGIN_ROOT` environment variable into the server process, so server code can access the plugin path at runtime.

### How plugin MCP servers interact with other servers

Plugin MCP servers appear alongside workspace and user-level MCP servers. You can manage them through the same tools:

* Select **Configure Tools** in the Chat view to see tools from all MCP servers, including plugin servers.
* Run **MCP: List Servers** from the Command Palette to view plugin servers alongside other servers.

Plugin MCP servers are implicitly trusted when you install the plugin. Unlike workspace MCP servers, they do not show a separate trust prompt at startup.

Disabling a plugin stops its MCP servers. Tools provided by the stopped servers are no longer available in chat.

## Hooks in plugins

Plugins can include [hooks](<https://code.visualstudio.com/docs/agent-customization/hooks>) that run shell commands at agent lifecycle points. Plugin-wide hooks work alongside your workspace and user-level hooks. When a plugin is enabled, these hooks fire in addition to any other hooks configured for the same event.

Note

Hooks are client-specific and are not a portable Agent Plugins 1.0 component type. In an Agent Plugins package, they come from the `com.github.copilot` namespace.

Organizations can distribute approved hooks through plugins. When managed settings specify `allowManagedHooksOnly: true`, plugin hooks run only when the plugin is force-enabled by a managed `enabledPlugins["plugin@marketplace"]: true` entry. User enablement alone is not sufficient, and `allowManagedHooksOnly` does not itself enable the plugin. See [Deploy hooks through managed plugins](<https://code.visualstudio.com/docs/enterprise/manage-ai-settings#_deploy-hooks-through-managed-plugins>).

Hook configuration and payloads depend on the session's harness. The event and matcher behavior described below applies to the Local harness. Start with [choosing a hook implementation](<https://code.visualstudio.com/docs/agent-customization/hooks#_choose-the-hook-implementation-for-your-session>) for Copilot, Claude, and Codex sessions.

### Hook file location

The hook file location depends on the plugin format:

| Plugin format | Hook file path |
| --- | --- |
| Agent Plugins 1.0 | `com.github.copilot/hooks/hooks.json` |
| Claude | `hooks/hooks.json` |
| Copilot | `hooks.json` (at the plugin root) |

VS Code auto-detects the plugin format and discovers the hook file automatically.

```
my-plugin/
  plugin.json
  com.github.copilot/
    hooks/
      hooks.json         # Hook configuration (Agent Plugins format)
  scripts/
    format.sh            # Hook script referenced by hooks.json
```

### Hook configuration format

For the Local harness, plugin hooks use the same base format as [workspace hooks](<https://code.visualstudio.com/docs/agent-customization/hooks#_local-hook-configuration-formats>). The Local parser accepts Claude hook configuration, including matcher syntax, but ignores matcher values. As a result, all nested commands for the event run in Local sessions.

**Flat format** (same as workspace hooks):

```
{
  "hooks": {
    "PostToolUse": [
      {
        "type": "command",
        "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
      }
    ]
  }
}
```

**Matcher format** (Claude compatibility syntax):

```
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Write|Edit",
        "hooks": [
          {
            "type": "command",
            "command": "${CLAUDE_PLUGIN_ROOT}/scripts/format.sh"
          }
        ]
      }
    ]
  }
}
```

The Local harness parses the `matcher` field for compatibility with Claude Code, but ignores matcher values. To filter Local hook behavior, check the event input inside the hook script.

### Reference plugin paths in hook commands

Use a plugin-root token in Local hook commands to reference bundled scripts and files without hardcoding the plugin's installation path.

| Plugin format | Token | Environment variable |
| --- | --- | --- |
| Claude | `${CLAUDE_PLUGIN_ROOT}` | `CLAUDE_PLUGIN_ROOT` |
| Legacy OpenPlugin | `${PLUGIN_ROOT}` | `PLUGIN_ROOT` |

VS Code expands the token to the plugin's absolute path in hook commands and `env` values. This includes the `command`, `bash`, `powershell`, and platform-specific command fields. Expanded command paths are shell-quoted, so plugin paths can contain spaces.

The hook process also receives the matching root environment variable. For example, a Node.js script can read `process.env.CLAUDE_PLUGIN_ROOT`. These references resolve to the new root when the plugin is discovered at a different location.

```
{
  "hooks": {
    "PreToolUse": [
      {
        "type": "command",
        "command": "${CLAUDE_PLUGIN_ROOT}/scripts/validate-tool.sh"
      }
    ]
  }
}
```

The same expansion applies to hooks in the frontmatter of plugin-provided custom agents. For example, a Claude-format plugin can contribute `agents/reviewer.md` that invokes its bundled `scripts/validate-tool.js` script:

```
---
name: Code reviewer
description: Review code with plugin-provided validation.
hooks:
  PreToolUse:
    - type: command
      command: "node ${CLAUDE_PLUGIN_ROOT}/scripts/validate-tool.js"
---

Review code for correctness and maintainability.
```

For legacy OpenPlugin plugins, use `${PLUGIN_ROOT}` in place of `${CLAUDE_PLUGIN_ROOT}`.

These [agent-scoped hooks](<https://code.visualstudio.com/docs/agent-customization/hooks#_agent-scoped-hooks-for-local>) are in Preview and require the Local harness, 


chat.useHooks

Open in VS Code
Open in VS Code Insiders
, and a trusted workspace. They run only while the contributing custom agent is active, including when it runs as a subagent.

### Supported hook events

In the Local harness, plugin hooks support the same events as workspace hooks: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PreCompact`, `SubagentStart`, `SubagentStop`, and `Stop`. See the [Local hooks reference](<https://code.visualstudio.com/docs/agents/reference/hooks-reference>) for event schemas.

### How plugin hooks interact with other hooks

Plugin-wide hooks run alongside workspace-level and user-level hooks. When multiple hooks target the same event, all of them execute. For `PreToolUse` hooks, the most restrictive permission decision across all hooks wins: `deny` overrides `ask`, which overrides `allow`.

Disabling a plugin also disables its hooks. Unless enterprise policy controls the plugin's enablement, you can enable or disable plugins globally or for a specific workspace from the Extensions view.

## Configure plugin marketplaces

By default, VS Code discovers plugins from the [copilot-plugins](<https://github.com/github/copilot-plugins>) and [awesome-copilot](<https://github.com/github/awesome-copilot/>). You can add additional marketplaces with the 


chat.plugins.marketplaces

Open in VS Code
Open in VS Code Insiders
 setting.

Marketplaces are Git repositories that contain plugin definitions. You can reference them in several formats:

* **Shorthand**: `owner/repo` for public GitHub repositories. For example, `anthropics/claude-code`. Append `#<ref>` to select a branch, tag, or full 40-character commit SHA.
* **HTTPS git remote**: a full URL ending in `.git`. For example, `https://github.com/anthropics/claude-code.git`.
* **SCP-style git remote**: SSH-style references. For example, `git@github.com:anthropics/claude-code.git`.
* **file URI**: a `file:///` path to a marketplace repository already cloned on disk.

For reproducible installations, use a full 40-character commit SHA, such as `owner/repo#<commit-sha>`. VS Code installs plugins from that exact revision. Branch and tag references use the revision they resolve to when the marketplace is fetched.

Private repositories are also supported. If a public lookup fails, VS Code falls back to cloning the repository directly.

When a marketplace index declares a plugin at a relative path, VS Code verifies the repository, resolved revision, and path before installation. Sources with a missing revision, an invalid path, or an ambiguous path match are rejected.

Marketplace plugins can also reference external package sources such as npm or PyPI packages. For the full marketplace plugin schema, see the [Claude Code plugin marketplace documentation](<https://code.claude.com/docs/en/plugin-marketplaces>).

```
// settings.json
"chat.plugins.marketplaces": [
    "anthropics/claude-code"
]
```

Note

Enterprise admins can centrally control which plugins and marketplaces are available to developers. For more information, see [Manage agent plugins and marketplaces](<https://code.visualstudio.com/docs/enterprise/manage-ai-settings#_manage-agent-plugins-and-marketplaces>).

## Cross-tool compatibility

Agent Plugins 1.0 is an open standard designed for cross-tool compatibility. A conformant plugin uses a root `plugin.json`, puts skills in `skills/`, and puts MCP server configuration in `mcp.json`. Compatible clients can discover the portable component types they support from the same package.

Agent Plugins can also include client-specific manifest data and files under a stable reverse-domain namespace. Clients ignore namespaces they don't implement, so client-specific capabilities don't prevent other clients from loading the portable components. VS Code reads custom agents, slash commands, rules, hooks, and automation path configuration from the `com.github.copilot` namespace. Other clients only use the capabilities in that namespace that they support.

For example:

```
my-plugin/
  plugin.json
  skills/
  mcp.json
  com.github.copilot/      # Read by VS Code and other Copilot clients
  com.example.client/      # Ignored by VS Code
```

VS Code continues to support existing Copilot, Claude, and legacy OpenPlugin formats. Plugins that don't declare the Agent Plugins schema continue to use their existing format-specific discovery rules.

For details about the portable format, see the [Agent Plugins specification](<https://github.com/agentplugins/agent-plugins-spec/blob/main/spec/1.0.0.md>). For other formats, see the [GitHub Copilot CLI plugin reference](<https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference>) and the [Claude Code plugin marketplace documentation](<https://code.claude.com/docs/en/plugin-marketplaces>).

## Troubleshooting

### Plugin does not appear after installation

* Confirm that agent plugins are enabled: check that 


  chat.plugins.enabled

  Open in VS Code
  Open in VS Code Insiders
   is set to `true`.
* Verify the plugin's `name` field follows the naming rules for its format. Agent Plugins 1.0 names use lowercase letters, numbers, hyphens, and periods. Legacy Copilot plugin names use lowercase letters, numbers, and hyphens. Slashes and colons aren't supported.
* Check that `plugin.json` is in a recognized location (see [Cross-tool compatibility](<#_cross-tool-compatibility>)).

### Skills from a plugin do not load

* Open the `SKILL.md` file and check the `name` field in the YAML frontmatter. The name must be plain kebab-case without namespace prefixes (for example, `test-runner`, not `myorg/test-runner`). Invalid names cause the skill to be silently skipped.
* Make sure the skill directory name matches the `name` field in the `SKILL.md` frontmatter.

### Plugin version does not update

* Bump the `version` field in `plugin.json` (and in the `marketplace.json` plugin entry, if applicable) before pushing changes.
* Run **Extensions: Check for Extension Updates** from the Command Palette to trigger an update check.

### Plugin installation fails after retry

Retry the installation. VS Code validates marketplace repository caches and replaces incomplete or invalid caches automatically.

If installation still fails, review the error for an invalid repository, revision, or plugin path. If the source is valid and retry continues to fail, run **Help: Report Issue**. Don't delete or modify the internal plugin cache manually.
