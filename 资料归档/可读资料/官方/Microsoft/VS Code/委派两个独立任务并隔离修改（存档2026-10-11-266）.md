---

当两个编码任务是独立的时，您可以将每个任务分配给 agent 并让两个任务同时运行，同时您查看其进度。单独的对话可以使指令集中，但它们不一定可以使文件更改分开。

在本指南中，您在自己的存储库中选择两项更改，在单独的 Git 工作树中运行它们，查看每个结果，然后集成并重新测试组合的更改。您首先定义任务及其接受标准，然后在整个工作流程中使用它们。不需要示例项目。

## 先决条件

要遵循本指南，您需要：

* Visual Studio Code 与 [AI 功能设置为 ](<https://code.visualstudio.com/docs/setup/copilot>)。
* 访问 [Agents 窗口 ](<https://code.visualstudio.com/docs/agents/run/agents-window>) 和 **Copilot** 会话目标。
* 一个本地 Git 存储库，至少有一次提交、一个工作开发环境和现有测试。
* 体验完成单个 agent 辅助任务。如果您是 agents 的新手，请从 [agents 快速入门 ](<https://code.visualstudio.com/docs/agents/quickstart>) 开始。

## 1。将工作分开

从待办事项中选择两个小更改，并将其标记为 **任务 A** 和 **任务 B**。每个任务都必须可以根据当前代码实现和测试，而无需等待其他任务。

为每项任务创建一份包含以下详细信息的摘要。您可以使用这些摘要来编写授权提示并查看结果。

|详情|记录什么|
| --- | --- |
|结果|您想要的可观察的更改，例如必须产生特定结果的输入。|
|允许的文件|agent可以编辑的实现和测试文件。|
|验收标准|证明任务完成的行为或测试结果。|
|要保留的行为|必须保持不变的现有行为。|
|超出范围|agent 必须避免的文件和更改，包括其他任务的实现。|
|验证|验证结果所需的现有测试命令和任何手动检查。|

例如，实用程序中的解析修复和不相关表单中的验证消息更改可能是独立的。这些是任务边界的示例，而不是您的项目所需的功能。选择您的存储库中重要的工作。

在继续之前比较两个摘要：

1. 检查每个任务是否都有一组不同的文件并且可以单独验证。
2. 识别两个任务都不应更改的共享文件，例如依赖项清单、API 合同、生成的文件和共享样式。
3. 检查任一任务是否依赖于另一个任务的输出。如果是这样，请选择另一对或先完成先决条件。

不同的文件并不总是意味着独立工作。如果这两个任务都需要新的 API 响应形状，请首先完成并验证共享更改。不要要求两个agents独立设计。

**检查您的任务定义：**您应该能够解释每项任务的成功是什么样子，而无需参考其他agent将要做的工作。

## 2。选择隔离

在发送提示之前选择 agents 可以进行更改的位置：

|工作安排|适当使用|文件隔离|
| --- | --- | --- |
|一个会话中的多个聊天|可以共享编辑的相关问题或协调工作。|聊天共享会话的文件夹或工作树，并且它们的更改一起显示。|
|使用同一文件夹的单独会话|只读调查与实施或一次运行一项任务。|对话是分开的，但两个会话可以编辑相同的工作文件。|
|单独的会话，每个会话都有一个新的工作树|您想要单独审查和集成的独立实施任务。|每个任务都有自己的工作文件和分支。整合仍然会产生冲突。|

对于本演练，使用 ** 两个单独的会话 **，每个会话都选择 ** 新工作树 **。创建另一个聊天或分叉对话并不能替代创建另一个工作树。

注意事项

工作树隔离工作文件，而不是 agent 对您的计算机或外部服务的访问。 Copilot 工作树会话使用 ** 允许所有 **，这会跳过工具批准提示。使用受信任的存储库并在继续之前查看 [ 权限和沙箱控制 ](<https://code.visualstudio.com/docs/agents/run/approvals>)。如果您需要手动批准，请一次使用一个文件夹会话。

有关可用选项的详细信息，请参阅[选择代码隔离](<https://code.visualstudio.com/docs/agents/run/agent-harnesses#_choose-code-isolation>)。

## 3。准备和委托

从相同的已知良好提交开始这两项任务，以便您可以根据相同的基线检查每个结果。

1. 在您的主工作区中，提交这两个任务所需的更改。提交或隐藏不相关的工作，包括要保留的未跟踪文件。确认工作树是干净的：

   ```
   git status --short
   ```

没有输出意味着没有要考虑的跟踪或未跟踪的更改。不包括被忽略的文件。
2. 为两个任务区域运行现有测试。在开始之前解决基线故障。
3. 在主编辑器工作区中，查看您希望这两个任务从中启动的分支。运行 **Git：从命令面板创建分支 ** 并输入 `integrate-agent-tasks` 或其他未使用的分支名称。这将创建并检查组合更改的分支。

使用此集成分支作为两个工作树会话的基础。 **合并更改**操作将每个会话合并回其配置的基本分支，而不是稍后选择的任意目标。
4. 记录集成分支名称和开始提交：

   ```
   git branch --show-current
   git rev-parse HEAD
   ```

在您的主工作区中保持集成分支处于签出状态。在到达集成步骤之前，请勿对其添加更改。
5. 从标题栏中的**在Agents**中打开按钮打开Agents窗口。选择**新建**，选择本地项目文件夹，然后选择**Copilot**作为**会话目标**。
6. 选择 **New Worktree** 并选择您记录的集成分支作为基础分支。
7. 填写任务 A 简介中的以下提示模板，然后提交。将每个尖括号占位符替换为任务的详细信息和存储库的命令。对于依赖项设置，请使用项目的正常过程进行新的签出。

   ```
   Implement <task-name>.
   Outcome: <expected-outcome>

   Limit edits to <allowed-implementation-and-test-files>.
   Acceptance criteria: <acceptance-criteria>
   Preserve this existing behavior: <behavior-to-preserve>
   Out of scope: <files-and-changes-to-avoid>
   Add or update tests for the acceptance criteria.
   If the task requires edits outside this scope, stop and explain the dependency.

   Use <dependency-setup-command> if this worktree needs dependencies, then run <validation-commands>.
   Do not commit, merge, push, deploy, or modify external services.
   Finish with the changed files, validation commands and results, any manual checks still needed, and unresolved concerns.
   ```
8. 再次选择 **New** 为同一项目创建单独的会话。选择相同的会话目标和集成分支作为基础，然后再次选择**新建工作树**。不要在第一个会话中添加聊天。
9. 填写任务 B 简介中的模板的第二个副本，并将其提交到新会话。使用任务 B 的结果、范围和验证命令，而不是任务 A 的结果、范围和验证命令。保持相同的基本提交。

工作树不包含主工作区中未提交的更改。默认情况下，Git 忽略的文件（例如已安装的依赖项和本地配置）也不存在。在每个工作树中使用项目的正常设置过程，并仅提供 agent 可以安全访问的配置。不要复制生产凭据。了解有关 [ 在创建工作树时包含文件的更多信息 ](<https://code.visualstudio.com/docs/sourcecontrol/branches-worktrees#_include-files-when-creating-a-worktree>)。

**检查您的设置：**确认两个会话报告不同的工作树路径和分支，但起始提交相同。在主工作区中运行 `git worktree list` 以检查路径和分支。如果两个任务使用相同的目录，请停止它们并在继续之前更正隔离。

## 4。监控这两个任务

使用会话列表来跟踪每个任务的状态。选择一个会话以检查其对话和 **更改** 视图。在发送反馈或打开终端之前确认哪个会话处于活动状态。

提示

您可以在Agents窗口中并排查看多个会话，以轻松比较它们的进度和变化。拖放会话以根据需要进行排列。

在第一次有意义的更改后检查每个任务：

* 是否只编辑约定的文件？
* 是否符合验收标准？
* 它是在等待您的答复、所需的确认还是正在运行的命令？
* 在 agent 验证更改之前设置或测试是否失败？

如果任务开始更改其概要之外的文件，请向该任务的会话发送重点更正。将占位符替换为特定边界和您需要的证据：

```
Keep <out-of-scope-files-or-behavior> unchanged. Stop expanding the scope. Explain why <allowed-files> are insufficient for <expected-outcome>, and wait for my decision before editing more files.
```

如果任一任务发现共享依赖项，请暂停受影响的工作。决定是首先完成该依赖项，还是将共享更改分配给一项任务，然后运行依赖项工作。

单独的工作树仍然可以共享端口、数据库和其他外部资源。使用单独的测试资源或一次运行一项检查。对于漂移或重复失败的 agent，请按照 [让 agent 回到正轨 ](<https://code.visualstudio.com/docs/agents/guides/get-agent-back-on-track>)。

## 5。单独审查每个结果

完成的回复是交接以供审核，而不是证明任务正确。在合并任务 A 和任务 B 之前，先独立审查它们。

1. 选择任务的会话并打开 **更改**。检查完整的分支差异，包括添加的测试和新文件，而不仅仅是最新的响应。
2. 将更改与任务简介进行比较。检查是否满足每个验收标准，保留所需的现有行为，并且没有不相关的编辑。
3. 检查测试输出。验证预期的测试是否已运行，并且设置失败或跳过的测试未报告为成功。
4. 运行验证命令并根据该会话工作树中的摘要完成手动检查。使用会话标题栏中的**打开终端**，并在运行命令之前确认其工作目录。
5. 将修订发送到同一会话，然后查看修订后的差异并重新运行受影响的检查。
6. 结果准备就绪后，查看工作树中的 `git status --short` 是否有意外或未跟踪的文件。在选择 **提交更改** 之前，单独保留任何不相关的工作，这会将所有当前更改提交到会话分支。
7. 记录会话分支名称并提交。保持会话可用，直到集成得到验证。

检查测试中的预期结果，而不仅仅是测试是否通过。这些断言应该展示任务简介中的结果，而不是重复实施过程中的假设。

有关完整的差异和反馈过程，请参阅[审查agent更改](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_review-agent-changes>)。

## 6。整合并重新测试

使用 Agents 窗口中的 ** 合并更改 ** 将每个已审核的会话分支合并到主工作区中的集成分支中。将任务提交分开，以便您可以在合并的历史记录中识别每个结果。

注意事项

**合并更改**可用于有更改且会话分支没有关联拉取请求的工作树会话。它在合并之前提交任何未提交的工作树更改。即使您已经提交了任务结果，也要先查看所有更改。如果会话分支有拉取请求，请改用该拉取请求的审核和合并工作流程。

如果任一合并失败，请先按照 [ 恢复步骤 ](<#_if-a-merge-fails>) 操作，然后再继续。

1. 确认两个会话都已停止编辑，两个结果均已提交，并且您的主要工作树是干净的。
2. 在主编辑器工作区中，确认集成分支已签出。 **合并更改**要求父存储库位于会话的配置基础分支上。如果您切换了分支，请先切换回来，然后再继续。
3. 在Agents窗口中，选择任务A的会话。打开**更改**并选择**分支更改**。
4. 选择**合并更改**并确认。等待合并完成后再继续。
5. 返回主工作区并在集成分支上运行任务 A 的验证命令。如果它们失败，请解决故障并在添加任务 B 之前提交任何修复。确认工作树再次干净。
6. 在Agents窗口中选择任务B的会话。打开**更改**，选择**分支更改**，然后选择**合并更改**。确认并等待合并完成。
7. 在主工作区中，根据您记录的起始提交检查组合差异。确认两个已审核的更改均存在，并且冲突解决方案未删除任务的行为或测试。
8. 在组合分支上运行目标测试集和项目的相关集成检查。包括项目贡献工作流程所需的现有构建、类型检查或 lint 检查。
9. 使用任务简介中的手动检查，从目标工作区练习这两种更改的行为：

   * 确认任务 A 的预期结果以及任务 B 的更改。
   * 通过任务 A 的更改来确认任务 B 的预期结果。
   * 检查两个简报都要求您保留的现有行为。

通过每个工作树中的测试并不能证明组合的更改有效。如果集成导致失败，请在存在两个更改的目标分支上进行调查。提交任何后续修复并重新运行受影响的检查。

### 如果合并失败

重试之前请阅读错误。如果主工作区有未提交的更改或签出错误的分支，请首先更正该状态。

如果 Git 报告冲突，请打开主工作区，检查两个版本，并保留两个任务的要求。不要全盘接受某一方以使冲突消失。 [解决冲突](<https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts>)并在运行测试或开始下一次合并之前完成该合并。即使集成未完成，失败的合并也可能导致会话的工作被提交。

如果您喜欢手动合并，请在主编辑器工作区中使用 **Git：合并分支 ** 或从其终端运行 `git merge --no-ff <session-branch>`，并签出集成分支。使用实际审核的会话分支名称，一次集成一项任务，并遵循相同的验证步骤。不要同时通过其他集成操作应用更改。

## 7。完成工作流程

在将任一会话标记为完成之前，请确认：

* 每项任务都保持在其商定的范围内，或者您明确批准了范围变更。
* 您分别审查并提交了每个结果。
* 两个结果都出现在预期的目标分支上。
* 综合测试和手动检查均通过。
* 任何集成修复均已提交。

Continue 与您团队的正常拉取请求或审核流程。然后才将会话标记为已完成。当会话或其工作树包含尚未保留的工作时，请勿删除它。

现在，您拥有一项由两项独立审核的任务组合而成的经过测试的更改，并且保留了每项任务的历史记录。

---

When two coding tasks are independent, you can assign each to an agent and let both run while you review their progress. Separate conversations keep instructions focused, but they don't necessarily keep file changes separate.

In this guide, you choose two changes in your own repository, run them in separate Git worktrees, review each result, and integrate and retest the combined change. You define the tasks and their acceptance criteria first, then use them throughout the workflow. No sample project is required.

## Prerequisites

To follow this guide, you need:

* Visual Studio Code with [AI features set up](<https://code.visualstudio.com/docs/setup/copilot>).
* Access to the [Agents window](<https://code.visualstudio.com/docs/agents/run/agents-window>) and the **Copilot** session target.
* A local Git repository with at least one commit, a working development environment, and existing tests.
* Experience completing a single agent-assisted task. If you're new to agents, start with the [agents quickstart](<https://code.visualstudio.com/docs/agents/quickstart>).

## 1. Separate the work

Choose two small changes from your backlog and label them **task A** and **task B**. Each task must be implementable and testable against the current code, without waiting for the other task.

Create a brief for each task with the following details. You use these briefs to write the delegation prompts and review the results.

| Detail | What to record |
| --- | --- |
| Outcome | The observable change you want, such as an input that must produce a particular result. |
| Allowed files | The implementation and test files the agent can edit. |
| Acceptance criteria | The behavior or test results that prove the task is complete. |
| Behavior to preserve | Existing behavior that must remain unchanged. |
| Out of scope | Files and changes the agent must avoid, including the other task's implementation. |
| Validation | Existing test commands and any manual checks needed to verify the result. |

For example, a parsing fix in a utility and a validation-message change in an unrelated form might be independent. These are examples of task boundaries, not features your project needs. Choose work that matters in your repository.

Compare the two briefs before you continue:

1. Check that each task has a distinct set of files and can be validated on its own.
2. Identify shared files that neither task should change, such as dependency manifests, API contracts, generated files, and shared styles.
3. Check whether either task depends on the other's output. If so, choose a different pair or complete the prerequisite first.

Different files don't always mean independent work. If both tasks need a new API response shape, complete and validate that shared change first. Don't ask two agents to design it independently.

**Check your task definitions:** You should be able to explain what success looks like for each task without referring to work the other agent will do.

## 2. Choose isolation

Choose where the agents can make changes before you send the prompts:

| Work arrangement | Appropriate use | File isolation |
| --- | --- | --- |
| Multiple chats in one session | Related questions or coordinated work that can share edits. | Chats share the session's folder or worktree, and their changes appear together. |
| Separate sessions using the same folder | Read-only investigation alongside implementation, or tasks you run one at a time. | Conversations are separate, but both sessions can edit the same working files. |
| Separate sessions, each with a new worktree | Independent implementation tasks you want to review and integrate separately. | Each task has its own working files and branch. Integration can still produce conflicts. |

For this walkthrough, use **two separate sessions**, each with **New Worktree** selected. Creating another chat or forking a conversation is not a substitute for creating another worktree.

Caution

Worktrees isolate working files, not the agent's access to your machine or external services. Copilot worktree sessions use **Allow all**, which skips tool approval prompts. Use a trusted repository and review the [permission and sandboxing controls](<https://code.visualstudio.com/docs/agents/run/approvals>) before proceeding. If you require manual approvals, use folder sessions one at a time instead.

For details about the available choices, see [choose code isolation](<https://code.visualstudio.com/docs/agents/run/agent-harnesses#_choose-code-isolation>).

## 3. Prepare and delegate

Start both tasks from the same known-good commit so that you can review each result against the same baseline.

1. In your primary workspace, commit the changes that both tasks need. Commit or stash unrelated work, including untracked files you want to preserve. Confirm that the working tree is clean:

   ```
   git status --short
   ```

   No output means there are no tracked or untracked changes to account for. Ignored files aren't included.
2. Run the existing tests for both task areas. Resolve baseline failures before you start.
3. In the primary editor workspace, check out the branch you want both tasks to start from. Run **Git: Create Branch** from the Command Palette and enter `integrate-agent-tasks`, or another unused branch name. This creates and checks out a branch for the combined change.

   Use this integration branch as the base for both worktree sessions. The **Merge Changes** action merges each session back into its configured base branch, not an arbitrary destination chosen later.
4. Record the integration branch name and starting commit:

   ```
   git branch --show-current
   git rev-parse HEAD
   ```

   Keep the integration branch checked out in your primary workspace. Don't add changes to it until you reach the integration steps.
5. Open the Agents window from the **Open in Agents** button in the title bar. Select **New**, select your local project folder, and choose **Copilot** as the **Session Target**.
6. Select **New Worktree** and choose the integration branch you recorded as the base branch.
7. Fill in the following prompt template from task A's brief, then submit it. Replace every angle-bracket placeholder with the task's details and your repository's commands. For dependency setup, use your project's normal procedure for a new checkout.

   ```
   Implement <task-name>.
   Outcome: <expected-outcome>

   Limit edits to <allowed-implementation-and-test-files>.
   Acceptance criteria: <acceptance-criteria>
   Preserve this existing behavior: <behavior-to-preserve>
   Out of scope: <files-and-changes-to-avoid>
   Add or update tests for the acceptance criteria.
   If the task requires edits outside this scope, stop and explain the dependency.

   Use <dependency-setup-command> if this worktree needs dependencies, then run <validation-commands>.
   Do not commit, merge, push, deploy, or modify external services.
   Finish with the changed files, validation commands and results, any manual checks still needed, and unresolved concerns.
   ```
8. Select **New** again to create a separate session for the same project. Choose the same session target and integration branch as the base, and select **New Worktree** again. Don't add a chat to the first session.
9. Fill in a second copy of the template from task B's brief and submit it to the new session. Use task B's outcome, scope, and validation commands, not task A's. Keep the same base commit.

Worktrees don't include uncommitted changes from your primary workspace. Git-ignored files, such as installed dependencies and local configuration, are also absent by default. Use your project's normal setup procedure in each worktree, and provide only configuration that is safe for the agent to access. Don't copy production credentials. Learn more about [including files when creating a worktree](<https://code.visualstudio.com/docs/sourcecontrol/branches-worktrees#_include-files-when-creating-a-worktree>).

**Check your setup:** Confirm that the two sessions report different worktree paths and branches, but the same starting commit. Run `git worktree list` in your primary workspace to check the paths and branches. If both tasks are using the same directory, stop them and correct the isolation before they continue.

## 4. Monitor both tasks

Use the sessions list to track each task's status. Select a session to inspect its conversation and **Changes** view. Confirm which session is active before you send feedback or open a terminal.

Tip

You can view multiple sessions side by side in the Agents window to easily compare their progress and changes. Drag and drop sessions to arrange them as needed.

Check each task after its first meaningful change:

* Is it editing only the agreed files?
* Is it following the acceptance criteria?
* Is it waiting for your answer, a required confirmation, or a running command?
* Did setup or testing fail before the agent could validate the change?

If a task starts changing files outside its brief, send a focused correction to that task's session. Replace the placeholders with the specific boundary and the evidence you need:

```
Keep <out-of-scope-files-or-behavior> unchanged. Stop expanding the scope. Explain why <allowed-files> are insufficient for <expected-outcome>, and wait for my decision before editing more files.
```

If either task discovers a shared dependency, pause the affected work. Decide whether to complete that dependency first or assign the shared change to one task and run the dependent work afterward.

Separate worktrees can still share ports, databases, and other external resources. Use separate test resources or run those checks one at a time. For an agent that drifts or repeats failures, follow [Get an agent back on track](<https://code.visualstudio.com/docs/agents/guides/get-agent-back-on-track>).

## 5. Review each result separately

A completed response is a handoff for review, not proof that the task is correct. Review task A and task B independently before combining them.

1. Select the task's session and open **Changes**. Inspect the full branch diff, including added tests and new files, rather than only the most recent response.
2. Compare the changes with the task's brief. Check that every acceptance criterion is met, the required existing behavior is preserved, and there are no unrelated edits.
3. Inspect the test output. Verify that the expected tests ran and that a setup failure or skipped test wasn't reported as success.
4. Run the validation commands and complete the manual checks from the brief in that session's worktree. Use **Open Terminal** in the session title bar and confirm its working directory before running commands.
5. Send revisions to the same session, then review the revised diff and rerun the affected checks.
6. When the result is ready, review `git status --short` in the worktree for unintended or untracked files. Preserve any unrelated work separately before you select **Commit Changes**, which commits all current changes to the session branch.
7. Record the session branch name and commit. Keep the session available until integration is validated.

Inspect the expected results in the tests, not only whether the tests pass. The assertions should demonstrate the outcome in the task's brief, rather than repeat assumptions from the implementation.

For the full diff and feedback procedures, see [review agent changes](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_review-agent-changes>).

## 6. Integrate and retest

Use **Merge Changes** in the Agents window to merge each reviewed session branch into the integration branch in your primary workspace. Keep the task commits separate so that you can identify each result in the combined history.

Note

**Merge Changes** is available for worktree sessions with changes and no associated pull request for the session branch. It commits any uncommitted worktree changes before merging. Review all changes first, even if you already committed the task's result. If the session branch has a pull request, use that pull request's review and merge workflow instead.

If either merge fails, follow [the recovery steps](<#_if-a-merge-fails>) before continuing.

1. Confirm that both sessions have stopped editing, that both results are committed, and that your primary working tree is clean.
2. In the primary editor workspace, confirm that the integration branch is checked out. **Merge Changes** requires the parent repository to be on the session's configured base branch. If you switched branches, switch back before proceeding.
3. In the Agents window, select task A's session. Open **Changes** and select **Branch Changes**.
4. Select **Merge Changes** and confirm. Wait for the merge to complete before you continue.
5. Return to the primary workspace and run task A's validation commands on the integration branch. If they fail, resolve the failure and commit any fix before you add task B. Confirm that the working tree is clean again.
6. Select task B's session in the Agents window. Open **Changes**, select **Branch Changes**, and select **Merge Changes**. Confirm and wait for the merge to complete.
7. In the primary workspace, review the combined diff against the starting commit you recorded. Confirm that both reviewed changes are present and that conflict resolution hasn't removed either task's behavior or tests.
8. Run both targeted test sets and the project's relevant integration checks on the combined branch. Include the existing build, type check, or lint checks required by your project's contribution workflow.
9. Exercise both changed behaviors from the destination workspace, using the manual checks in the task briefs:

   * Confirm task A's expected outcome with task B's changes present.
   * Confirm task B's expected outcome with task A's changes present.
   * Check the existing behavior that both briefs require you to preserve.

Passing tests in each worktree doesn't prove the combined change works. If integration introduces a failure, investigate it on the destination branch where both changes are present. Commit any follow-up fix and rerun the affected checks.

### If a merge fails

Read the error before you retry. If the primary workspace has uncommitted changes or the wrong branch checked out, correct that state first.

If Git reports conflicts, open the primary workspace, inspect both versions, and preserve both tasks' requirements. Don't accept one side wholesale to make the conflict disappear. [Resolve the conflicts](<https://code.visualstudio.com/docs/sourcecontrol/merge-conflicts>) and complete that merge before you run tests or start the next merge. A failed merge can leave the session's work committed even though integration didn't complete.

If you prefer to merge manually, use **Git: Merge Branch** in the primary editor workspace or run `git merge --no-ff <session-branch>` from its terminal, with the integration branch checked out. Use the actual reviewed session branch name, integrate one task at a time, and follow the same validation steps. Don't also apply the changes through another integration action.

## 7. Finish the workflow

Before you mark either session done, confirm:

* Each task stayed within its agreed scope, or you explicitly approved a scope change.
* You reviewed and committed each result separately.
* Both results are present on the intended destination branch.
* The combined tests and manual checks pass.
* Any integration fixes are committed.

Continue with your team's normal pull request or review process. Only then mark the sessions done. Don't delete a session or its worktree while it contains work that hasn't been preserved.

You now have one tested change assembled from two independently reviewed tasks, with each task's history retained.
