---

AI agent 可能会误解目标、重复不成功的操作、更改比预期更多的文件，或者忘记先前的决定。一旦发现不匹配，请立即干预。早期更正可以保留有用的工作并减少需要检查或撤消的更改数量。

本指南可帮助您选择破坏性最小的恢复操作。您将了解如何重定向正在运行的请求、更正已完成的工作、恢复不需要的更改、重置对话上下文以及诊断重复的故障。

## 选择恢复操作

从您观察到的症状开始：

|症状|恢复动作|
| --- | --- |
|agent 显示空闲或阻塞。|[检查当前状态](<#_assess-the-current-state>)是否有待处理的问题、批准请求或正在运行的终端命令。|
|agent仍在运行，当前的方法是安全的，但不正确。|[通过重点修正引导请求](<#_redirect-a-running-request>)。|
|agent 即将执行不安全、破坏性或不相关的操作。|[立即停止请求](<#_redirect-a-running-request>)并说明不得执行的操作。|
|响应已完成，大部分工作都是有用的。|[发送重点跟进](<#_correct-a-completed-response>)，以识别特定的不匹配情况。|
|较早的一个模棱两可的提示导致agent采取了错误的方法。|[编辑之前的请求](<#_correct-a-completed-response>)并重新发送。|
|已知点之后的文件更改是不需要的。|[恢复检查点](<#_recover-unwanted-changes>)。|
|您想要在不丢失当前对话的情况下比较另一种方法。|[分叉对话](<#_reset-conversation-context>)。|
|对话包含太多不相关或冲突的上下文。|[压缩上下文或启动新会话](<#_reset-conversation-context>)。|
|agent按照您的指示操作，但反复遇到相同的错误。|[在重试之前诊断故障](<#_diagnose-repeated-failures>)。|

注意事项

如果 agent 即将运行破坏性命令、部署更改、暴露敏感信息或修改外部服务，请在进一步调查之前停止该请求。

## 评估当前状态

在您要求 agent 继续之前，请确定发生了什么以及您想要保留的内容：

1. 检查agent是否正在等待答复或批准，或者正在跟踪仍在运行的终端命令。
2. 找到 agent 的工作与您的意图相悖的最早点。
3. 查看更改的文件、最近的工具调用、终端输出和错误消息。
4. 将正确的工作与需要修订或删除的更改分开。
5. 检查已完成的操作是否仅影响工作区文件，或者还影响终端、网络、部署或外部服务。
6. 写下 agent 错过的预期结果、约束和验证。

在你的修正中使用这些事实。避免诸如“重试”或“修复它”之类的提示，这些提示不会告诉 agent 需要更改什么。

## 重定向正在运行的请求

当请求运行时，在聊天输入框中输入更正。输入消息后，**发送**按钮菜单将变为可用。打开菜单并选择新消息应如何影响当前请求：

* 当当前操作安全时，选择 ** 使用消息转向 **，但 agent 需要不同的方法。 agent 完成活动工具调用，停止当前响应，并处理您的更正。
* 当agent不应继续当前请求时，选择**停止并发送**。 VS Code取消请求并立即发送您的新消息。

例如，在 agent 进行更多编辑之前操纵它：

```
Do not change the database schema or add dependencies. Stop editing after the current tool call. Explain why the existing API tests fail, then propose a fix limited to src/api. Wait for my approval before changing files.
```

如果某个操作存在直接风险，请停止该操作并要求 agent 报告当前状态：

```
Stop. Do not run deployment commands or modify external services. Summarize the commands and tool calls that already completed, list their effects, and wait for further instructions.
```

引导或停止请求不会撤消已完成的操作。如果需要回退工作区文件，请查看当前更改并[恢复检查点](<#_recover-unwanted-changes>)。

了解有关 [在请求运行时发送消息的详细信息 ](<https://code.visualstudio.com/docs/chat/chat-overview#_send-messages-while-a-request-is-running>)。

## 更正已完成的回复

回复完成后，选择保留多少对话和工作。

### 发送有针对性的后续行动

当总体方法正确时，保留当前工作。描述观察到的不匹配、预期结果、修正的边界以及如何验证它：

```
The new test passes, but the existing pagination test now fails because the response shape changed. Keep the public API unchanged. Update only the pagination calculation, run the complete API test suite, and report the test results.
```

如果agent重复相同的不成功操作，则需要在再次尝试之前进行分析：

```
Do not rerun the unchanged command. Summarize the first error, identify which assumption the error disproves, and propose two different recovery options. Do not edit files or run commands until I choose an option.
```

### 编辑较早的请求

当以前的请求的措辞引入了错误的要求或省略了重要的限制时，请编辑该请求。当您编辑并重新发送请求时，VS Code 会恢复该请求和所有后续请求中的工作区文件更改，然后处理修改后的提示。

在编辑请求之前，请查看受影响的更改，以便了解哪些工作将被删除。选择对话中的提示，修改其文本，然后重新发送。详细了解[编辑之前的聊天请求](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_edit-a-previous-chat-request>)。

## 恢复不需要的更改

当您可以识别 agent 的工作区更改出错之前的最后一个请求时，请使用检查点。恢复检查点会将受影响的工作区文件和聊天历史记录返回到该点。

在受支持的聊天会话中，检查点默认启用，并在处理每个请求之前自动创建。在 agent 进行更改之前发送建立检查点的请求。您无需手动创建一个。

恢复之前：

1. 查看已更改的文件以查找您计划删除的请求。
2. 检查工作区之外已完成的操作。
3. 记录修改后的请求所需的任何错误输出或决策。

恢复后，使用缺少的约束和预期验证重新陈述任务。

重要

检查点不会反转终端命令、网络请求、部署或对外部服务的更改。使用 Git 或外部系统的恢复控件来扭转这些影响。检查点是临时的，不会取代 Git 版本控制。

有关完整过程和范围，请参阅[恢复检查点](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_restore-a-checkpoint>)。

## 重置对话上下文

恢复有时需要更改对话而不是代码。选择与上下文仍然有用的程度相匹配的选项。

### 压缩当前对话

当您想要继续相同的任务但对话包含旧的探索、重复的输出或不再重要的细节时，请使用 `/compact`。告诉 agent 要保留哪些事实：

```
/compact Retain the approved API contract, the root cause of the pagination failure, the files changed so far, and the required test commands. Discard superseded approaches and repeated command output.
```

压缩总结了早期的历史。它不会更改工作区文件。详细了解 [ 压缩对话上下文 ](<https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions#_compact-conversation-context>)。

### 分叉对话

当您想在保留原始对话的同时探索不同的方法时，从检查点分叉。如果替代方法没有用，您可以比较结果并返回到原始会话。

分叉创建单独的对话历史记录，但并不总是提供单独的文件。根据会话类型，分支可能共享相同的文件夹或 Git 工作树。当两种方法必须独立修改文件时，请使用单独的工作树隔离会话。了解有关 [ 分叉聊天会话 ](<https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions#_fork-a-chat-session>) 的更多信息。

### 开始新会话

在以下情况下开始新会话：

* 目标变成了不同的任务。
* 早期的说明与当前的要求相冲突。
* 反复修正，难以确定权威决策。
* 您希望 agent 调查当前工作区而不继承先前的假设。

启动新会话不会撤消文件更改。首先查看或恢复工作区，然后提供包含当前状态、接受的决策、约束和验证标准的简洁提示。

## 诊断重复故障

如果 agent 理解任务但无法取得进展，请停止自动重试并调查潜在的故障。

1. 要求 agent 报告失败的确切命令或工具、第一个错误以及用于诊断错误的证据。
2. 验证先决条件，例如工作目录、安装的依赖项、所需的服务、身份验证和权限。
3. 要求提供不会重复失败操作的恢复选项。
4. 如果会话的调试日志记录处于活动状态，则当您需要了解被忽略的指令、意外的工具行为或缓慢的响应时，请使用 `/troubleshoot` 来分析捕获的日志。
5. 要进行更深入的检查，请使用 Agent 调试日志面板（预览）来查看模型请求、工具调用、提示文件发现和错误。

对于连接、扩展、自定义和 MCP 服务器问题，请遵循 [AI 故障排除过程 ](<https://code.visualstudio.com/docs/agents/agent-troubleshooting/troubleshooting>)。要检查 agent 交互，请参阅[调试聊天交互](<https://code.visualstudio.com/docs/agents/agent-troubleshooting/chat-debug-view>)。

## 防止agent漂移

通过使预期结果可观察来减少恢复的需要：

* 定义任务边界、约束以及不得更改的文件或系统。
* 包括验收标准、预期输出或测试命令。
* 当任务跨越多个组成部分或包含重大风险时，在实施之前要求制定计划。
* 在进行重大更改之前，使用 Git 提交一个已知良好的起点。
* 对于不熟悉的存储库、工具和工作流程，请保持选择**手动权限**。
* 查看第一个有意义的结果，而不是等到整个任务完成。
* 当您切换到不相关的任务时开始新的会话。

---

An AI agent might misunderstand the goal, repeat an unsuccessful action, change more files than expected, or lose track of an earlier decision. Intervene as soon as you recognize a mismatch. Early corrections preserve useful work and reduce the number of changes you need to review or undo.

This guide helps you choose the least disruptive recovery action. You learn how to redirect a running request, correct completed work, recover unwanted changes, reset conversation context, and diagnose repeated failures.

## Choose a recovery action

Start with the symptom you observe:

| Symptom | Recovery action |
| --- | --- |
| The agent appears idle or blocked. | [Check the current state](<#_assess-the-current-state>) for a pending question, approval request, or running terminal command. |
| The agent is still running, and the current approach is safe but incorrect. | [Steer the request](<#_redirect-a-running-request>) with a focused correction. |
| The agent is about to perform an unsafe, destructive, or irrelevant action. | [Stop the request](<#_redirect-a-running-request>) immediately and state what it must not do. |
| The response is complete, and most of the work is useful. | [Send a focused follow-up](<#_correct-a-completed-response>) that identifies the specific mismatch. |
| An ambiguous earlier prompt caused the agent to take the wrong approach. | [Edit the earlier request](<#_correct-a-completed-response>) and resend it. |
| File changes after a known point are unwanted. | [Restore a checkpoint](<#_recover-unwanted-changes>). |
| You want to compare another approach without losing the current conversation. | [Fork the conversation](<#_reset-conversation-context>). |
| The conversation contains too much irrelevant or conflicting context. | [Compact the context or start a new session](<#_reset-conversation-context>). |
| The agent follows your instructions but repeatedly encounters the same error. | [Diagnose the failure](<#_diagnose-repeated-failures>) before it retries. |

Caution

If the agent is about to run a destructive command, deploy a change, expose sensitive information, or modify an external service, stop the request before you investigate further.

## Assess the current state

Before you ask the agent to continue, identify what happened and what you want to preserve:

1. Check whether the agent is waiting for an answer or approval, or is tracking a terminal command that is still running.
2. Find the earliest point where the agent's work diverged from your intent.
3. Review the changed files, recent tool calls, terminal output, and error messages.
4. Separate correct work from changes that need revision or removal.
5. Check whether completed actions affected only workspace files or also affected the terminal, network, deployments, or external services.
6. Write down the expected result, constraints, and validation that the agent missed.

Use these facts in your correction. Avoid prompts such as "try again" or "fix it," which don't tell the agent what needs to change.

## Redirect a running request

While a request is running, type your correction in the chat input box. The **Send** button menu becomes available after you type a message. Open the menu and choose how the new message should affect the current request:

* Select **Steer with Message** when the current actions are safe, but the agent needs a different approach. The agent finishes the active tool call, stops the current response, and processes your correction.
* Select **Stop and Send** when the agent should not continue the current request. VS Code cancels the request and sends your new message immediately.

For example, steer an agent before it makes more edits:

```
Do not change the database schema or add dependencies. Stop editing after the current tool call. Explain why the existing API tests fail, then propose a fix limited to src/api. Wait for my approval before changing files.
```

If an action presents an immediate risk, stop it and ask the agent to report the current state:

```
Stop. Do not run deployment commands or modify external services. Summarize the commands and tool calls that already completed, list their effects, and wait for further instructions.
```

Steering or stopping a request does not undo actions that already completed. Review the current changes and [restore a checkpoint](<#_recover-unwanted-changes>) if you need to rewind workspace files.

Learn more about [sending messages while a request is running](<https://code.visualstudio.com/docs/chat/chat-overview#_send-messages-while-a-request-is-running>).

## Correct a completed response

When the response is complete, choose how much of the conversation and work to keep.

### Send a focused follow-up

Keep the current work when the overall approach is correct. Describe the observed mismatch, the expected result, the boundaries of the correction, and how to verify it:

```
The new test passes, but the existing pagination test now fails because the response shape changed. Keep the public API unchanged. Update only the pagination calculation, run the complete API test suite, and report the test results.
```

If the agent repeats the same unsuccessful action, require analysis before another attempt:

```
Do not rerun the unchanged command. Summarize the first error, identify which assumption the error disproves, and propose two different recovery options. Do not edit files or run commands until I choose an option.
```

### Edit an earlier request

Edit a previous request when its wording introduced the wrong requirement or omitted an important constraint. When you edit and resend a request, VS Code reverts workspace file changes from that request and all subsequent requests, then processes the revised prompt.

Before you edit the request, review the affected changes so you understand which work will be removed. Select the prompt in the conversation, modify its text, and resend it. Learn more about [editing a previous chat request](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_edit-a-previous-chat-request>).

## Recover unwanted changes

Use a checkpoint when you can identify the last request before the agent's workspace changes went wrong. Restoring the checkpoint returns affected workspace files and chat history to that point.

In supported chat sessions, checkpoints are enabled by default and created automatically before each request is processed. Send a request to establish a checkpoint before the agent makes changes. You don't need to create one manually.

Before you restore:

1. Review the changed files for the requests you plan to remove.
2. Check for completed actions outside the workspace.
3. Record any error output or decisions that you need for the revised request.

After you restore, restate the task with the missing constraints and expected validation.

Important

Checkpoints don't reverse terminal commands, network requests, deployments, or changes to external services. Use Git or the external system's recovery controls to reverse those effects. Checkpoints are temporary and don't replace Git version control.

For the complete procedure and scope, see [restore a checkpoint](<https://code.visualstudio.com/docs/agents/run/review-code-edits#_restore-a-checkpoint>).

## Reset conversation context

Recovery sometimes requires changing the conversation rather than the code. Choose the option that matches how much context remains useful.

### Compact the current conversation

Use `/compact` when you want to continue the same task but the conversation contains old exploration, repeated output, or details that no longer matter. Tell the agent which facts to retain:

```
/compact Retain the approved API contract, the root cause of the pagination failure, the files changed so far, and the required test commands. Discard superseded approaches and repeated command output.
```

Compaction summarizes earlier history. It doesn't change workspace files. Learn more about [compacting conversation context](<https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions#_compact-conversation-context>).

### Fork the conversation

Fork from a checkpoint when you want to explore a different approach while preserving the original conversation. You can compare the results and return to the original session if the alternative is not useful.

A fork creates separate conversation history, but it doesn't always provide separate files. Depending on the session type, the fork might share the same folder or Git worktree. Use a separate worktree-isolated session when both approaches must modify files independently. Learn more about [forking a chat session](<https://code.visualstudio.com/docs/agents/run/sessions/manage-sessions#_fork-a-chat-session>).

### Start a new session

Start a new session when:

* The goal changed into a different task.
* Earlier instructions conflict with the current requirements.
* Repeated corrections make it difficult to identify the authoritative decision.
* You want the agent to investigate the current workspace without inheriting earlier assumptions.

Starting a new session doesn't undo file changes. Review or restore the workspace first, then provide a concise prompt with the current state, accepted decisions, constraints, and validation criteria.

## Diagnose repeated failures

If the agent understands the task but can't make progress, stop automatic retries and investigate the underlying failure.

1. Ask the agent to report the exact command or tool that failed, the first error, and the evidence it used to diagnose the error.
2. Verify prerequisites such as the working directory, installed dependencies, required services, authentication, and permissions.
3. Ask for recovery options that don't repeat the failed action.
4. If debug logging was active for the session, use `/troubleshoot` to analyze the captured logs when you need to understand ignored instructions, unexpected tool behavior, or slow responses.
5. For deeper inspection, use the Agent Debug Log panel (Preview) to review model requests, tool calls, prompt-file discovery, and errors.

For connectivity, extension, customization, and MCP server problems, follow the [AI troubleshooting procedures](<https://code.visualstudio.com/docs/agents/agent-troubleshooting/troubleshooting>). To inspect an agent interaction, see [Debug chat interactions](<https://code.visualstudio.com/docs/agents/agent-troubleshooting/chat-debug-view>).

## Prevent the agent from drifting

Reduce the need for recovery by making the intended outcome observable:

* Define the task boundary, constraints, and files or systems that must not change.
* Include acceptance criteria, expected output, or test commands.
* Ask for a plan before implementation when the task spans several components or contains significant risk.
* Commit a known-good starting point with Git before a large change.
* Keep **Manual permissions** selected for unfamiliar repositories, tools, and workflows.
* Review the first meaningful result instead of waiting until the entire task is complete.
* Start a new session when you switch to an unrelated task.
