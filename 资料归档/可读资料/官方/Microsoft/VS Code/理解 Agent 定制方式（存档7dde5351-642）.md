# 了解【agent】定制

AI 模型拥有广泛的知识，但他们不了解您的代码库、团队实践或开发系统。 Agent 自定义通过添加持久上下文、可重复工作流程、专门角色、外部工具和确定性控制，使 agent 适应您的环境。

本文介绍自定义如何更改 agent、自定义类型有何不同以及如何组合它们。要创建和管理自定义项，请参阅 [自定义 {% data variables.product.prodname_vscode %}](<https://github.com/docs/agent-customization/overview.md>) 中的 agent 行为。

按照实践教程探索自定义选项并为您的项目配置它们。

## 定制如何改变 agent

如果不进行自定义，agent 将根据您的提示、当前对话以及它从您的工作区收集的上下文进行工作。自定义添加的信息或功能在单个提示之外仍然存在。他们可以更改 agent 工作的不同部分：

* **提供上下文**：[指令](<https://github.com/docs/agent-customization/custom-instructions.md>)描述编码标准、架构决策以及agent应遵循的其他规则。
* **定义可重复工作**：[agent skills](<https://github.com/docs/agent-customization/agent-skills.md>)和[提示文件](<https://github.com/docs/agent-customization/prompt-files.md>)包特定于任务的指导，因此您不必在每次对话中描述相同的流程。
* **配置角色**：[自定义agents](<https://github.com/docs/agent-customization/custom-agents.md>)将指令、工具和语言模型组合成专门的agent角色。
* **添加功能**：[MCP服务器](<https://github.com/docs/agent-customization/mcp-servers.md>)提供agent与外部系统（例如数据库、浏览器和API）交互的工具。
* **强制执行操作**：[挂钩](<https://github.com/docs/agent-customization/hooks.md>)在agent循环中的特定点运行命令，与模型是否选择运行它们无关。
* **采用现成的设置**：[agent插件](<https://github.com/docs/agent-customization/agent-plugins.md>)允许您将多种相关的自定义类型安装为一个包。

这些机制影响 agent 的不同层。指令指导模型的决策，工具扩展其可以采取的操作，挂钩在模型决策之外运行。因此，向指令文件添加规则并不等同于使用挂钩强制执行该规则。

通过从一开始就提供 agent 项目上下文，相关定制可以减少来回和返工。避免纠正转向和放弃实施可以帮助减少[AI信用使用](<https://github.com/docs/agents/guides/optimize-usage.md>)。保持自定义的重点，因为它们的内容也会占用模型上下文窗口中的空间。

## 定制选项一目了然

从观察到的问题开始，而不是默认添加自定义。定义代表性任务及其预期结果。如果结果已经满足您的需求，请停止。否则，请尝试解决重复问题的最小更改。

|观察到的行为|尝试的最小改变|
|-------------------|------------------------|
|agent 缺少一次性要求或相关文件|将要求或 [ 上下文 ](<https://github.com/docs/chat/copilot-chat-context.md>) 添加到当前请求|
|agent 多次错过项目范围的命令、约定或架构决策|添加或完善项目说明|
|该问题仅影响某些文件、语言或任务|添加针对性指令|
|您的团队反复解释相同的多步骤流程|创建 agent 技能|
|经常性角色需要集中的指导或有限的工具集|创建自定义 agent|
|agent需要与外部系统交互|添加 MCP 服务器|
|操作必须在独立于模型的生命周期点运行|配置一个钩子|
|您的团队想要安装和维护一组打包的自定义项|使用 agent 插件|

选择定制时请询问以下问题：

* 它应该自动应用，还是仅在您请求时应用？
* 您是否提供指导、定义工作流程、添加功能或执行操作？
* 模型应该决定何时使用它吗？

下表按目的和激活比较了自定义类型。

|需要|使用|示例|激活|
|------|-----|---------|------------|
|在整个项目中应用标准|[常亮指令](<https://github.com/docs/agent-customization/custom-instructions.md>)|需要特定的日志库和错误处理模式|自动包含在每个请求中|
|将指导应用于特定代码或任务|[基于文件的指令](<https://github.com/docs/agent-customization/custom-instructions.md>)|当 agent 与 `.tsx` 文件一起使用时应用 React 约定|当文件与模式匹配或任务与描述匹配时包含|
|使用支持资源教授 agent 工作流程| [Agent skills](<https://github.com/docs/agent-customization/agent-skills.md>) |根据说明、模板文件和设置脚本创建服务|agent在任务匹配时加载技能，或者直接调用它|
|按需运行已保存的任务|[提示文件](<https://github.com/docs/agent-customization/prompt-files.md>)|搭建 React 组件的支架|您将提示符作为斜杠命令调用|
|使用专门的角色和工具配置|[定制 agents](<https://github.com/docs/agent-customization/custom-agents.md>)|使用只读工具检查代码|您选择 agent，将其用作子代理，或将另一个 agent 委托给它|
|连接到外部系统| [MCP](<https://github.com/docs/agent-customization/mcp-servers.md>) |查询数据库或更新问题|agent 在任务需要时调用 MCP 工具|
|在生命周期事件中运行代码|[挂钩](<https://github.com/docs/agent-customization/hooks.md>)|文件编辑后运行格式化程序或阻止有风险的命令|{% data variables.product.prodname_vscode_shortname %} 当配置的事件发生时运行钩子|
|安装打包的自定义设置|[Agent 插件](<https://github.com/docs/agent-customization/agent-plugins.md>)|添加带有技能、agent、挂钩和 MCP 服务器的测试工作流程|每个捆绑定制都遵循自己的激活规则|

当您的主要目标是停止重复项目上下文时，请从说明开始。当您确定重复任务、专门角色、缺少的功能或必须始终运行的操作时，添加其他自定义类型。

## 模型驱动与确定性行为

大多数自定义都会指导模型或为其提供更多选项。该模型解释指令，确定技能是否相关，并选择何时调用可用工具。结果取决于请求、可用上下文和模型推理。

钩子是确定性的。钩子在其配置的生命周期事件发生时运行。当操作必须一致发生时，例如在命令运行之前验证命令或在编辑后启动格式化程序，请使用挂钩。当您想要指导 agent 如何推理或编写代码时，请使用说明。

例如，“编辑文件后运行格式化程序”的指令要求模型记住并执行该操作。无论模型是否记住该指令，为相应生命周期事件配置的钩子都会运行。

## 定制如何结合

定制类型是构建块而不是相互排斥的替代方案。考虑一个为您的项目准备拉取请求的 agent：

1. **说明**提供存储库的编码标准和拉取请求约定。
1. **自定义agent**为agent提供了一个集中的角色，并将其限制为任务所需的工具。
1. **agent 技能** 提供用于准备拉取请求的步骤、脚本和模板。
1. **MCP 服务器** 提供从外部问题跟踪器检索相关问题的工具。
1. **Hooks** 在 agent 编辑文件并阻止不允许的命令后运行所需的验证。

每一层都有单独的职责。您可以在不改变工作流程的情况下更新编码标准，或者更换外部系统而无需重写agent的角色。

插件可以分发完整的配置，例如在您的组织内，以便其他开发人员可以安装相同的技能和 MCP 服务器。

## 定制范围

定义自定义的位置决定了谁可以使用它以及它的应用范围。根据自定义类型，您可以在以下一个或多个级别进行定义：

* **用户**：可供您跨工作区使用。
* **工作空间或存储库**：与项目一起存储并通过源代码管理与贡献者共享。
* **组织**：集中管理并在支持的情况下跨存储库共享。

选择与信息匹配的最窄范围。个人偏好属于用户级别。项目架构和团队工作流程属于存储库。当定制类型支持时，组织范围的需求属于组织级别。

Agent [内存](<https://github.com/docs/agents/run/memory.md>)与项目定制分开。使用本地内存来存储个人偏好或尚未准备好共享的新观察结果。将贡献者所依赖的经过审核的项目规则和工作流程放入存储库文档或自定义中，以便您的团队可以审核和维护它们。

并非每个自定义类型都支持每个范围或 agent 线束。有关受支持的位置和环境，请参阅单独的自定义指南。

# Understand agent customization

AI models have broad knowledge, but they don't know your codebase, team practices, or development systems. Agent customization adapts an agent to your environment by adding persistent context, repeatable workflows, specialized roles, external tools, and deterministic controls.

This article explains how customizations change an agent, how the customization types differ, and how you can combine them. To create and manage customizations, see [Customize agent behavior in {% data variables.product.prodname_vscode %}](<https://github.com/docs/agent-customization/overview.md>).

<div class="docs-action" data-show-in-doc="false" data-show-in-sidebar="true" title="Get started with customizations">
Follow a hands-on tutorial to discover the customization options and configure them for your project.

* [Customize AI for your project](<https://github.com/docs/agents/guides/customize-copilot-guide.md>)

</div>

## How customization changes an agent

Without customization, the agent works from your prompt, the current conversation, and the context it gathers from your workspace. Customizations add information or capabilities that persist beyond a single prompt. They can change different parts of the agent's work:

* **Provide context**: [instructions](<https://github.com/docs/agent-customization/custom-instructions.md>) describe coding standards, architecture decisions, and other rules the agent should follow.
* **Define repeatable work**: [agent skills](<https://github.com/docs/agent-customization/agent-skills.md>) and [prompt files](<https://github.com/docs/agent-customization/prompt-files.md>) package task-specific guidance so you don't have to describe the same process in every conversation.
* **Configure a role**: [custom agents](<https://github.com/docs/agent-customization/custom-agents.md>) combine instructions, tools, and a language model into a specialized agent persona.
* **Add capabilities**: [MCP servers](<https://github.com/docs/agent-customization/mcp-servers.md>) give the agent tools for interacting with external systems such as databases, browsers, and APIs.
* **Enforce actions**: [hooks](<https://github.com/docs/agent-customization/hooks.md>) run commands at specific points in the agent loop, independent of whether the model chooses to run them.
* **Adopt a ready-made setup**: [agent plugins](<https://github.com/docs/agent-customization/agent-plugins.md>) let you install multiple related customization types as one package.

These mechanisms affect different layers of the agent. Instructions guide the model's decisions, tools expand the actions it can take, and hooks run outside the model's decision-making. As a result, adding a rule to an instructions file is not equivalent to enforcing that rule with a hook.

Relevant customizations can reduce back-and-forth and rework by giving the agent project context from the start. Avoiding corrective turns and discarded implementations can help reduce [AI credit usage](<https://github.com/docs/agents/guides/optimize-usage.md>). Keep customizations focused because their content also consumes space in the model's context window.

## Customization options at a glance

Start from an observed problem instead of adding customization by default. Define a representative task and its expected outcome. If the result already meets your needs, stop. Otherwise, try the smallest change that addresses the repeated problem.

| Observed behavior | Smallest change to try |
|-------------------|------------------------|
| The agent misses a one-time requirement or relevant file | Add the requirement or [context](<https://github.com/docs/chat/copilot-chat-context.md>) to the current request |
| The agent repeatedly misses a project-wide command, convention, or architecture decision | Add or refine project instructions |
| The problem only affects certain files, languages, or tasks | Add targeted instructions |
| Your team repeatedly explains the same multi-step process | Create an agent skill |
| A recurring role needs focused instructions or a restricted tool set | Create a custom agent |
| The agent needs to interact with an external system | Add an MCP server |
| An action must run at a lifecycle point independently of the model | Configure a hook |
| Your team wants to install and maintain a packaged set of customizations | Use an agent plugin |

Ask the following questions when choosing a customization:

* Should it apply automatically, or only when you request it?
* Are you providing guidance, defining a workflow, adding a capability, or enforcing an action?
* Should the model decide when to use it?

The following table compares the customization types by purpose and activation.

| Need | Use | Example | Activation |
|------|-----|---------|------------|
| Apply standards across a project | [Always-on instructions](<https://github.com/docs/agent-customization/custom-instructions.md>) | Require a specific logging library and error-handling pattern | Automatically included in each request |
| Apply guidance to specific code or tasks | [File-based instructions](<https://github.com/docs/agent-customization/custom-instructions.md>) | Apply React conventions when the agent works with `.tsx` files | Included when files match a pattern or the task matches the description |
| Teach the agent a workflow with supporting resources | [Agent skills](<https://github.com/docs/agent-customization/agent-skills.md>) | Create a service from instructions, template files, and a setup script | The agent loads the skill when the task matches, or you invoke it directly |
| Run a saved task on demand | [Prompt files](<https://github.com/docs/agent-customization/prompt-files.md>) | Scaffold a React component | You invoke the prompt as a slash command |
| Use a specialized role and tool configuration | [Custom agents](<https://github.com/docs/agent-customization/custom-agents.md>) | Review code with read-only tools | You select the agent, use it as a subagent, or another agent delegates to it |
| Connect to an external system | [MCP](<https://github.com/docs/agent-customization/mcp-servers.md>) | Query a database or update an issue | The agent calls an MCP tool when the task requires it |
| Run code at a lifecycle event | [Hooks](<https://github.com/docs/agent-customization/hooks.md>) | Run a formatter after a file edit or block a risky command | {% data variables.product.prodname_vscode_shortname %} runs the hook when the configured event occurs |
| Install a packaged customization setup | [Agent plugins](<https://github.com/docs/agent-customization/agent-plugins.md>) | Add a testing workflow with a skill, agent, hooks, and MCP server | Each bundled customization follows its own activation rules |

Start with instructions when your main goal is to stop repeating project context. Add other customization types when you identify a recurring task, specialized role, missing capability, or action that must always run.

## Model-driven vs. deterministic behavior

Most customizations guide the model or give it more options. The model interprets instructions, decides whether a skill is relevant, and chooses when to call an available tool. The result depends on the request, available context, and model reasoning.

Hooks are deterministic. A hook runs when its configured lifecycle event occurs. Use a hook when an action must happen consistently, such as validating a command before it runs or starting a formatter after an edit. Use instructions when you want to guide how the agent reasons or writes code.

For example, an instruction that says "run the formatter after editing a file" asks the model to remember and perform that action. A hook configured for the corresponding lifecycle event runs regardless of whether the model remembers the instruction.

## How customizations combine

Customization types are building blocks rather than mutually exclusive alternatives. Consider an agent that prepares a pull request for your project:

1. **Instructions** provide the repository's coding standards and pull request conventions.
1. A **custom agent** gives the agent a focused role and limits it to the tools needed for the task.
1. An **agent skill** supplies the steps, scripts, and templates for preparing the pull request.
1. An **MCP server** provides tools to retrieve the related issue from an external issue tracker.
1. **Hooks** run required validation after the agent edits files and block disallowed commands.

Each layer has a separate responsibility. You can update the coding standards without changing the workflow, or replace the external system without rewriting the agent's role.

A plugin can distribute the complete configuration, for example within your organization, so that other developers can install the same skills and MCP servers.

## Customization scope

Where you define a customization determines who can use it and where it applies. Depending on the customization type, you can define it at one or more of these levels:

* **User**: available to you across workspaces.
* **Workspace or repository**: stored with the project and shared with contributors through source control.
* **Organization**: managed centrally and shared across repositories, where supported.

Choose the narrowest scope that matches the information. Personal preferences belong at the user level. Project architecture and team workflows belong in the repository. Organization-wide requirements belong at the organization level when the customization type supports it.

Agent [memory](<https://github.com/docs/agents/run/memory.md>) is separate from project customization. Use local memory for personal preferences or emerging observations that aren't ready to share. Put reviewed project rules and workflows that contributors depend on in repository documentation or customizations so your team can review and maintain them.

Not every customization type supports every scope or agent harness. See the individual customization guide for supported locations and environments.
