AgentpermissionsSection标题“Agent权限”

Antigravity 使用统一的细粒度权限引擎来评估拒绝、询问和允许访问列表中的
敏感工具操作。如果您在 Gemini Enterprise 中使用反重力，请参阅 Gemini Enterprise 中的反重力。

macOS 和 LinuxSection 标题为“macOS 和 Linux”
Antigravity 使用强大、统一的权限引擎来保护您的环境，同时启用自主工作流程。 agent 执行的每个敏感操作都表示为格式为操作（目标）的权限资源。
 权限通过三个不同的访问列表进行评估：

拒绝：立即阻止该操作。

询问：agent 暂停并提示您明确批准，然后再继续。

允许：允许该操作而不提示。

注意
优先规则：冲突规则严格按照优先顺序进行评估：拒绝 > 询问 > 允许。例如，如果您在询问中配置command(*)并在允许中配置command(git)，则询问规则优先，并在每个命令之前进行提示。

沙盒中的 PresetSandboxTerminal CommandsFile AccessMCP 和 WebDefaultEnabledAllowed； Ask outsideWorkspace + temp dirsAskRequest ReviewDisabledAlways askWorkspace onlyAskTurboDisabledAllowed（无限制）完全filesystemAllowed
默认情况下，终端命令在隔离的终端沙箱内运行，访问权限仅限于您的工作区和临时目录，并且没有网络访问权限。当命令需要网络连接或主机资源时，agent 请求在沙箱外运行它 - 提示您批准，除非命令(...) 允许规则覆盖。
在“设置”>“常规”>“权限设置”下配置您的预设，或在“设置”>“项目”下按项目覆盖它（新项目默认为“继承常规”，它遵循您的全局预设）。有关每个预设的更多详细信息，请参阅 Agent 设置。

全局通配符语法 (*)：跨所有支持的操作类型（例如 read_file(*), 命令(*) 和 mcp(*))，传递全局通配符 * 匹配整个操作命名空间内的所有目标。当命令需要精确的 matchSection 标题为“当命令需要完全匹配时”
某些 shell 构造可以将任意命令执行隐藏在其他良性前缀后面，例如，命令或进程替换（$(...)、反引号、<(...)）、算术上下文（$((...))）、大括号扩展（{a,b}）、非文字命令名称、网络或文件描述符重定向以及执行子命令的开发人员工具标志（例如 git -c core.pager=<cmd> 或焦油 --to-command）。当 Antigravity 检测到其中任何一个（或无法清楚地解析命令）时，它会禁用整个命令行的前缀匹配：仅当规则与整行字符逐个字符匹配（或跨越正则表达式的完整原始行：规则）时，命令才会运行而不提示，否则回退到 Ask。
标准 shell 组合仍然正常前缀匹配：管道、&&/||/；链、引用文字、普通 $VAR 参数、简单文件重定向和透明包装器（timeout、nohup、nice、env，其内部命令自行评估）。例如，如果 command(git) 位于允许列表中，则 git status && git log 会在没有提示的情况下运行，而 git log $(whoami) 会提示批准。理解 read_url 和 execute_url 横跨 platformSection 标题为“理解 read_url 和 execute_url 跨平台”
的 read_url 权限控制反重力三个不同领域的出站网络连接：

read_url 工具：当 agent 使用内部 read_url_content 工具获取网页 Markdown 进行研究时，它会检查您的 read_url 资助。

浏览器子代理和工具：驱动 Chrome 会话时，read_url 授权加载和查看目标域。然而，交互式 UI 驱动（单击按钮、输入文本）由 execute_url 独立控制。

终端沙箱：read_url下授予的任何域都会直接编译到沙箱的出站网络白名单中，允许像curl或npm这样的命令连接到授权主机。
跨平台命令和路径matchingSection标题为“跨平台命令和路径”匹配”
反重力可确保您的权限规则一致地工作，无论您是在 macOS、Linux 还是 Windows 上进行开发。在 macOS 和 Linux 上，路径使用标准正斜杠 (/)。在 Windows 上，Antigravity 在规则评估之前自动规范化路径，方法是剥离驱动器号（例如 C:）并将所有反斜杠（\) 转换为正斜杠 (/)）。
标题为“隐式权限规则”的隐式权限 rulesSection
Antigravity 应用以下隐式权限规则：

写入意味着读取：在路径上允许 write_file 会自动在该路径上授予 read_file。

拒绝读取意味着拒绝写入：拒绝路径上的 read_file 会立即阻止该路径上的 write_file。

交互权限promptsSection标题为“交互权限提示”
当agent遇到需要批准的操作（询问模式）时，编辑器中会出现交互卡。在对文件、URL或MCP权限点击“允许”之前，您可以直接编辑提示卡中的目标字符串来扩大授予范围（例如将/project/file.txt这样的单个文件请求扩大到父目录/project）。反重力验证您编辑的目标是否安全地覆盖该操作，并在该回合的剩余时间内应用扩展的授权，从而防止重复提示相关操作。 （注意：终端命令不支持范围编辑）。
终端命令和标题为“终端命令和沙箱”的sandboxSection
在默认预设下，agent在隔离的终端沙箱内运行终端命令，默认情况下只能访问您的工作区和系统临时目录，并且没有网络访问权限。命令可以在沙箱中运行，无需手动批准，并且您的权限授予可以进一步决定沙箱可以达到的范围：

read_file 下授予的路径动态填充沙箱的只读文件系统白名单。

write_file 下授予的路径动态填充沙箱的读写文件系统白名单。

read_url 下授予的域定义出站网络访问策略。

由于某些命令无法在沙箱中运行（例如，那些需要网络访问的命令），agent 仍然可以选择在沙箱外运行命令。此类命令会提示您批准，除非已被命令规则允许或拒绝。
默认系统行为和guardrailsSection标题为“默认系统行为和护栏”
当您的“允许”、“拒绝”或“询问”列表中未明确列出某个操作时，反重力会回退到安全系统默认值：

命令：在默认预设下，命令在沙箱内运行时不会提示，并且需要批准才能在沙箱外运行。

工作区文件：允许在活动项目目录中读取和写入文件而无需提示，而非工作区文件则需要批准。

Web 浏览默认为“询问”：read_url 和 execute_url 的操作默认为“询问”。在 agent 导航到或在任何网页上启动之前，它会暂停并提示您明确批准，除非配置了允许规则。

MCP 工具默认询问：未配置 MCP 工具调用提示进行批准。

注意
显式规则始终优先于默认规则。即使命令在沙箱中运行时不会提示，诸如 command(rm) 之类的询问规则也会提示批准。
标题为“配置示例”的配置 examplesSection
以下示例显示允许列表的规则，该规则定义了在没有提示的情况下运行的操作：

终端沙箱：在沙箱模式下，任何授予的域 read_url 直接编译到容器的出站网络白名单中（AllowedDomains），允许像curl或这样的命令 npm 连接到授权主机。

Agent permissionsSection titled “Agent permissions”

Antigravity uses a unified fine-grained permission engine to evaluate
sensitive tool operations across Deny, Ask, and Allow access lists. If you are using Antigravity with Gemini Enterprise, see Antigravity in Gemini Enterprise.

Antigravity CLI
Antigravity 2.0Section titled “Antigravity 2.0”
Note
Antigravity’s updated permission system is currently available on macOS and
Linux. On Windows, Antigravity continues to use the previous permission
system. Refer to the Windows section for details.
macOS and LinuxSection titled “macOS and Linux”
Antigravity uses a robust, unified permission engine to secure your environment while enabling autonomous workflows. Every sensitive operation the agent performs is represented as a permission resource formatted as action(target).
Permissions are evaluated across three distinct access lists:

Deny: The action is blocked immediately.

Ask: The agent pauses and prompts for your explicit approval before proceeding.

Allow: The action is allowed without prompting.

Note
Precedence rule: Conflicting rules are strictly evaluated in priority order: Deny > Ask > Allow. For example, if you configure command(*) in Ask and command(git) in Allow, the Ask rule takes precedence and prompts before every command.
Permission presetsSection titled “Permission presets”
The permission preset controls how agent actions are approved. Your configured allow, deny, and ask rules are layered on top of the preset and always take precedence:

Under Default, terminal commands run inside the isolated Terminal sandbox with access restricted to your workspace and temp directories and no network access. When a command needs network connectivity or host resources, the agent requests to run it outside the sandbox—prompting for your approval unless covered by a command(...) allow rule.
Configure your preset under Settings > General > Permission Settings, or override it per project under Settings > Projects (new projects default to Inherit General, which follows your global preset). Refer to Agent settings for more detail on each preset.

Certain shell constructs can hide arbitrary command execution behind an otherwise benign prefix—for example, command or process substitution ($(...), backticks, <(...)), arithmetic contexts ($((...))), brace expansion ({a,b}), non-literal command names, network or file descriptor redirections, and developer-tool flags that execute subcommands (such as git -c core.pager=<cmd> or tar --to-command). When Antigravity detects any of these (or cannot cleanly parse the command), it disables prefix matching for the entire command line: the command runs without prompting only if a rule matches the full line character-for-character (or across the full raw line for regex: rules), and otherwise falls back to Ask.
Standard shell composition still prefix-matches normally: pipelines, &&/||/; chains, quoted literals, plain $VAR arguments, simple file redirects, and transparent wrappers (timeout, nohup, nice, env, whose inner command is evaluated on its own). The read_url permission governs outbound web connectivity across three distinct areas of Antigravity:

The read_url tool: When the agent uses the internal read_url_content tool to fetch web page Markdown for research, it checks your read_url grants.

Browser subagent and tool: When driving Chrome sessions, read_url authorizes loading and viewing the target domain. However, interactive UI actuation (clicking buttons, typing text) is governed independently by execute_url.

Terminal sandboxing: Any domain granted under read_url is compiled directly into the sandbox’s outbound network allowlist, permitting commands like curl or npm to connect to authorized hosts.
Cross-platform command and path matchingSection titled “Cross-platform command and path matching”
Antigravity ensures your permission rules work consistently whether you’re developing on macOS, Linux, or Windows. On macOS and Linux, paths use standard forward slashes (/). On Windows, Antigravity automatically normalizes paths prior to rule evaluation by stripping drive letters (for example, C:) and converting all backslashes (\) to forward slashes (/).
Implicit permission rulesSection titled “Implicit permission rules”
Antigravity applies the following implicit permission rules:

Write implies read: Allowing write_file on a path automatically grants read_file on that path.

Deny read implies deny write: Denying read_file on a path immediately blocks write_file on that path.

Interactive permission promptsSection titled “Interactive permission prompts”
When the agent encounters an operation requiring approval (Ask mode), an interactive card appears in your editor. Before clicking Allow for file, URL, or MCP permissions, you can directly edit the target string in the prompt card to expand the granted scope (for example, broadening a single file request like /project/file.txt to the parent directory /project). Antigravity validates that your edited target safely covers the operation and applies the expanded grant for the remainder of the turn, preventing repeated prompts for related operations. (Note: Scope editing isn’t supported for terminal commands).
Terminal commands and the sandboxSection titled “Terminal commands and the sandbox”
Under the Default preset, the agent runs terminal commands inside an isolated Terminal sandbox, which by default has access only to your workspace and system temp directories, and no network access. Commands can run without manual approval in the sandbox, and your permission grants can further shape what the sandbox can reach:

Paths granted under read_file dynamically populate the sandbox’s read-only filesystem allowlist.

Paths granted under write_file dynamically populate the sandbox’s read-write filesystem allowlist.

Domains granted under read_url define outbound network access policies.

Because some commands cannot run in the sandbox—for example, those requiring network access—the agent can still choose to run commands outside the sandbox. Such commands prompt for your approval, unless already allowed or denied by a command rule.
Default system behaviors and guardrailsSection titled “Default system behaviors and guardrails”
When an action isn’t explicitly listed in your Allow, Deny, or Ask lists, Antigravity falls back to secure system defaults:

Commands: Under the Default preset, commands run without prompting inside the sandbox and require approval to run outside it.

Workspace files: Reading and writing files inside your active project directory is allowed without prompting, while non-workspace files require approval.

Web browsing defaults to Ask: Actions for read_url and execute_url default to Ask. Before the agent navigates to or actuates on any web page, it pauses and prompts for your explicit approval unless an allow rule is configured.

MCP tools default to Ask: Unconfigured MCP tool calls prompt for approval.

Note
Explicit rules always take precedence over defaults. An Ask rule such as command(rm) prompts for approval even when the command would otherwise run without prompting in the sandbox.

Certain shell constructs can hide arbitrary command execution behind an otherwise benign prefix—for example, command or process substitution ($(...), backticks, <(...)), arithmetic contexts ($((...))), brace expansion ({a,b}), non-literal command names, network or file descriptor redirections, and developer-tool flags that execute subcommands (such as git -c core.pager=<cmd> or tar --to-command). On Windows shells like PowerShell or Command Prompt, commands whose syntax cannot be cleanly split into separate words also fall into this category. When Antigravity detects any of these, it disables prefix matching for the entire command line: the command runs without prompting only if a rule matches the full line character-for-character (or across the full raw line for regex: rules, such as command(regex:git .*)), and otherwise falls back to Ask.
Standard shell composition still prefix-matches normally: pipelines, &&/||/; chains, quoted literals, plain $VAR arguments, simple file redirects, and transparent wrappers (timeout, nohup, nice, env, whose inner command is evaluated on its own). The read_url permission governs outbound web connectivity across three distinct areas of Antigravity:

The read_url tool: When the agent uses the internal read_url_content tool to fetch web page Markdown for research, it checks your read_url grants.

Browser subagent and tool: When driving Chrome sessions, read_url authorizes loading and viewing the target domain. However, interactive UI actuation (clicking buttons, typing text) is governed independently by execute_url.

Terminal sandboxing: In sandbox mode, any domain granted under read_url is compiled directly into the container’s outbound network allowlist (AllowedDomains), permitting commands like curl or npm to connect to authorized hosts.
