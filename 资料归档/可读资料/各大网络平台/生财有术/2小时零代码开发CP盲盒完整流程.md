一、为什么写这篇

前两天看到生财官方发的 520 活动——「生财 CP 盲盒交友」。

规则很轻：评论区投盲盒（昵称 / 城市 / MBTI / 3 个标签 / 想找的 CP 类型 / 想聊的话题），看到同频的人就找鱼丸表达"想拆盒"的意愿，鱼丸再去对接。

我看完心痒：这个机制如果做成一个 App，体验会好太多——可筛选、可双向匹配、可承接长期复用。

于是开干。 2 小时，0 行手写代码，做出一个完整的 Web App ：邀请码注册、盲盒卡 CRUD、瀑布流 + Tinder 滑卡两种浏览模式、双向互点自动 match、鱼丸协助工单、举报拉黑、鱼丸后台。能直接 gunicorn 上线那种。

但这篇不是来炫成果的。

这篇要做的事是：把我 2 小时跑通的全流程拆给你看，让你看完今天就能动手做你自己的产品 。生财圈友里太多人有想法、有场景、有用户，就差"我不会写代码"这一道墙。

而这道墙，2026 年的今天， 只要会用 vibe coding，就能彻底推倒 。

下面是完整教程。每一步都有可以直接抄走的提示词模板。

二、先纠正一个核心认知，不然学了也白学

90% 的人玩 vibe coding 没出活，问题根本不在 AI， 在你自己定位错了 。

错误定位：你以为 vibe coding 是"我躺着，AI 干活"。 正确定位：你是 AI 团队的 产品经理 + 架构师 。你不用敲代码，但你必须负责定规则、拆任务、控方向。

绝大多数人卡在最底层——AI 报错就贴回去，AI 改完再贴回去，改 5 次还跑不起来就骂 AI 不行。

真相是： 你没给 AI 边界，AI 就只能瞎写；你没给 AI 上下文，AI 就只能现编。

vibe coding 不是让你不动脑，是让你换个地方动脑——从"逐行写代码"换成"画边界、定规则、拆任务"。

这套认知没建立起来，下面的 SOP 学了也白学 。

三、四步 SOP 教程（核心）

我做了 80+ 个 vibe coding 项目沉淀出来的完整流程是 4 步：

需求对齐 → 技术选型 → 原型生成 → AI 流水线开发

每一步都有死规则、有可复制的提示词模板、有踩坑后总结出来的反直觉判断准则。下面我用 520 CP 盲盒这个例子带你走一遍 每一步内部的子步骤 ，看完你换成自己的项目就能直接套。

时间分配参考：

| Step | 内容 | 时间 |
| --- | --- | --- |
| 1 | 需求对齐 | 15–20 min |
| 2 | 技术选型 | 10 min |
| 3 | 原型生成 | 10 min |
| 4 | AI 流水线开发 | 60–80 min |
| 合计 | 完整 MVP | ≈ 2 h |

第 1 步｜需求对齐：把"想法"压成"封闭决策"（15–20 分钟）

这一步是整套 SOP 里 最被低估 的一步。我做坏掉的 80 个项目里至少有 15 个是死在这一步。

1.1 为什么 90% 的人在这一步就翻车

直接对 AI 说"帮我做一个 XX 系统"——AI 听了一定开始自由发挥。一会儿给你加星座匹配算法，一会儿给你接短信验证码，一会儿要你装 Redis。等你反应过来，已经写了 3000 行没用的代码。

根本原因 ：你脑子里的需求是模糊的、连续的、有歧义的；AI 接收到模糊输入就会按"通用最佳实践"自由发挥，而通用最佳实践 = 大公司大项目的范式 = 你完全用不上的过度设计。

核心心法 ：你需求模糊一寸，AI 自由发挥一尺。

ChatGPT 给我列了 12 个：

| 决策点 | 我的选择 |
| --- | --- |
| 邀请码用一次性还是次数限制？ | 一次性（防扩散） |
| 一个人能投几个盲盒？ | 一个（UniqueConstraint） |
| match 后是否解锁联系方式？ | 不解锁（对齐活动规则） |
| Swipe 模式怎么防止刷过的卡又出现？ | 加 Pass 表去重 |
| 鱼丸申请的流转状态有几个？ | pending / handling / done / rejected |
| 被举报后是冻结还是隐藏？ | 隐藏（保留数据，鱼丸定夺） |
| 用户能修改自己的盲盒吗？ | 能，但有版本号防止并发 |
| 互点的 wish 能撤回吗？ | 24h 内能撤回，超过不能 |
| match 成功是双方都通知还是单方通知？ | 双方都通知 |
| 鱼丸账号怎么开？ | 数据库直接改 role 字段，不开放注册入口 |
| 数据库定期清理吗？ | 每期活动结束归档，不清理 |
| 用户自删盲盒后旧的 match 怎么办？ | 保留，标记为"对方已下架" |

每一条都当场拍板 。不要"以后再说"，"以后再说"的决策点 100% 会在开发到一半时炸出来逼你停下手忙脚乱。

1.6 这一步的产出物

一份不超过 1 页 A4 的「产品定义 + 功能优先级 + 决策清单 + 红线」文档。

后面所有跟 AI 的对话都基于这份文档。 这份文档稳定，AI 就稳定；这份文档模糊，AI 就漂移 。

第 2 步｜技术选型：在"轻"和"重"之间，永远选轻（10 分钟）

2.1 这一步你做错会怎样

AI 默认会给你推荐"全家桶"——Next.js + tRPC + Prisma + PostgreSQL + Redis + Docker Compose + Kubernetes。听起来很专业，但有两个致命问题：

2.

每多一个技术栈，AI 出错的面积就大一圈 ——AI 不仅要写业务代码，还要正确配置每一层依赖关系，配错一处可能调一小时

我做过最痛的一次：让 AI 选了"工业级"栈做一个小工具，光 Docker Compose 调通就花了 4 个小时，业务代码本身只用了 30 分钟。

2.2 选型的 5 个维度，逐个最小化

vibe coding 选型不是选"最好"的，是选"最少坑"的。5 个维度逐个挑：

| 维度 | 重型选择 | 轻型选择（我推荐） | 何时该重型 |
| --- | --- | --- | --- |
| 后端框架 | Spring Boot / NestJS | Flask / FastAPI / Express | 团队已有重型经验 |
| 数据库 | MySQL / PostgreSQL | SQLite（WAL 模式） | 写并发 > 100 QPS |
| 缓存 | Redis | 直接不用 | 真有热点数据再加 |
| 前端框架 | React + 全家桶 | Vue 3 + Vite | 团队已经在用 React |
| UI 库 | 自己撸 / Material UI | Vant（移动端）/ Element Plus（桌面） | 设计师定制需求强 |
| 部署 | K8s / Docker Compose | gunicorn + Caddy / Vercel | 多机房多副本 |

百人到千人规模的内测项目， 全部选右边 。理由：

SQLite WAL 模式 ，几百到几千用户读多写少完全够用，省掉数据库部署和运维

Flask 单文件能跑 ，gunicorn 两个 worker 起飞，不需要 Docker

Vant 自带移动端组件 （适配微信内嵌浏览器），省掉 80% 样式工作

Tailwind 三个 class 拼一个组件 ，调色全走 config 不硬编码

2.4 选型的唯一判断准则

最少的代码完成最多的事。 能用 SQLite 不用 MySQL，能用 Vant 不自己撸组件，能 Tailwind 不写 CSS，能 Vite 不用 Webpack。

我做了 80 个项目，能用"轻型版"做完的占 70 个以上。 真正需要重型版的项目，你自己心里有数——通常是有团队、有运维、有 DAU > 1 万的需求 。

第 3 步｜让 AI 生成原型图：给 AI 一个视觉锚点（10 分钟）

3.1 为什么不能跳过这一步

你不给 AI 视觉参考，它默认给你做 Bootstrap 风的灰白蓝——丑、没辨识度、像 2014 年的后台管理系统。

更重要的是： 人类对"美"的描述是模糊的，但人类对"美"的识别是精确的 。你说"现代、年轻、活泼"，AI 给你 100 种诠释，但你拿一张图说"做成这样"，AI 90% 还原。

3.2 四个原型生成工具横向对比

第 4 步｜进入 Claude Code：写规则 + 拆任务（核心 60–80 分钟）

这一步是整套 SOP 投入产出比最高的一步。前 3 步做好了，这一步就只是把决策落实成代码。

但绝大多数人在这一步会反复翻车，原因就一个： 他们以为这一步是"对话"，其实这一步是"管理" 。你不是在和 AI 聊天，你是在管理一个 AI 工程团队。

4.1 第一件事：写一份 AI 永远要先读的"宪法"—— [CLAUDE.md](<http://claude.md/>)

Claude Code 有一个机制： 项目根目录下的 CLAUDE.md 会被自动注入到每次对话的上下文 。

这相当于你给 AI 装了一个"长期记忆"。无论你换多少个对话窗口、写多少天，AI 永远先读这份文档。

为什么这份文档关键 ：AI 经常脑补。看到 match 表就想给你加微信号字段，看到用户表就想给你加积分系统，看到列表页就想给你加排行榜。 把红线写死，它就不敢碰 。

我做 80 个项目的经验： [CLAUDE.md ](<http://claude.md/>)每加 1 条规则，后期 debug 时间减少 10 分钟 。这是杠杆最高的投资。

4.2 第二件事：把项目拆成 5–8 个 Phase

拆 Phase 的颗粒度有个经验公式：

一个 Phase = AI 能在 15–30 分钟内做完 + 完成后能独立验证

太大（> 30 分钟）AI 上下文容易飘；太小（< 10 分钟）你来回切换成本太高。

4.5 AI 卡住 / 报错 / 瞎搞时怎么办

这一步最多人栽跟头。三个止血规则：

规则 A：报错连续 2 次没解决，停止盲改

很多人是 AI 报错就贴回去，AI 改完再报错再贴回去——5 轮下来代码已经面目全非。

正确做法： 第 3 次报错就停下来 ，开新对话窗口，把"原始任务 + 当前代码 + 当前报错"一起贴过去，让一个干净的 AI 重新看。

规则 B：AI 开始改你没让它改的文件，立即中断

只要发现 AI 改了"动作范围"外的文件，立刻按 ESC 中断，发：

"你刚刚改了 X 文件，这不在动作范围内。撤销那部分修改，只做我让你做的事。"

这一步必须强硬 。AI 一旦发现你纵容它越界，后面会越界得越来越离谱。

规则 C：上下文超过 1 万行就开新窗口

Claude Code 的上下文虽然大，但超过一定量后注意力会涣散，开始忘记 [CLAUDE.md ](<http://claude.md/>)里的规则。

信号 ：AI 开始重复确认你刚刚说过的事 / 重新引入你已经删过的代码 / 开始用项目里不存在的函数名。

看到信号立即开新窗口，让它先读 [CLAUDE.md ](<http://claude.md/>)，再贴当前任务。

坑 1：核心业务逻辑必须开"评审员"窗口
